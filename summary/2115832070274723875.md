Sashank Gondala (FurtherAI) shares nine months of lessons building an AI-native engineering org, in a long-form thread prompted by Will Larson's question about evaluating engineering managers for AI skills.

Part 1 reports the shipping numbers: ~5x more merged code changes per engineer since January with a revert rate under 0.5%. He is explicit that handing out coding agents did not produce this on its own — each sped-up step just piled work onto the next, so the team reworked the whole pipeline stage by stage: agents writing code (March), tests alongside code (91% of changes, up from 15%), AI review before human review (99% of changes), parallelized affected-only CI (20x tests in the same 17 minutes), automated bug intake via ClaudeTag in Slack (60% of tickets), tribal-knowledge rules converted into Python checks that fail builds (21 rules), autonomous merging of low-risk changes (up to a third of changes merge with no person), and Slack "code channels" where anyone describes a change and an agent opens a PR. In-house Poirot and Sherlock agents investigate production issues with logs, metrics, traces and read-only DB access; agents routinely hand work to each other (ClaudeTag triages, Devin builds, Poirot fetches data). Side effect: the designer has merged ~50 changes since August, and non-engineers ship UI tweaks from Slack. The cost: much of the summer's engineering went into tests and tooling, with customer-facing changes per engineer stuck at 17–30/month until September jumped to 45.

Part 2 turns to the organisation. With building compressed, planning and review now dominate — in his simplified model, 70% of feature time, up from 40% — and those decisions traditionally route through managers, PMs and designers. His bet is to push ownership to engineers rather than add management layers, redefining seniority by end-to-end problem ownership (junior: build with an agent and know when it's wrong; senior: plan and review their own work; staff: take a vague problem, make the tradeoffs, own the success number). Managers are asked to "be in the work" (use features on staging as an end user) and to be product-savvy, so small product decisions don't need a PM or designer. He flags that making the whole organisation move at the engineers' new speed will be harder than automating code, tests and reviews.
