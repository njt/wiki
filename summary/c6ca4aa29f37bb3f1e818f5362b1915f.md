Verbatim transcript of a MotherDuck webinar with Alex Monahan and Matt Martin on tuning DuckLake for speed and cost, plus a pre-written digest at the top of the gist. The speakers' falsifiable claim: Iceberg and Delta "put their metadata in the wrong spot" — on object storage, where each serial metadata request costs ~100ms — whereas DuckLake's SQL-database catalog makes one ~5ms round trip, making it the first lakehouse format that can genuinely serve interactive, low-latency workloads.

Tuning is organised around DuckLake's three buckets — catalog/metadata (a relational DB like Postgres), storage (parquet on object store), and compute (usually DuckDB) — with rules of thumb by workload shape: big reads → file layout (partitioning and sorting, including Z-order/Hilbert space-filling curves for multi-column filters and "hidden partitioning" so analysts can filter on the original column); small reads → catalog; big writes → compute; many small writes → inlining, DuckLake's killer feature, which buffers inserts ≤10 rows in the catalog transactionally and flushes at ~target parquet file size.

Parquet settings: parquet v2, zstandard over snappy, row-group size 2–4x with a target of ~10 row groups per file — tuned jointly via design of experiments, with an agent running the benchmarks ("sequential tuning lands in local optima"), worth ~40%. Catalog tuning: index the column-statistics table, size the DB so the whole catalog fits in RAM (a petabyte-scale catalog is only a few gigs), and expire snapshots with a progressive stair-step schedule. Maintenance is mandatory (compact deletions and files to ~1GB, 10-day deletion window so vacation doesn't force cold retrieval). DuckDB 2.0's asyncio gives ~3x faster bulk reads via ~4 background threads per core.

The recurring method throughout: measure before tuning (Postgres slow-query logs with explain plans, DuckDB JSON profiling), then point an AI agent at the logs and ask what the bottleneck is — "agents can shred through JSON like nobody's business."
