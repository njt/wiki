A Grist webinar transcript (heavily edited summary followed by the verbatim talk) demonstrating app-building in Grist via the MCP connector, live with Claude. Two build modes are contrasted: "from prompt" greenfield builds and "from spreadsheet" migrations.

For greenfield builds the presenter uses a structured three-part prompt — use case and data, important views and workflows, user permissions — and deliberately lets the model do domain research (an electrician work-order tracker was built without naming any fields; Claude was asked to research typical workflow statuses and safety procedures). For migrations the presenter imposes a "harness": a planning phase where Claude must write a markdown plan file ("Do not build it in grist yet") broken into three stages — data structure and formulas, views, permissions — before building, stage by stage with human feedback. The planning file doubles as an audit trail ("what did we say we were going to build? What did we actually build?"). Two heuristics flag a complex spreadsheet needing staged building: could you explain it to someone else without confusing yourself, and are there more hidden sheets than unhidden sheets?

The running demonstration of overbuilding — Claude adding purchasing workflows to a hobby brewery spreadsheet — is the motivation for the harness: "Claud's here building a castle every time." The second half argues Grist's spreadsheet-database architecture makes it uniquely suited to vibe coding: no deployment step (the app is live immediately), human or agent can edit anything the other can, tables link via one-line reference columns rather than queries, the app is a self-contained file you can copy/download/roll back, and access rules are auditable in the UI via "view as" — and enforced server-side, even inside custom HTML/JS widgets whose code now lives in the document metadata. Notable side points: the connector injects instructions (dummy data, Grist-native styling, light/dark mode) agents wouldn't follow alone; Claude applied database normalisation unprompted (collapsing separate ingredient sheets into one table with a category column); a structure-only download lets agents work on templates without exposing sensitive data; snapshots are readable (not editable) so agents can recover from mistakes. The Q&A candidly leaves unresolved: no cost/token accounting, anecdotal error rates, no staging-vs-production story yet, and an unexamined lock-in tension (the presenter stopped hosting widget code externally, contradicting the portability pitch).
