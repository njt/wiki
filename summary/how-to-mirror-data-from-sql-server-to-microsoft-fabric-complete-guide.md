Redgate's Simple-Talk runs a complete guide to Microsoft Fabric mirroring for SQL Server — the feature that replicates operational SQL Server data into OneLake in near real time, so it is available for Fabric reporting, analytics, and notebooks without building a traditional batch ETL pipeline. The guide's central claim is a fit argument, not a cheerleading one: mirroring has low insert/update/delete replication latency and suits "current or near-current analytical copies," but it does not guarantee the freshness of synchronous availability-group replicas, and "data transformation still needs to happen somewhere in the system." Heavy reshaping before the data is useful is a reason to pick another approach.

The load-bearing fact is a version split. For SQL Server 2016–2022, mirroring rides on Change Data Capture (CDC): the source database must support CDC, which setup either uses or configures. On Windows it is supported in Standard, Enterprise, and Developer editions; on Linux only from SQL Server 2017 CU18; and it works against on-premises instances, Azure VMs, and even non-Azure clouds like AWS and GCP. SQL Server 2025 changes the mechanism entirely: it uses Fabric's change feed instead of CDC — "closer to what's in Azure SQL Database" — with different change-feed DMVs and stored procedures, so design and troubleshooting assumptions must change too. The author judges this the better direction, but flags that 2025 mirroring currently supports only on-premises instances: no Azure VMs, no Linux at all.

Setup for 2025 is a hybrid-management story: the server must be connected to Azure Arc (with the Azure Extension for SQL Server), a data gateway (on-premises data gateway or virtual network data gateway) must reach the instance, and PowerShell, an Azure Arc user account, and registered resource providers are prerequisites before the portal GUI makes the rest simple. Identity rides on Arc: a managed identity (checkable via `sys.dm_server_managed_identities`) needs read/write on the Fabric workspace, while the source uses a dedicated least-privilege user — SQL authentication or Microsoft Entra ID — granted `SELECT`, `ALTER ANY EXTERNAL MIRROR`, `VIEW DATABASE PERFORMANCE STATE`, and `VIEW DATABASE SECURITY STATE`. With Always On availability groups, configuration must target the listener rather than the primary node, and the system-assigned managed identity of *every* secondary needs at least contributor on the workspace for failover to keep working.

The limitations come in three tiers. Database-level blockers: Azure Synapse Link, an existing mirror, and replication; CDC stops being compatible in 2025; `.dacpac` deployments need `/p:DoNotAlterReplicatedObjects=False`; row-level security, object-level security, and Dynamic Data Masking are not replicated; cross-tenant setups are unsupported. Table-level: at most 1,000 tables, primary key/clustered index type restrictions, no clustered columnstore, and no temporal/ledger history tables, Always Encrypted columns, in-memory/graph/external tables, partition switching, or primary-key alteration. Column-level: no `JSON` or `VECTOR` types, potential LOB trimming, and no computed columns, `image`/`text`/`ntext`, `XML`, `rowversion`/`timestamp`, `sql_variant`, user-defined/SQL CLR types, or `geometry`/`geography`.

Troubleshooting follows a specific ladder: `sys.dm_change_feed_log_scan_sessions` for incremental progress, `sys.dm_change_feed_errors` for reported errors, `sp_help_change_feed` for configuration state (any state value besides 4 is trouble), then portal-side managed-identity permissions with an `AppId` match, and finally `log_reuse_wait_desc` in `sys.databases` — `REPLICATION` means mirroring is blocking log truncation. Resource governor workload groups can throttle mirroring's impact on the source. The author's verdict: the change-feed mechanism is a positive step, but the feature is young, and many limitations are things he "hopes get addressed over time."
