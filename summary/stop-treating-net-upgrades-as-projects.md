# Stop Treating .NET Upgrades as Projects

A compact polemic: upgrades fail because they're organized as projects — bounded bursts with a beginning, an end, and a large temporary budget — when they should be a permanent engineering capability. With .NET now on a predictable annual rhythm (and .NET 11 RC1 already production-licensed), waiting years to upgrade guarantees the next migration is exceptional, expensive, and risky.

The fix is continuous hygiene: maintain compatibility inventories, characterization tests, automated upgrade recipes, performance baselines, small reversible pull requests, and explicit ownership of exceptions — all the time, not once per rescue mission. AI agents can accelerate this work, but the author insists the larger change is organizational, not technical. The punchline: "The best upgrade project is the one you no longer need to create."
