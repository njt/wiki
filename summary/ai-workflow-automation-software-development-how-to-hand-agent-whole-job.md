Adam Bertram's Telerik essay argues that most teams that claim to have automated AI workflows have only added AI to individual steps of a manual process. His opening example: a dependency upgrade where a bot opens the bump PR, one engineer pastes the changelog into an assistant, another pastes the build failure into a second assistant, and a third applies the fix by hand — four days for a version bump. Both assistants did useful work; neither knew the other existed. "The steps got automated. The workflow did not." Real workflow automation means the human carryover between steps disappears: one trigger, one run, one review at the end.

The piece's sharpest observation is that removing the human carryover removes controls nobody counted. Every handoff was a checkpoint where somebody looked at the work before passing it on, but because those looks were never written down as controls, nobody notices they're gone until something merges that shouldn't have. Hence the prescription: before the first run, write down what counts as finished, what the run may touch, and who approves. A traditional if-then workflow stays; the model goes only into the judgment steps no condition can express — and the fully "agentic" version that picks its own steps carries the reward-hacking risk (give it "make the tests pass" and it may weaken an assertion instead of fixing the code).

Bertram ranks automation targets by how hard the finish line is to define. Low-stakes administrative work around the code (issue triage, labeling, PR summaries) automates first because nothing the automation produced had to be correct. Delivery stages are harder because "a run has to produce something that still works after the workflow closes" — a table maps test maintenance, dependency upgrades, and incident response to the judgment a rule can't cover and to what "finished" must mean (a green suite nobody weakened; an upgrade small enough to have been read; a named person deciding to roll back). Most of a workflow needs no model: "A shell command that breaks will break identically every time, which is the most underrated feature it has."

The operational core is a four-part limit set that must be written into the workflow definition, since "a run cannot set the limits that constrain it": budget (retry/step/token ceilings — unlimited retries teach the agent that changing the test is easier than changing the code), write paths (narrow paths keep diffs small enough to review — "hand somebody 4,000 changed lines, and you'll get an approval, not a review"), commands and credentials (least privilege, citing OWASP prompt-injection guidance and the incident where "your own service account" makes the change at 3 a.m. because a stranger asked it to in a bug report), and approvals (a Microsoft study of 1,535 developers put the median at Level 3 — AI writes, human approves before it takes effect; "worth remembering the next time somebody calls approvals 'friction'"). Each limit needs an owner; NIST's AI RMF is cited for documented AI-risk roles, and most limits can be enforced with controls CI already audits.

On measurement, the argument is delivery over vibes: watch DORA metrics, not how fast the model types. The METR randomized trial (16 experienced open-source developers, 246 real issues, early-2025 tools) made developers 19% slower — time moved into reading and verifying output — and Google's 2025 DORA report paired higher estimated throughput with higher estimated instability, the risk in miniature: "a workflow can produce more than your reviewers can check." The rollout recipe: pick the weekly workflow the team resents, write its finish line in a sentence and its limits on one page with an owner's name beside them, run approval-required for weeks, and only then grant more authority. Choose tooling last, judging products by what they make reviewable rather than by the "AI workflow platform" label — which is where the piece reveals its vendor angle, pitching Progress Forge (formerly Progress Agent Harness), Telerik parent Progress's agent-orchestration product now in early access.
