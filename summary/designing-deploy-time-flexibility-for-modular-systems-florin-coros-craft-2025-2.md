Florin Coros (founder of Co-Design, the company behind the iQuark App Boot library) delivered this Craft 2025 talk in Budapest on escaping the monolith-versus-microservices debate. His thesis: "Microservices or monoliths is not the right question to ask. What I think you all want to build is a modular system." Deployment should be a post-compilation decision — the same binaries run as a modular monolith (plain in-process function calls) or as microservices (REST, gRPC, or a message bus), switched by copying DLLs into a different deployment folder and restarting. No recompile.

Both architectures fail the same way, he argues: bad decomposition, done while thinking about communication and deployment ("will these two things live on the same server?"). A modular system separates that concern and defers it to deploy time. The desirable properties — maintainability, extensibility, reusability — are inseparable, but teams budget only for maintainability because reusability is a hard sell to managers ("what the manager hears is that someone else, another project, will benefit of our work"). Sizing comes from a two-cost graph — cost to build a service versus cost to integrate services — and the architect's whole job is holding the system in the "area of minimum cost": in orders of magnitude, ~10 services (20–25 is fine; 2 or 90 is not).

Three pillars make deploy-time flexibility real: (1) dependencies only through contracts, enforced by structure — contract assemblies contain interfaces, DTOs, and exceptions and "there is forbidden to write any logic"; (2) proxies — every contract is implemented by a proxy that forwards over the wire or in-process, with production systems adding a second set of in-process proxies around real implementations so error semantics stay consistent (a 500 over REST versus a raw IndexOutOfBoundsException in-process) and so logging and telemetry have a home; (3) type discovery — a generic host that configures DI declaratively at startup by scanning assemblies via the open-source App Boot library, instead of imperative registration code that would force the host to reference every implementation.

The talk is grounded in an origin story from ~11 years earlier: a Dutch investment bank spent three years splitting a Delphi monolith (drivers: a shrinking Delphi talent pool and ~14-month release cycles caused by manual end-to-end testing), then discovered 10–15-hop service call chains whose accumulated network latency broke core use cases like placing an order. Coros's proposal to co-locate chatty services in one process at deploy time won the project and inspired the talk. He also covers the surrounding discipline: dependency diagrams generated from code, single-output builds with post-build copy scripts standing in for Dockerfiles, service discovery as "a DNS for production," warm-up and DLL preloading, and trivially serializable contract DTOs. Nothing, he claims, is .NET-specific: "as long as you have interfaces and a little bit of reflection, things can be done" in Java or TypeScript.

The gist's own digest is unusually honest about what the talk leaves out: data and transactions in both deployment modes, the independent-scaling trade-off that co-location gives up, any benchmark for a latency-motivated design, the unproven generic host, fault serialization between REST errors and exceptions, the maintenance cost of the mechanism itself, security, tracing, testing, and any epilogue on whether the bank actually got fixed. His framing of history — monolith to microservices ~15 years ago, back to modular monoliths ~5 years ago — lands on the diagnosis that "we are moving in this circle mainly because we don't ask the correct question."
