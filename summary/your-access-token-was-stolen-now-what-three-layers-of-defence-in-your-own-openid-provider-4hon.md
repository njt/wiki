An engineering writeup of redb.Identity, the author's Apache-2.0 OAuth 2.1 / OpenID Connect provider on .NET, organised around one question: what happens when an access token is stolen? An access token is a bearer token — whoever holds it is you — and theft comes through four vectors that share one property (own-code XSS, a compromised npm dependency, browser extensions, localStorage): the attacker walks away with the token itself and needs nothing else. The answer is three layers: don't let it be stolen, make the stolen thing worthless, kill it fast.

**Layer one — the BFF.** Mature identity servers (Keycloak, WSO2) ship their admin consoles as public OAuth SPAs, leaving an administrator token in page memory any script can read. redb.Identity.Web instead runs as a Blazor Server back-end-for-frontend: the OIDC exchange happens server-to-server, tokens live on the authentication ticket, and the browser holds only an HttpOnly, SameSite=Lax, Secure session cookie. The honest trade-off table: BFF wins four of five rows (attacker location, duration, tab-close survival, replayability) but loses the fifth — detectability. Activity inside the victim's browser arrives from the victim's own IP and user-agent during their working hours, indistinguishable from the person, and the author admits they have no anomaly detection yet. Taking a cookie also re-shapes rather than removes risk: token theft becomes CSRF, so SameSite flags and antiforgery tokens on all twelve state-changing forms are both required. Mobile clients get the different combination of RFC 8252 system-browser auth, PKCE, OS key stores, and DPoP.

**Layer two — DPoP (RFC 9449).** Stop issuing bearer tokens: the client generates a key pair, the token is stamped with the key thumbprint (`cnf.jkt` per RFC 7638/7800), and every request carries a short signed proof bound to method and URL. Stolen token without the private key is a useless string. Implementation details: HMAC-signed stateless DPoP-nonces, a store of consumed `jti` values, asymmetric algorithms only — and crucially a separate validator package so resource APIs check proofs themselves, not just the provider.

**Layer three — kill it fast.** Idempotent RFC 7009 revocation, refresh-token rotation with reuse detection, session idle timeout. The standout piece: classic OIDC backchannel logout is push and fails at the first network partition or crashed replica, so alongside it runs a pull feed of revoked session IDs with a cursor — applications catch up on what was revoked while they were away, and the BFF checks the same list on every request, so "sign out everywhere" kills live UI sessions across every replica.

The hygiene layer beneath (password history, TOTP replay protection under a lock, constant-time comparisons in sixteen files, three-level rate limiting, X-Forwarded-For sanitisation ordering, SSRF guards on `jwks_uri`/`request_uri` fetches, refusal of `alg:none`) culminates in the external arbiter: the server was run through the official OpenID Foundation conformance suite, which found a real PII leak their own tests missed — scope-derived claims landing in the id_token that gets forwarded to third parties and logs. No OpenID Certified™ claim is made; only the suite results.

Finally the worst case — a stolen database. What encryption buys: Argon2id passwords (64 MiB; 24 GB of video memory holds ~380 parallel cracking lanes instead of bcrypt's tens of thousands) with legacy bcrypt hashes migrated by upgrade-on-login; recovery codes hashed with a pepper that lives outside the database entirely; signing keys encrypted under DataProtection; and the key ring encrypted at rest, with a fail-to-start condition in production. What it doesn't buy: a dump still yields PII, org structure, session metadata and the full audit trail — a reportable personal-data breach with zero passwords cracked. And if the backup ships with the configuration holding the root key, the protection collapses to zero. Takeaway checks for your own server: what hashes your passwords and whether upgrade-on-login exists, and where the key that encrypts your signing keys lives — if it's in the same database, the encryption is decorative.
