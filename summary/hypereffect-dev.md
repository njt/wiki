hypereffect is a small protocol for describing server-guided, reactive interfaces that any renderer can draw. A client ("renderer") sends `hello`; the server answers with **signals** (state) and **elements** (UI drawn from a fixed set of eighteen components carrying semantic variants like `h2`, `warning`, `primary` — never styles). Element attributes, including text and visibility, can be side-effect-free expressions (CEL-like) evaluated on the client, so a signal update re-renders without the server re-sending the interface. Handlers can do only two things: patch local state (signals prefixed `_` stay client-side) or fire a named **action** sent to the server with the current signals; the server then decides what new elements, removals, or signal updates follow.

The pitch is hypermedia redux: the server describes the UI and drives application state; buttons and inputs are *hypermedia controls*; the client never parses domain objects, only renders what it is told. Transport is unspecified — stdin/stdout, Unix sockets, serial lines, SSE+POST, iroh, even in-process WASM all work. Because there are no scripts and expressions have no side effects, the protocol claims to be "inherently safe": a renderer trusts a server for content, never for execution. Accessibility falls out of the design since messages carry meaning, not pixels.

Stated ambitions: "the world's second most successful hypermedia system, after HTML" — the shared interface layer for devices, sandboxed WASM modules, hardware control panels, simple services outside the browser duopoly, and notably **interfaces generated by LLM agents on the fly as plain JSON with no code to run**. The non-use cases are honest: no standalone apps, no dense or visually interactive UIs, no tools people live in all day.
