JetBrains' field diary on building Context, their semantic code search platform: a RAG pipeline that gives coding agents "precise, citable evidence from real repositories instead of whatever grep happens to surface." This first part of a series covers the pipeline head — parsing, chunking, and vectorization. The framing: the question is no longer whether an agent can finish a task (given enough tokens it will), but how much time and steering it burns searching for the right code. Keyword search requires knowing the text in advance — an agent hunting for where session tokens get refreshed cannot count on the code containing the word "refresh."

Chunking gets the full engineering treatment. Fixed-size splits group unrelated code; embedding whole files returns whole files. JetBrains instead leans on its 26-year parser heritage (the internal Code Engine platform) for structure-aware chunking in nine languages — Kotlin, Java, Python, JavaScript, TypeScript, C#, PHP, Go, Rust — with naive line-splitting fallback elsewhere. The algorithm resembles cAST (Zhang et al. 2025) — keep the largest syntax units that fit, subdivide oversized ones, merge tiny adjacent ones — but bakes in more language semantics: decorators stay with definitions, KDocs stay with Kotlin declarations, doc comments and modifiers stay glued to their declarations, and semantically empty annotations like `@NotNull` are scrubbed. Chunk quality is evaluated by an LLM-as-a-judge that checks whether boundaries make sense (detached documentation, orphaned closing syntax), plus end-to-end retrieval evaluation.

The vectorization section is a storage-economics argument. Millions of chunks at 16 KB per float32 vector add up to tens of gigabytes, so the question becomes "what do we get per byte?" Two independent levers — fewer dimensions or fewer bytes per dimension — and the trade-off is lopsided: a 512-byte budget spent on 128 dimensions at full precision retrieves considerably worse than the same budget on all 4,096 dimensions at 1 bit each. Their metaphor: dimensions are questions the model learned to ask about text; "a long questionnaire filled in with checkmarks beats a short one filled in to six decimal places." So they quantize to sign bits (32× smaller), switch cosine similarity to Hamming distance (XOR + popcount, ~100 instructions vs thousands of multiplies), and accept a few points of recall loss because the consumer is an agent that opens and reads candidates anyway — rank 2 vs rank 5 is invisible in that loop.

The subtler cost gets its own section: binary quantization compresses the *range* of similarity scores. Unrelated vectors agree on about half their bits by pure chance, so every score lands in a thin band — ranking survives, thresholding doesn't. Proactive features ("suggest related code while you type") need a usable gap between related and unrelated, so those indexes keep 16-bit floats. Serving details: separate models for indexing (throughput; the GPU saturates around 32 chunks per batch) versus search (time-to-first-result); an instruction-following asymmetric embedding where queries are wrapped with a task instruction and documents are embedded as-is; file paths embedded alongside chunks but truncated with a "both ends survive" rule (the IntelliJ monorepo has a median path of 91 characters at nine directories deep); and directory scoping rendered into the query text itself, in exactly the abbreviated form the chunks were indexed under, rather than as a post-hoc metadata filter.

The privacy posture is a design decision, not a policy: nothing is stored server-side but coordinates — path, offsets, vector reference — and the snippet you see is assembled on your machine from your checkout. Embeddings run on an open-weight model on JetBrains' own GPUs, so no code embedding request leaves their infrastructure. They report their open-weight candidates beat the major hosted embedding APIs on their internal benchmarks, concluding that "the interesting engineering has moved into what you feed them, how you serve them, and what you choose to keep." Later parts of the series promise storage, millisecond query serving, continuous evaluation, and agent integration.
