# OpenArm

OpenArm is Enactic's open-source 7DOF humanoid arm platform for physical-AI research — $6,500 for a complete bimanual system, with CAD under CERN-OHL-S and all software under Apache-2.0 — but the arm is almost the least interesting part. What the project actually ships is an end-to-end loop for embodied-AI data work: three teleoperation modalities (bilateral force feedback, VR, and a motorless wearable leader arm), an open dataset format that converts to LeRobot, ACT-policy training via LeRobot, a model-agnostic policy-server contract for inference, and a standardized physical evaluation cell. The repo ingested here is the project's documentation monorepo (a Docusaurus site with versioned 1.0/2.0 docs), and its docs are the technical map of a nine-repo ecosystem: openarm_hardware, openarm_description, openarm_can, openarm_ros2, openarm_teleop, openarm_isaac_lab, openarm_mujoco, openarm_dataset, and dora-openarm.

## Architecture

**The repo itself is documentation-as-product.** `website/` is Docusaurus 3.10 with MDX docs, KaTeX, mermaid, and a `versioned_docs/version-1.0` snapshot managed by Docusaurus versioning; CI (`website.yaml`, `lint.yaml`, `preview-comment.yaml`) builds and previews it. There is no robot code here — the docs specify the interfaces of the sibling repos.

**Hardware layer.** Each arm has 7 joints plus a parallel gripper with an in-hand camera; a bimanual pair is a 16-DOF action space (`right_arm[7] + right_gripper[1] + left_arm[7] + left_gripper[1]`). Motors are Damiao BLDCs selected per joint from a documented spec table (`website/docs/hardware/openarm-2.0/motor.mdx`): DM-J4310-2EC (10:1, 7 Nm peak) distal, DM4340 (40:1, 27 Nm) mid-arm, DM-J8009P (9:1, 40 Nm, 50 A peak) shoulder — all 24 V, dual 14-bit magnetic encoders, CAN-controlled, MIT-mode. The frame is MISUMI extrusion with mechanical range-of-motion limits on every axis.

**Low-level control (`openarm_can`, C++).** A three-layer stack documented in `website/docs/api-reference/can/can.mdx`: `canbus` (CANSocket over Linux SocketCAN, generic CANDevice/CANDeviceCollection) → `damiao_motor` (DMCANDevice, Motor, DMDeviceCollection) → `can/socket` (OpenArm orchestrator, ArmComponent, GripperComponent). All control is Damiao MIT mode — `MITParam{kp, kd, q, dq, tau}` mixing position, velocity, and torque in one frame. Each motor has a send ID and a distinct receive ID (0x01 ↔ 0x11 pattern), and a `CallbackMode` enum (STATE / PARAM / IGNORE) multiplexes what incoming frames mean — request/response semantics over a broadcast bus. The loop is polling: `recv_all(timeout_us)` with tuned timeouts (100–2000 µs; 300–500 µs for fast control, 2 ms for enable/query), giving a practical ceiling of ~1000 Hz on an 8-motor CAN-FD bus (1 Mbps nominal / 5 Mbps data, up to 10 Mbps).

**Middleware.** Two coexisting stacks: ROS2 (`openarm_ros2`) exposes the arm through a ros2_control hardware interface with mock-hardware support, joint_trajectory/forward_position controllers, and an in-progress MoveIt2 integration; Dora dataflow nodes (`dora-openarm*`) serve the AI data-collection and inference loops. The docs honestly flag the ROS2 hardware bridge as unstable and gripper bridging as under active development.

**Data (`openarm_dataset`).** Episodes are directories, not containers: `episodes/<n>/action/arms/{left,right}/qpos.parquet`, `obs/.../state.parquet` (qpos/qvel/qtorque), a `lifter/elevation.parquet`, and cameras as individually timestamped JPEG files (`cameras/ceiling/1778841171518984960.jpeg` — nanosecond filenames). A `metadata.yaml` records task prompts and per-episode success flags. The Python API loads everything as timestamp-indexed pandas DataFrames, and `dataset.sample(hz=30)` re-aligns asynchronously captured streams onto a fixed grid — capture is deliberately asynchronous; synchronization happens at load.

**Inference (Dora dataflow, `website/docs/tutorial/inference.mdx`).** A 250 Hz dora timer ticks a gate chain → `observer` (JPEG→RGB decode, arm concat, Arrow StructArray) → `policy-server` (writes the observation bundle as Arrow IPC to `/dev/shm`, sends a JSON request line over a Unix socket) → model process (local or Docker) → `actions-executor`. The executor Hermite-upsamples the policy's 30 Hz chunk to 250 Hz and applies a 15 Hz Biquad low-pass filter before touching the arm.

**Simulation.** MuJoCo MJCFs (torque actuators, visual/collision geom groups 2/3, convex-hull collision) and Isaac Lab environments (Isaac Sim 5.1 / Isaac Lab 2.3) with RL tasks (reaching, cube lifting, drawer opening). The published example dataset and trained model (`openarm-2-cell-pick_up_cube_mujoco`) were collected *in MuJoCo*, and the MuJoCo node and hardware node are interchangeable in the inference dataflow.

**Evaluation (`OpenArm Cell`).** A ~100 kg / 480 W MISUMI enclosure standardizing background, lighting, camera placement, and arm mounting, with an area-sensor reach-in power cut and a zero-position calibration jig that physically constrains the gripper to CAD-defined angles before data collection.

## Key techniques

- **Bilateral force feedback without force sensors.** The motors' backdrivability turns the leader arm itself into the sensor: the operator feels what the follower contacts. The enabling trick is friction compensation with a tanh model (`tau_f = Fc·tanh(k·dq) + Fv·dq + Fo` — Coulomb knee, viscous term, offset bias) in `openarm_teleop`'s `Control` class, run across three threads (leader, follower, admin) at ≥500 Hz. Without the tanh, static friction would quantize the felt force; with it, contact transmits cleanly.
- **The policy server contract.** Inference is defined by a one-page protocol: JSON request line with a `/dev/shm/*.arrow` path plus camera metadata; JSON response `{interval_ns, cutoff_hz, positions: N×16}`. Notably the *policy* specifies its own step interval and low-pass cutoff per response — the executor's smoothing is policy-tunable, so a jerky VLA can ask for more filtering and a precise one for less. Swapping ACT for any other model means implementing one socket handler.
- **Rate-mismatch machinery as a first-class concern.** 30 Hz policy, 250 Hz execution: Hermite interpolation (position- and slope-continuous) rather than linear interpolation, then a Biquad LPF. Most hobby teleop/data stacks ship action chunks raw; this is where sim-trained policies survive contact with hardware, and it's engineered, not incidental.
- **Arrow IPC on shared memory instead of sockets for observations.** Five 600×960 RGB streams per tick don't fit a JSON socket; the observer node writes zero-copy Arrow to `/dev/shm` and the socket carries only a path and metadata. The same shape as modern LLM serving stacks (tensor sidecar + control channel).
- **KER: subtract hardware from the teleop problem.** The Kinematic Equivalent Replica deletes the leader's motors entirely — magnetic encoders, CFRP pipes, 1.7 kg, worn as a 30-second backpack mount, linked at 70% scale but kinematically identical so joint angles map 1:1 with no retargeting. It streams 16 encoder angles over USB (M5Stack, vendor ID 303a) with per-encoder error flags. The bet: operator fatigue, not leader stiffness, is the binding constraint on long data-collection sessions.
- **Benchmark integrity as hardware.** The Cell's calibration jig mechanically removes assembly tolerance from every dataset recorded anywhere in the world — a data-quality guarantee with no software-benchmark equivalent. The reach-in stop and documented "backdrivable loads fall when e-stopped" warnings show safety treated as an engineering property, not a disclaimer.

## Design decisions

- **Compliance over stiffness, and the cost is stated out loud.** QDD backdrivable motors buy safe human-robot contact and bilateral control; the price is that an e-stopped arm drops its load, which the safety guide documents as a hazard rather than hiding. One non-backdrivable motor (DM4340) is deliberately mixed in where payload demands it.
- **Openness as distribution strategy.** Every part purchasable and buildable (CNC, 3D prints, wiring, BOMs on Google Drive), verified third-party manufacturers, and per-repo licenses split between hardware (CERN-OHL-S) and code (Apache-2.0). The trade-off is a fragmented experience: nine repos, a ROS2/Dora middleware split, and docs that warn about flash-write limits (~10,000 cycles on motor parameter saves) and baudrate-mismatch bootstrapping (the `discover` command must scan to find a motor's baudrate before you can talk to it).
- **Documentation is the deliverable in this repo.** Keeping the docs as the hub — with versioned snapshots for hardware generations — is honest for a fast-moving multi-repo ecosystem, but it concentrates risk: the docs assert interfaces that live elsewhere, and the ROS2 paths they flag as unstable may drift from reality between doc releases.
- **Standardization over flexibility.** The Cell's value is that nothing in it varies — which also means 100 kg of fixed infrastructure per evaluation station. The project bets that reproducible negative results are worth more than cheap ad-hoc experiments.

## Comparison notes

- [[World Models — Promise and Limits (Ars)]] reports Sitzmann's field consensus that "teleoperation won't get us there" on robot training data and world models are the proposed fix. OpenArm is a bet on the other side of that tension: instead of synthesizing data, it slashes the cost and fatigue of human data collection (KER, VR, $6,500 bimanual) and standardizes evaluation — while quietly hedging, since its example dataset and demos are collected *in MuJoCo*, one step toward the world-model direction anyway.
- [[Goldman Sachs World Model]] describes physical world models as "robots practice millions of digital failures before touching reality." OpenArm instantiates that loop concretely: the same MJCF assets and policy-server contract serve MuJoCo data collection, training, and deployment, so sim-to-real is a node swap in a Dora YAML rather than a porting project.
- [[Benchmark Exploitation]] catalogues how software agent benchmarks fail — evaluator isolation, answer-key exposure, judge manipulation. The Cell is the physical analogue's defense: calibration jigs and fixed lighting make tampering and drift visible. But it doesn't escape the deeper failure mode that paper identifies — a single standardized cell is one giant answer key, and policies overfit to it exactly the way agents overfit to SWE-bench.
- [[Four Time Scales for Technology Development and Deployment]] — Rodney Brooks argues robotics deployment runs on a 20+ year clock and that conflating research demos with deployment produces outrageous predictions. OpenArm is unusually disciplined about this: it positions itself as reproducibility infrastructure for research, not as a labor-replacement product, which is the correct time-scale posture even as its price quietly attacks the hardware-cost barrier Brooks identifies.
