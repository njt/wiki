# OpenDisplay

OpenDisplay is a free, open-source (GPL-3.0) replacement for Apple Sidecar/Duet Display/Luna Display: it turns a spare iPhone, iPad, or old Mac into a *true extended* second monitor for a Mac — a new desktop space macOS treats as a real display, not a mirror — over a USB cable or WiFi, with touch, scroll, and Apple Pencil input flowing back. It matters as a small-systems design study: ~10,700 lines of Swift across three tiny apps, one direct TCP connection, no accounts or servers, and a level of wire-protocol and field-hardening discipline (a normative spec, a compatibility policy, issue-annotated race fixes) that most "vibe-coded" repos never reach.

## Architecture

Three targets generated by `project.yml` (xcodegen), sharing one `Shared/` code base. The only runtime dependency is Sparkle, for the Mac apps' out-of-store auto-update:

- **Sender** — `OpenSidecarMac` (macOS 14+): `Mac/MacSender.swift` (2,286 lines) owns the session. Pipeline: **private-API virtual display** (`Mac/VirtualDisplay.swift` + the reverse-engineered `Mac/CGVirtualDisplayPrivate.h`, originally from Khaos Tian's VirtualDisplayExp and the same interface DeskPad/BetterDisplay use) → **ScreenCaptureKit** capture → **VideoToolbox H.264** encode → `[4-byte BE length][Annex B payload]` frames over `NWConnection`.
- **Receiver** — `OpenSidecariOS` (iOS 16.4+) and `OpenSidecarMacReceiver` (macOS 12+, a spare Mac as display): `Shared/StreamReceiver.swift` (1,372 lines) listens on TCP :9000, advertises via Bonjour (`_opensidecar._tcp` — the project's original name was OpenSidecar), deframes, and feeds `AVSampleBufferDisplayLayer` (with an experimental `VTDecompressionSession` + `iOS/MetalVideoRenderer.swift` path behind a toggle, kept off because the system layer wins on iOS).
- **Input** — touches in `iOS/OpenSidecarPhoneApp.swift`'s `VideoLayerView` become JSON control messages; `Mac/InputInjector.swift` turns them into `CGEvent` mouse events and synthetic tablet events for Pencil.

The load-bearing decision (PROTOCOL.md §1): **the receiver listens, the sender connects.** One code path serves both transports — over WiFi the sender dials the Bonjour address; over USB, `Mac/Usbmux.swift` is a *native client for macOS's built-in `usbmuxd` daemon*, speaking the plist protocol on `/var/run/usbmuxd` (ListDevices / Listen / Connect) so that after a Connect-OK the socket becomes a transparent byte pipe. That drops the usual external `iproxy`/libimobiledevice dependency entirely. It also means no UDP exists through the cable — which shaped the cursor side channel below.

## Key techniques

- **Two-stage backpressure** (`MacSender`): `pendingEncodes` capped at 1 (skip capture while a hardware encode is in flight) and `pendingSends` capped at 3 (frames not yet TCP-ACKed), both under one `pipelineLock`. Frames are dropped *pre-encode*, so the H.264 reference chain stays valid — a skip is just P-frame n→n+2 — and no keyframe is forced on drops (that caused "IDR pulsing"). A debounced 30ms replay timer re-encodes `lastPixelBuffer` once the pipeline clears, and the watchdog replays the last frame as an IDR after a reconnect on a static screen (ScreenCaptureKit only emits on content change, so a reconnect would otherwise stay black).
- **Local cursor echo**: the cursor is hidden from capture (`showsCursor = false`) and its position polled at 120Hz (deduped at 0.0004 normalized movement) over the control channel — a ~2ms path instead of ~30ms of video latency. The sprite is hashed from its TIFF representation at 30Hz and PNG-encoded only on change, capped under 24 KB *because of the demux limit* (below). Over WiFi, positions move to a **UDP side channel** (port+1 = 9001) with a per-session sequence number `s`; the receiver drops anything not newer, `cursorAck` confirms real delivery (UDP `.ready` proves only a local route — a firewalled port would eat the cursor silently), and the sender mirrors onto TCP until the ack arrives.
- **Heuristic channel demux** (PROTOCOL.md §4): sender→receiver frames share one TCP socket. A frame is JSON iff length < 32,768 ∧ first byte `{` ∧ no NUL byte — Annex B start codes (`00 00 00 01`) guarantee NULs in every video frame, even one prefixed with a `{`-shaped telemetry header. The spec is honest: this is "design debt, not a feature," normatively constrained so it can't misfire, and slated for a typed frame header in protocol 4.
- **NTP-style clock sync**: `ping(t)`/`pong(t, mt)`; offset = mt − (t1+t2)/2, taken from the minimum-RTT sample of the last 15. Every video frame carries a `{"cap":…,"snd":…}` telemetry prefix before its first start code, so the receiver displays *measured* end-to-end and photon latency — and stamps `touch.t` in the sender's clock so the Mac measures input latency with no sync of its own.
- **Display identity survival kit** (`Mac/VirtualDisplay.swift`, `Mac/DisplayArrangement.swift`): macOS keys saved arrangement and saved display state on vendor/product/serial, and restores it asynchronously, seconds after creation. So: stable per-device serials so each phone keeps its arrangement; a 2s enforcement loop that re-asserts the @2x HiDPI mode and re-breaks mirror sets (session-scope config, because `permanent` mirror changes on a private display are silently rejected); and a **poisoned-identity escape** — when saved state makes an identity never come online (#206), the sender bumps serial *and* productID and persists the offset so the device skips its dead identities forever. Rotation is a re-`hello` that applies a new mode to the *same* virtual monitor (both axes reserved for the longer orientation at creation) instead of destroy+create, so WindowServer never redistributes the windows. User drags are persisted by install ID, not serial, with side-preserving rotation geometry — the one part of the system with real unit tests (`MacTests/DisplayArrangementTests.swift`).
- **Connection forensics** everywhere: `dialGeneration`/`captureGeneration` guard async races (a stale USB dial must not adopt; a late encoder callback must not leak a retired display's frame onto a new socket); a newcomer TCP connection must *prove itself with bytes* before it can evict a live session (Bonjour's IPv4/IPv6 double-dial otherwise caused reset storms); three consecutive refused dials or a withdrawn Bonjour service end the session faster than the 10s grace; and losing a *direct cable* link (wired + link-local peer + Mac receiver) is treated as the user pulling the plug — deliberate disconnect, no WiFi fallback — while every other death keeps redialing. Throttled log policies stop a 240 msg/s pencil stroke from flooding the log.

## Design decisions

- **TCP, not UDP/RTP/WebRTC, for video.** Reliability and ordering come free, the usbmuxd tunnel carries it, and "latency" is handled by *dropping frames before they enter the pipeline* rather than by congestion control. Head-of-line blocking was accepted for video (a late frame should be dropped anyway) and escaped only where it was actually visible — the cursor. The cost: WiFi bandwidth jitter becomes latency, and there's no encryption at protocol v3 (pairing-code encryption is roadmap #16).
- **H.264, not HEVC/AV1**: universal hardware encode/decode, no B-frames, `MaxKeyFrameInterval` 3600 — periodic IDRs are bitrate spikes, so keyframes happen only on demand (`kf`, reconnect, SPS/PPS change on rotation). HEVC is a planned option, not a requirement.
- **Private API, knowingly**: `CGVirtualDisplay` is why the Mac app can't be on the App Store and "possibly breaks on a macOS update" — the same risk every virtual-display product carries. The capture/streaming pipeline itself is public API only.
- **A real protocol spec as a product feature**: `PROTOCOL.md` (normative, RFC 2119) plus `COMPATIBILITY.md` (the evolution policy) exist so third-party clients — Android receivers, an iOS 12 client, a Linux Wayland sender — could interoperate from the spec instead of reverse-engineering. The versioning model is textbook: `pv` bumped only when the wire changes, absent = 1, additive fields free, breaking changes two-phase (ship both, saturate, raise the floor), and a remote-config force lever on iOS that fails open.
- **On the "vibe-coded and likely loose" caveat — what I actually found**: the code is far more disciplined than that framing suggests. Issue-numbered comments document *why* (e.g. `#75` bans self-rescheduling asyncAfter chains; `#142` explains comparing against `== 1` not `!= 0`), log noise is throttled by policy, CI builds and tests PRs including forks, and the geometry that's easiest to regress is tested. The genuine looseness is where the authors admit it: the demux heuristic itself, JSON built by string interpolation (`sendJSONFrame`, `sendCursor`), several receive/error paths that silently `return`, and zero tests over the streaming core — the test target covers display-arrangement geometry and log policies, nothing else. The 2,286-line `MacSender` is one class doing dialing, capture, encode, cursors, upgrades, and telemetry; it works, but it's the file a refactor would split first.

## Comparison notes

- [[RustDesk]] is the closest neighbour in the wiki: both self-hosted screen streaming with native apps. The difference is scope: RustDesk is *remote* desktop — internet, NAT traversal, relay servers, end-to-end encryption — while OpenDisplay is *local* display extension (a fresh desktop space, not a remote view of one) over a cable or LAN, with no rendezvous infrastructure at all. OpenDisplay's current lack of WiFi encryption is the gap RustDesk's threat model already solved.
- [[WebRTC Is the Problem]] argues WebRTC's complexity, packet-dropping and head-of-line blocking make it the wrong transport for real-time audio; OpenDisplay is the same conclusion reached independently for video — plain TCP with app-level frame dropping. But it also *nuances* that essay's counterintuitive defence of head-of-line blocking: OpenDisplay found exactly one place where HOL blocking visibly hurt (the cursor stuttering behind multi-hundred-KB video frames) and fixed it surgically with a UDP side channel, rather than either accepting it everywhere or adopting an RTP stack for everything.
- [[Castor]] shares the "decouple stages so one slow stage can't kill the rest" instinct — Castor's read-once spool separates CDN fetch from playback so token expiry can't kill a cast; OpenDisplay bounds in-flight work (one encode, three sends) and drops-and-replays instead of queueing unbounded latency. Both treat bounded queues as the cheap insurance of a one-way pipeline.
- [[The Observability Pain Cycle]] describes teams discovering too late that they can't diagnose their own system; OpenDisplay is the counter-example — measurement was built in from day one, with a perf overlay showing percentiles (e2e, encode, decode, photon, input) on both ends, per-frame telemetry on the wire, and the receiver's stats logged into the *sender's* log file (`PHONE-STATS`) so one log tells both ends' story.
