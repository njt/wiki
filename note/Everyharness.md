# Everyharness

everyharness is a ~5,000-line TypeScript CLI (prime-radiant-inc, v1.0.0, MIT) that compiles one `everyharness.yaml` config into native plugin artifacts for twelve coding-agent harnesses — Claude Code, Codex, Gemini CLI, Cursor, Copilot CLI, OpenCode, Pi, Kimi Code, Hermes, Devin CLI, Factory Droid, and Grok Build CLI — through eleven adapters, then keeps the generated output honest with sha256 drift detection, container-backed real-install checks, and single-source version bumping. It was extracted from the superpowers plugin, which had drifted into nine hand-maintained manifests and four divergent bootstrap mechanisms. Its significance for the wiki is what it documents about the harness ecosystem itself: the plugin format fragmentation is now bad enough that someone built a compiler for it, and the compiler's comments double as a dated, empirically-verified field survey of how each harness actually loads plugins.

## Architecture

The shape is a classic compiler pass pipeline, with file generation as the back end:

1. **Config load** (`src/config.ts`) — `everyharness.yaml` is parsed with the `yaml` package, screened for four legacy-v1 syntaxes with pointed migration errors (`rejectLegacySyntax`), then validated with zod. Component paths are restricted to `[A-Za-z0-9._-]+` segments with an explicit `.`/`..` rejection, because these strings get substituted verbatim into emitted Python/JS/TS — the charset regex is a shell-metacharacter firewall. Per-harness keys are validated against a duplicated adapter-name registry (`ADAPTER_NAMES`) so a typo like `claudecode:` is a `ConfigError` instead of a silently ignored block.
2. **Model build** (`src/model.ts`) — `buildModel()` reads the plugin's actual source components into a normalized `PluginModel`: skills (directories with `SKILL.md`, frontmatter parsed), commands and agents (markdown with frontmatter), hooks and MCP configs (JSON, must be plain objects). Frontmatter parse errors are re-thrown with the source file path attached — a small touch that turns a needle-in-haystack YAML error into a one-line fix.
3. **Adapter emission** (`src/adapters/*.ts`) — each of the 11 adapters implements `HarnessAdapter { name, support: ComponentSupport, emit(model): EmitResult, installDoc?(model) }` where `ComponentSupport` is a static per-component (`skills/commands/agents/hooks/mcp/bootstrap`) full/partial/none matrix. `emit()` returns a `FileSet` of `{path, content, executable?}`.
4. **Merge with collision rules** (`src/generate.ts` `mergeFiles`) — adapters cannot clobber source paths (skills/, commands/, agents/, hooks, .mcp.json are `isSourcePath`-protected); byte-identical cross-adapter collisions dedupe silently; differing-content collisions are a `ConfigError`.
5. **Manifest-tracked write** (`src/fileset.ts`, `src/manifest.ts`) — paths are checked as relative and inside the plugin root, files are written, and `.everyharness/manifest.json` records `{path → sha256, executable}` for every generated file, stamped `schema: 1` and the tool version.
6. **Prune and conflict-refuse** — before writing, `generate()` consults the prior manifest: previously-generated files that this run no longer emits are deleted (with empty parent directory cleanup) *only if* unmodified on disk; a hand-edited stale file is kept with a warning pointing at everyharness.yaml. Files that exist but were never generated are refused unless byte-identical or `--force`, with a special note when the file is `package.json` (which the opencode/pi adapters emit as a full replacement — no merging, so `--force` there means "lose your package.json").
7. **Docs stage** (`src/docs-emit.ts`) — per-adapter install docs (`docs/install/<harness>.md`) and `docs/support-matrix.md` go through the same merge/manifest machinery, then a README injection between hand-placed `<!-- everyharness:install:start/end -->` markers runs outside the FileSet path because README.md is a user file.

On top of the pipeline sit four operational commands: `validate` (config load + drift check + vendored JSON-Schema validation with exit 1 config error / 2 schema / 3 drift), `test` (`src/test-command.ts` shells out to `docker run` with the plugin mounted read-only), `bump` (`src/bump.ts`), and `init`/`import` (`src/init.ts`, `src/import.ts` — the latter converting a Claude-format plugin.json into everyharness.yaml, extracting inline `hooks`/`mcpServers` payloads to their default component files).

## Key techniques

- **The generation manifest as the load-bearing artifact.** `.everyharness/manifest.json` is what makes committed generated files tractable: drift detection (`checkDrift` compares sha256 and the exec bit), stale-file pruning, and the clobber-refusal check all hang off it. Corruption handling is asymmetric by design: `validate` fails loudly on a corrupt manifest, but `generate` recovers by treating it as absent and skipping pruning — regeneration is the recovery path, and a warning says so.
- **Null-as-delete-sentinel deep merge** (`src/fileset.ts` `deepMerge`). Per-harness manifest patches deep-merge into the generated manifest, and a literal `null` at any depth deletes the inherited field — essential because kimi's plugin.json format has no `repository` while claude-code's requires it. The cost: a literal null value can never be *set* through a patch (arrays are opaque and replace wholesale, so nulls inside arrays survive). A whole merging semantic was traded away to make field deletion expressible.
- **Bootstrap as a compiled abstraction** (`src/bootstrap/*`). One tagged config value compiles to wildly different machinery per harness: claude-code/cursor/muse get a SessionStart shell hook plus `run-hook.cmd`, a bash/cmd *polyglot* wrapper (the file begins with a `: << 'CMDBLOCK'` heredoc so cmd.exe and bash both parse it) that finds Git-bash on Windows; OpenCode gets a JS plugin module with a module-level tri-state bootstrap cache and a marker-guarded injection into the first user message; Pi gets a TypeScript extension that arms a flag on `session_start`/`session_compact`, disarms on `agent_end`, and splices the bootstrap message after any leading `compactionSummary` messages rather than at index 0; Hermes gets a Python module registering skills via `ctx.register_skill(name, Path(...))` and injecting through `pre_llm_call` — the only documented injection path, since `on_session_start` return values are ignored; Gemini gets a `GEMINI.md` using the `@`-import syntax; Kimi gets a `sessionStart.skill` manifest field; Codex and Devin get nothing active. In `generate` mode a synthetic `hooks/everyharness/bootstrap.md` (one line per skill: when to invoke it) is the shared injection payload.
- **Empirical ground truth as dated code comments.** The adapters record verified harness behavior with dates and versions: Claude Code reads hooks from *both* hooks files but dedupes exact-duplicate `{matcher, command}` entries at execution time (verified 2026-08-11 against Claude Code 2.1.217 — so merging user hooks into the generated file does not double-fire); Copilot CLI 1.0.78 reads *only* Claude's marketplace descriptor and never looks at `.agents/plugins/`; droid names marketplaces by repo basename, not descriptor name; Hermes' `register_skill` with a plain string raises AttributeError and silently disables the whole plugin (verified 2026-07-23). The Hermes module even *fails loudly* on a missing skills dir — "a bootstrap that silently skips is how a broken install masquerades as a working one."
- **Deliberate dedupe-by-construction.** The opencode and pi adapters both want a root `package.json`; `node-packageManifest` emits *both* the `main` (OpenCode) and `pi` (Pi) fields unconditionally regardless of which adapter is active, guaranteeing byte-identical output so `mergeFiles` collapses them instead of raising a conflict. A dangling field is harmless; a merge conflict between your own adapters is not.
- **Two-tier offline install verification** (`checks/run-checks.sh`). Tier 1 parses every generated manifest and checks referenced paths exist. Tier 2 does a *real install* of the plugin into each harness CLI present in the shared container image (claude, codex, gemini, opencode, grok, droid, hermes, copilot, pi) and asserts the CLI actually enumerates the plugin's skills — the check that catches "manifest parses but is wired to the wrong place." Harnesses with no offline enumeration path (kimi, cursor, devin) report `skip`. The checks script exits 3 on failure specifically so `test-command.ts` can distinguish a real check failure from docker's own generic exit 1 (daemon down, no socket perms).
- **Semantic dogfooding** (`tests/dogfood.test.ts`). The north-star test regenerates eight of superpowers' hand-maintained manifests from one config and compares parsed JSON with `toEqual` — key order and formatting explicitly not goals (a recorded ruling). It reads the live `dev` branch via `git archive` rather than a pinned SHA: it's a tripwire against superpowers and everyharness drifting apart, not a snapshot regression test.

## Design decisions

- **Commit generated files; detect drift, don't rebuild.** The obvious alternative is "run the generator in CI before release." everyharness instead commits all generated output and makes `validate` a CI gate. The trade: repos stay installable from git by users who never installed the tool, at the cost of drift-detection machinery (the manifest) that wouldn't otherwise exist. The dogfood test keeps the generator honest against the real-world repo it was extracted from.
- **Claude's format is the interchange hub.** `import` converts *Claude-format* plugins in; the agents-marketplace adapter exists because Copilot, Droid, and Grok all end up installing the claude-code-style layout through descriptor files. Rather than inventing a neutral IR, everyharness treats Claude Code's plugin model (skills/commands/agents/hooks/mcp + marketplace.json) as the de-facto standard and patches per-harness deltas on top — an acknowledgment of where the ecosystem's gravity actually is.
- **Warnings over failures for harness capability gaps; errors over silence for config mistakes.** An adapter whose harness can't express something (Codex has no commands, Gemini has no agents) emits a warning and moves on; the static `ComponentSupport` matrix documents the ceiling. But an unknown harness name, a `hooks: own` on a non-hook-emitting harness, or `source: repository` with no top-level repository are hard `ConfigError`s — the config layer refuses to let anything be silently ignored.
- **Refusing to validate the Codex manifest.** SchemaStore's codex schema is closed and rejects known-good manifests (including superpowers' own, which omits the load-bearing `hooks: {}` field), so `validate` pins codex output with exact-content tests instead of a schema that lies. Knowing when the checker is wrong is part of the tool's job.
- **Heavyweight verification, deliberately.** The `everyharness test` container is ~15GB, linux/amd64, and pins nine harness CLIs. That is an enormous cost for a plugin generator — accepted because tier-2 checks (real install + skill enumeration) are the only way to catch wiring bugs that parse-level checks structurally cannot.
- **Version management as regeneration.** `bump` rewrites `everyharness.yaml` (comments preserved via `src/field-edit.ts` dotted-path edits), rewrites declared non-generated `release.files`, regenerates everything, then audits for stray version strings in unaccounted files. Declaring a generated file in `release.files` is a `ConfigError` — the two systems would fight over the same file, and the tool refuses to arbitrate silently.

## Comparison notes

- [[Compound Engineering Plugin]] — the closest cousin, and the useful contrast. Every's converter translates one Claude-native skill format into each of 14 hosts' plugin formats, but it's a one-way skill translator inside a content plugin. everyharness is the infrastructure generalization: it targets the full plugin surface (manifests, hooks, MCP, marketplace descriptors, install docs), owns its outputs with a drift manifest, and verifies real installs in a container. Compound Engineering converts; everyharness compiles, commits, and audits.
- [[Claude Code Skills System]] — everyharness's source model *is* Claude Code's plugin model: skills as SKILL.md directories, commands/agents as frontmatter markdown, hooks.json and .mcp.json as component files. This repo is effectively a bet that Anthropic's plugin schema becomes the portable interchange format, and its deep-merge patch system (`harnesses.<name>.manifest`) exists precisely because every other harness's manifest is a variation on it.
- [[Agent Host Protocol (AHP)]] — the protocol-level answer to the same fragmentation problem. AHP standardizes the *session* (one agent session attachable from any client, LSP-style); everyharness standardizes the *distribution packaging* (one plugin config compiling to every harness's on-disk format). They operate at different layers and could coexist — AHP assumes standardized session transport that doesn't yet exist, while everyharness accepts the formats as they are and generates to each.
- [[Team-Wide Agentic Harness]] — Langworth's argument that skills and harness config are code deserving review discipline. everyharness operationalizes a harder version of that claim for plugin *distribution*: generated files are committed (reviewable), hand-edits are flagged by sha256, and drift is a CI exit code. Where Langworth version-controls the harness you use, everyharness version-controls the artifacts that install a plugin into everyone's harness.

The opinionated take: everyharness is interesting less as a tool than as an ecosystem diagnostic. Twelve harnesses, each with a plugin format nobody else reads, each drifting independently, and three of them riding Claude's descriptor files for install — that is the N²-format problem reasserting itself one layer above MCP (which standardized tools but not plugins). A compiler with a drift manifest is a reasonable patch, but it's also an admission that the de-facto standard is "whatever Claude Code did," with everyone else as delta. The dated empirical comments (hook double-fire dedup, Copilot's descriptor monoculture, Hermes' Path-vs-string landmine) are the part that outlasts the tool — that's harness-behavior documentation that none of the vendors have written down.
