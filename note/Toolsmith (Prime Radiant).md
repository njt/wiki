# Toolsmith (Prime Radiant)

Toolsmith is a Claude Code plugin by Jesse Vincent / Prime Radiant that attacks a real, observed failure mode: coding agents constantly build throwaway helper scripts — log trawlers, data converters, one-off fixers — save them wherever they happen to be, and nobody ever finds them again. The plugin's diagnosis (stated in the design doc at `docs/superpowers/specs/2026-11-05-toolsmith-plugin-design.md`) is sharper than the usual "agents are sloppy": the cause is prompting. The standard standing rule "write a named script instead of a one-liner" tells agents to write scripts and says nothing about where they live or whether one already exists, so the answer is always a new file. Toolsmith redirects that same instinct at a shared, git-backed catalog.

---

## Architecture

The plugin has four moving parts, with a strict division of labour:

- **`hooks/inject`** — one bash script serving two hook events (SessionStart matching `startup|clear|compact`, SubagentStart matching `.*`). It parses the hook's stdin JSON with regex (no `jq` dependency), asks `toolsmith-repo locate` for the literal absolute catalog paths, and emits a small "Toolsmith:" block: the definition of a tool, the exact `grep -s -i -E '<words>'` search command, the instruction to call the toolsmith, and the instruction to never write one yourself. It exits silently when `agent_type` is `toolsmith:toolsmith` so the subagent doesn't get its own pitch. Every failure path still exits 0 with valid JSON, and it appends `/usr/bin:/bin` to PATH because Claude Code can spawn startup hooks with a broken PATH (anthropics/claude-code#43127).
- **`skills/writing-tools/SKILL.md`** — the working agent's full rulebook: the tool/mission test, the four-field brief format, and how to act on the reply.
- **`agents/toolsmith.md`** — the subagent, with `omitClaudeMd: true` (requires Claude Code 2.1.271+, silently ignored by older versions) and no Agent tool (no recursion). Its frontmatter `description` is written for the Agent tool's chooser.
- **`bin/toolsmith-repo`** — 909 lines of bash 3.2-compatible plumbing that is the only code allowed to touch the tools repo: `path`, `locate`, `catalog`, `stage`, `install`, `move`, all emitting `key=value` lines and a documented exit-code table (0–9).

The tools repo lives at `~/.local/share/toolsmith/tools` (symlinkable to move it), with global tools in `bin/` and project-scoped ones in `projects/<key>/`, where the key is the project basename plus 6 hex chars of a git hash of the canonical root — taken from `git rev-parse --git-common-dir`, so every worktree and subdirectory of one repo shares a catalog.

## Key techniques

- **Deterministic core, probabilistic shell.** Everything with one right answer — git plumbing, locking, catalog generation, concurrency control — lives in `toolsmith-repo`, a tested bash script; the LLM subagent is only a thin procedure over it. The subagent's rules explicitly forbid running `git` or any raw file command on the tools repo, and the reason is concrete: neither `cd` nor shell variables survive between Bash calls, so a `git -C "$TOOLS"` with `$TOOLS` unset resolves to the caller's project. `toolsmith-repo` re-resolves the repo path on every call.
- **Optimistic concurrency via content hashes.** `stage` hands back a `base=` git blob hash of the staged copy (computed with `hash-object --no-filters` so a caller repo's autocrlf can't perturb it); `install` takes a repo lock, re-checks `bin/<name>` is still at that base, and exits 3 if someone else changed it — the agent then re-stages and redoes its edit, retrying once. The lock is a `mkdir`-atomic directory in the git dir holding the holder's PID, with a `.break` guard so two waiters seeing the same dead PID can't both break the lock, plus PID-liveness staleness breaking.
- **Snapshot-and-rollback writes.** A failed `install` or `move` must leave the repo as it found it — otherwise a retry sees its own half-install as a moved base (spurious exit 3), and the next install silently adopts leftover files. So `snapshot_writes` saves the index and each target file into the lock dir, and the EXIT trap rolls everything back, including removing directories it created.
- **Catalog-as-index with generation.** Each tool carries a `toolsmith-v1:` one-line purpose comment within its first five lines (in the language's own comment syntax; only the first five lines count so a header quoted in help text doesn't leak); `write_catalog` regenerates `CATALOG.md` atomically (write-tmp-then-rename) from those headers. `install` refuses a tool with no header (exit 7) — an uncataloged tool is invisible, so it's enforced, not encouraged. The design doc names catalog drift as an anti-goal: a catalog agents can't trust forces source-reading and kills the cold-start economics.
- **Hook-injected literal paths.** The hook injects the *actual absolute paths* and the ready-made grep command, because round two of design review found agents building `$HOME`-based paths themselves produced two different readings of the repo location. Also notable: a superpowers-derived hook script that hardcodes `SessionStart` silently injects nothing into subagents under Claude Code 2.1.318+ ("Hook returned incorrect event name"), hence the event-name-as-argument design.
- **Fixed reply protocol.** The toolsmith's final message is one block — `tool:` / `catalog:` / `status:` / `mutates:` / `verified:` / `assumed:` / `note:` — never prose. It never asks questions; thin briefs get guesses listed under `assumed`. Failures are `tool: none` with a note, and remedies stderr suggests (fix the rebase, remove the lock) are explicitly for the human, not the agent.
- **Cross-harness porting without code changes.** Outside Claude Code there are no hooks and no named agent: the skill tells the agent to run `toolsmith-repo locate` itself and launch a general-purpose subagent with the agent body, both reference files, and the absolute `toolsmith-repo` path pasted into one prompt, so the subagent reads nothing from the plugin. All the per-harness manifests and install docs are generated by [[Everyharness]] from `everyharness.yaml` — never hand-edited.

## Design decisions

- **Cheapest lookup is self-service.** An early draft routed every lookup through the subagent; reviewers argued a cold subagent start to return one grep-able line is the most expensive lookup available and the reason agents would route around the whole rule. Now the working agent greps the catalog itself and the toolsmith handles only new/changed tools.
- **`omitClaudeMd` matters more than it looks.** Subagents load the user's and project's CLAUDE.md by default, which would hand the toolsmith "follow TDD", "ask questions one at a time", and the mission project's conventions — all wrong for a shared repo that isn't the project.
- **`agents/` is deliberately a single file.** Plugin agent directories are scanned recursively, so a stray `agents/toolsmith/notes.md` would register as an `toolsmith:toolsmith:reply-format` agent with every tool — handing the authoring recipe to every working agent, the exact thing the plugin withholds.
- **Skills budget.** Only `writing-tools` ships as a skill because every skill name appears in every agent's context; three earlier toolsmith-side skills were cut.
- **No self-granting permissions.** The plugin could ship a PreToolUse hook that auto-approves its own commands; it deliberately doesn't, and documents the opt-in `Bash(toolsmith-repo *)` allow rule for the user instead. Permission friction is treated as a real product constraint — the README maps exactly what prompts in each permission mode, and the design doc's anti-goal is a toolsmith "slow or chatty enough that agents prefer writing a heredoc."
- **Context frugality is a tool standard.** Authoring standards require errors written for an agent reader ("no field 'user.id' in line 14 of app.log. Run with --list-fields..."), overflow dumped to a file with only the path printed, and no uninvited files in the caller's directory — because "an agent pays for every line of output in its context."

## Comparison notes

- It's the same lineage and plugin pattern as [[Superpowers for Humans (O'Reilly)]] — the hook script is explicitly copied from superpowers' session-start, and the spec's constraint was "shareable like superpowers, nothing from one person's CLAUDE.md." Where superpowers encodes *process* as skills, Toolsmith encodes an *economy*: it changes what agents do with surplus effort by making reuse cheaper than rewriting.
- [[Everyharness]] was extracted from this same shop and generates Toolsmith's per-harness artifacts from one `everyharness.yaml`; Toolsmith is its most demanding consumer, since the same plugin must degrade gracefully from full hooks-and-subagent support down to a paste-the-prompt-into-a-generic-subagent path.
- Compared with [[Go Skills for Claude Code]] — which is pure prose where the frontmatter description is the whole trigger surface — Toolsmith pairs prose with a deterministic binary and treats the prose as instructions *about* the binary; the tested code is the invariant layer, not the advice.
- The pressure-scenario methodology (real `claude -p` sessions against fixtures, 18/18 trials, published caveats about the permission classifier being a model) is a stronger empirical standard than most plugins ship; the design doc's two adversarial review rounds each caught concrete failure modes (heredoc escape hatch, agents writing into the repo without the lock).

Weaknesses worth naming: the cross-harness path is untested outside Claude Code (no other harness has run a trial), the fixed repo location is POSIX-flavoured (`~/.local/share`), the toolsmith is a cold subagent on every call, and the whole scheme rests on hooks and skills actually steering model behaviour — which the pressure scenarios test but can't guarantee across model versions.
