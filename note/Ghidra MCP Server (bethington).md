# Ghidra MCP Server (bethington)

A production-grade Model Context Protocol server that lets AI agents operate Ghidra, the NSA's reverse engineering suite — 209 tools spanning decompilation, renaming, structure creation, P-code emulation, and live debugging. It matters less as "yet another MCP server" than as an argument about where conventions belong: v5.0 moved naming rules, type safety, and documentation standards out of prompts and into the tool layer, where they are *enforced* rather than remembered. The repo is ~68K lines of Java plus ~5K of Python, with 255 Java files, an unusually disciplined test suite, and a changelog that reads like an engineering notebook.

---

## Architecture

The system is deliberately two-tier, split across a process boundary Ghidra owns:

- **Java plugin (`src/main/java/com/xebyte/`)**, ~44K lines. `GhidraMCPPlugin.java` (1,232 lines) is the Ghidra extension entry point; it boots an `McpHttpServer` that serves a Unix domain socket (`ghidra-<pid>.sock`) and optionally TCP on `127.0.0.1:8089`. The endpoint surface is generated by reflection: `AnnotationScanner.java` (877 lines) walks `@McpTool(path=..., category=..., access=...)` annotations on service methods and publishes the resulting catalog as JSON at `/mcp/schema`. The bridge then builds MCP tools *from that schema* — the Java side is the single source of truth.
- **Domain services** under `core/`, split by concern: `FunctionService` (4,877 lines), `AnalysisService` (5,137), `DataTypeService` (4,690), `ProgramScriptService` (3,769), plus smaller services for xrefs, comments, symbols, debugger, emulation, and version control. The headless server (`headless/GhidraMCPHeadlessServer.java`) reuses the same services via a `ProgramProvider` abstraction — 186 of the 209 tools are served by both GUI and headless servers, and the split is audited by `tools/audit_server_scope.py`.
- **Python bridge (`python/bridge_mcp_ghidra/`)**, ~5K lines: FastMCP server, transports (stdio, streamable-http, deprecated SSE), a `registry.py` that dynamically builds tool functions from `/mcp/schema`, and `discovery.py` which finds running Ghidra instances by scanning socket directories and TCP port ranges.
- **`ghidra_scripts/`** ships ~60 Ghidra scripts (documentation workflows, propagation, repair passes) callable through the MCP surface.

## Key techniques

- **Annotation-driven tool catalog.** Every endpoint is a `@McpTool`-annotated Java method; the schema, the README API reference (`tools/gen_readme_api_reference.py`), and conformance tests (`tests/endpoints.json`) are all generated or verified against the same catalog. Docs cannot drift from code because both are derived.
- **Convention enforcement in the tool layer.** `NamingConventions.java` (1,490 lines) is the heart of v5.0: a 90-verb allowlist, verb-specificity tiers (vague verbs like `Process`/`Handle` require two specifier tokens; `ProcessData` fails because `Data` is on a weak-noun denylist), Hungarian auto-prefixing on struct fields, and PascalCase/module-prefix regexes — with a comment documenting a regex bug where `X64_` prefixes failed matching. Writes return auto-fix / warn / reject per policy tier.
- **Normalized function hashing.** `DocumentationHashService.java` computes opcode hashes with absolute addresses replaced by placeholders, so identical functions match across binary versions and documentation propagates automatically — version-control for RE knowledge.
- **Emulation as a tool.** `EmulationService.java` wraps Ghidra's P-code emulator for API hash resolution: plant a candidate string at a scratch base (`0x7FFE0000`), set registers from a template, run up to 100K steps, compare the output register — `emulate_hash_batch` brute-forces a hash against a candidate list in one call.
- **Lazy tool loading under provider constraints.** Advertising 209 tools in one `tools/list` exceeds Gemini's constrained-decoding state-machine limit (a hard 400, not a degradation). The bridge loads only `listing,function,program` on connect and registers groups on demand via `search_tools`/`load_tool_group`/`tools/list_changed` — a real-world example of tool catalogs colliding with context-window economics.
- **Alias-folding in the bridge.** `registry.py` declares each `@Param(aliases=...)` spelling as an optional parameter and folds it onto the canonical name, because FastMCP's pydantic validation silently dropped alias spellings the Java server genuinely serves.
- **Instance discovery.** `discovery.py` scans every plausible socket-directory candidate and de-duplicates, working around a bug where Claude Desktop spawned the bridge without `$TMPDIR` so the plugin's socket landed in a directory the bridge never checked.

## Design decisions

- **The tool is the contract, not the prompt.** The project's central bet is that AI-agent consistency comes from enforcing conventions at the write boundary ("convention arbitration stays in the tool, not in code review"), not from pasting style guides into prompts. This is the same insight as linting over instructions — executable standards beat remembered ones.
- **Simplicity traded for surface area.** 209 tools is a selling point and a cost: the README documents an entire regime (lazy loading, paging, tool consolidation) devoted to managing catalog bloat. v7.0.0 folded 53 tools away, consolidating nine function readers into one `get_functions` with a `fields=` selector — an admission that the maximal-surface instinct needed correcting.
- **Localhost-first security, opt-in danger.** Script execution endpoints execute arbitrary Java inside Ghidra and were made default-off in v5.4.1 ("the prior default was unsafe"); non-loopback binds refuse to start without a token; filesystem endpoints canonicalize under `GHIDRA_MCP_FILE_ROOT`. A tool that renames functions in a shared database and can run code needed this.
- **Strict multi-program mode is opt-in.** Without `GHIDRA_MCP_REQUIRE_PROGRAM_SELECTORS=1`, a call omitting `program=` silently rides the shared "current program" — a wrong-binary write hazard when several clients share a server. They chose backward compatibility over safety-by-default, which is the defensible-but-cowardly call.
- **Shared Swing-thread bottleneck.** GUI-server handlers queue on the single Swing thread, so worker pools stay small by design; the headless server uses a `DirectThreadingStrategy` instead. GUI coupling is the price of live debugger and UI-cursor integration.

## Comparison notes

- Directly comparable to [[REA (morluto-rea) — MCP Server for Agent-Driven Reverse Engineering]], which takes the opposite architectural bet: provider-neutral adapters bridging many RE tools (Ghidra among them) rather than one deep, native integration. Ghidra MCP wins on depth (emulation, debugger, convention enforcement live inside Ghidra's APIs); REA wins on breadth. They also document their relationship honestly — the changelog notes game-specific tooling was split out to keep this a generic server.
- [[Giving Your Agent Eyes with Game Boy Hacking]] wires an early Ghidra-MCP generation into a ROM-hacking loop and concludes the feedback loop matters more than the tool count; this project is the matured counter-argument — when the tool layer also enforces quality (completeness scoring, naming gates), the tools themselves become part of the loop's discipline.
- [[WinDbg MCP]] covers the dynamic-analysis half of the same problem; Ghidra MCP's v5.4 debugger integration (TraceRmi-based step/breakpoint/memory tools with ASLR-aware address translation) brings static and dynamic under one catalog instead of requiring a second server.
- The lazy-loading and allowlist design ([[MCPs Aren't APIs — Stop Treating Them Like One]] makes the general case for tool surfaces as contracts) is a working answer to the tool-catalog economics [[Computer Use is 45x More Expensive Than Structured APIs]] describes: the bridge treats tool enumeration as a context cost to be minimized, complete with a documented *minimum viable read-only allowlist* of four tools.
