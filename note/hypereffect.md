# hypereffect — Server-Guided Reactive UI for Every Renderer

hypereffect.dev is a spec page for a deliberately tiny protocol: a server describes an interface with **signals** (state) and **elements** (18 fixed components with semantic variants), the client renders it natively on whatever platform it runs on, and interaction is just local state patches plus named actions sent back to the server. No styling, no custom components, no scripts — expressions over state compute values but have no side effects, which makes opening an unknown server "about as risky as reading what it says." Its most interesting use case in this wiki's terms: **agents generating interfaces at runtime as plain JSON, with nothing to run**.

---

## What the protocol actually is

The loop, walked through three worked examples (a basil plant monitor, a restaurant booking form, an expense filer):

- Renderer → `hello {}`. Server → signals plus elements. `element {"id":"water","type":"button","parent":"plant","variant":"primary","label":"Water now","onPress":{"action":"water"}}`
- Elements declare the few interactions they support. A handler does exactly two things: **patch local signals** (`{"patch":{"_why":true}}` — underscore-prefixed signals never leave the client), or **fire an action** with the current signals.
- The server answers with new/replaced/removed elements and **signal updates** that merge into client state — and because attributes like text, visibility, and disabled are *expressions* (`{"cel":"'Soil moisture ' + string(s.moisture) + '%'"}`), the interface re-derives itself locally without another round trip.

## Key quotes

> There is a **fixed set of eighteen components**, and they carry **semantic variants, not styles**: `h2` or `warning`, never a colour or a margin.

The interop bet in one sentence. Like HTML's element set, the constraint is what makes every renderer able to show every application — and what makes native look-and-feel free rather than themed.

> The server describes the UI. The client receives the interface itself: it never parses contacts or orders and never needs to know what they mean in order to render them.

Classic hypermedia (HATEOAS) applied to UI, not just to links. The client is dumb by construction — which is exactly the property that matters when the "client" might be a phone, a serial line, or a sandboxed WASM module.

> **Interfaces generated by agents** — An LLM agent builds forms and choices on the fly, as plain JSON with no code to run.

The use case that connects this source to the rest of this wiki: an agent-facing UI protocol where the model's output is declarative description rather than executable frontend code.

> In the other direction, the server treats every action as untrusted user input, whatever the renderer claims to have shown.

Quietly the most security-literate line on the page — the server must not assume the UI constraint it sent was honored, which is the same defense-in-depth posture as never trusting client-side validation.

> hypereffect strives to be the world's second most successful hypermedia system, after HTML.

Self-deprecating ambition, but the framing is right: the historical argument (every platform rebuilt interfaces from zero until a shared layer won — phones "until Android") is the whole thesis.

## Opinionated take

This is the most coherent answer yet to "what does an agent-built UI look like" — and it's notably *not* "the agent writes React." The design insight is that the safer and more interoperable you make the description, the better it suits LLM generation: eighteen components and side-effect-free expressions is a target a small model can hit reliably, and there is no arbitrary-code-execution surface for a hallucination to exploit. Compare that with the industry default of agents emitting framework code, where every widget is a fresh attack and compatibility surface.

The honest limits are also the tell: hypereffect explicitly excludes dense screens, tools people live in, and anything visually interactive. That carves out roughly the entire consumer software economy — but leaves behind a huge residue (control panels, internal tools, device UIs, form-and-list services) that is precisely the long tail of software agents are being asked to build. The bet is that the boring 80% is winnable with a boring protocol. I think that's right, and the "second most successful hypermedia system" framing quietly admits the ceiling.

One critique: "no custom components" is doing enormous work. The history it cites (OSes, Android) suggests shared layers win by being *extensible enough*, not minimal; HTML survived partly because it grew. A fixed eighteen is either the discipline that makes it work or the ceiling that caps it — the spec can't know which yet.
