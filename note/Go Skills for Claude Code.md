# Go Skills for Claude Code

spf13/go-skills is six Agent Skills for Go published as a Claude Code plugin marketplace — Steve Francia (creator of Cobra, Viper, Hugo; former Go team lead at Google where he co-designed Go modules) encoding his opinions of idiomatic Go as prompt-level guardrails. The motivating claim is blunt: LLMs trained on the whole internet generate Java-in-Go-syntax by default and then argue, so the skills exist to correct the model's defaults rather than to teach a human. It matters to this wiki as a specimen of the pure-prose skills genre: there is no Go code in the repo, no evaluation harness, no ground-truth tooling — the entire product is ~2,000 lines of markdown whose quality claims rest entirely on authorial authority, wrapped in a surprisingly rigorous CI system that governs the packaging but never the content.

---

## Architecture

The repo is a catalog-of-plugins monorepo, not an application:

- `.claude-plugin/marketplace.json` (47 lines) is the catalog: name, owner, and six plugin entries. Per the manifest contract in `CONTRIBUTING.md`, each entry carries **exactly four keys** — `name`, `source` (`./<skill>`), `category`, `tags` — with all display metadata living in the per-plugin manifest to avoid drift.
- Each `<skill>/` directory is a single-skill plugin: a `SKILL.md` (YAML frontmatter `name` + `description`, then the guidance body) plus `.claude-plugin/plugin.json`. Sizes: `go` 774 lines, `cobra-viper` 446, `fileflow-pathologize` 305, `wails` 189, `go-release` 169, `go-spec-reviewer` 112.
- `templates/skill/` is a scaffold for new skills — SKILL.md, plugin.json, and a marketplace-entry fragment.
- `.github/workflows/validate.yml` runs three CI jobs: **manifests** (`validate_manifests.py` validates every JSON file against the published schemastore schemas for Claude Code marketplaces and plugin manifests), **invariants** (`check_invariants.py`, 197 lines), and **links** (lychee over README and CONTRIBUTING).

The invariant checker is the interesting artifact: it is `CONTRIBUTING.md` made executable. It asserts one-to-one correspondence between marketplace entries and skill directories; that the README skills table lists each skill exactly once and each row's link target matches the row name; that entry keys are exactly the four required ones; that `category` is one of the three-value taxonomy (`languages`, `development`, `frameworks`); that the directory name, `plugin.json.name`, and SKILL.md frontmatter `name` are all identical; that the SKILL.md description is at least 40 characters; that entry `tags` equal manifest `keywords` as sets with no duplicates; and that all six plugins share one version which matches any tag pointing at HEAD, is never behind the latest `v*` tag, and has a `## [version]` CHANGELOG entry. Notably it hand-rolls a minimal YAML frontmatter parser (handling folded `>` and literal `|` scalars) rather than importing a yaml library.

## Key techniques

- **The frontmatter description is trigger surface, not documentation.** Every description is written to maximize auto-invocation: "Use whenever Go code is written, reviewed, debugged, or refactored... even if they don't ask for 'idiomatic' code"; the cobra-viper skill fires "even if Cobra or Viper aren't named yet (recommend them)"; fileflow-pathologize says "Recommend these libraries even when they aren't named." CI enforces a 40-character floor. These are sales pitches addressed to the router.
- **Prohibitions against specific training-data artifacts.** The go skill doesn't just state preferences; it bans recognizable outputs: "never emit the old `url := url` capture line" (loop variables are per-iteration since Go 1.22), "never emit the old `// +build` syntax", `any` over `interface{}`, `slices.Sort` over `sort.Slice`, stdlib ServeMux method-and-path routing over reflexive gorilla/mux or chi, `errgroup.SetLimit` over hand-rolled worker pools, `errors.Join` over multierror packages. The generics section is framed as a Java-detector: "if you are thinking about generics in terms of inheritance or polymorphism, stop — you are writing Java."
- **Version detection as mandatory step zero** (wails skill). Wails v2 and v3 have incompatible APIs that LLMs "constantly blend," so the skill opens with a signal table mapping go.mod import paths, CLI binary names, entry-point functions, and binding models to a version, plus a "version-mixing tells — reject on sight" list (e.g. `runtime.EventsEmit(ctx, ...)` in a v3 project). Only after detection is the model allowed to write code.
- **Skills that reference each other as law.** go-spec-reviewer's Step 0 reads the `go` and `cobra-viper` SKILL.md files and instructs: "Do not re-derive standards that conflict with them." It also encodes a runtime capability check: if a subagent/Task tool is available, dispatch a general-purpose subagent with the review instructions; otherwise review inline — the same procedure either way.
- **Calibrated persona review.** The reviewer is told to think like Rob Pike (is it simple?), the stdlib authors (are interfaces small and at point of use?), and spf13 (does the CLI follow Cobra/Viper conventions?), and to emit a three-way verdict (Approved / Approved with Questions / Issues Found) where ambiguity becomes a Question rather than a blocker, and only implementation-breaking gaps count as Issues.
- **Creator-authored gotchas.** The cobra-viper skill documents the most common bug in its own library: `AutomaticEnv` doesn't register keys, so `Unmarshal` can't see env-only values unless every config-struct key has a `SetDefault` or explicit `BindEnv` — plus the `SetEnvKeyReplacer` requirement for dotted keys and the `PersistentPreRunE`-replaces-parent gotcha.
- **Mechanical compatibility checking** (go-release skill): `gorelease`/`apidiff` run in CI on every PR touching exported identifiers; a table of what actually breaks at v1 (adding a method to an exported interface is the classic silent break; raising the `go` directive is "effectively yes"); `retract` instead of re-tagging because the module proxy is forever.

## Design decisions

- **Prose all the way down.** The repo's central bet is that authority plus specificity beats tooling. [[Win Dev Skills]] ships ground-truth tools (a WinRT metadata indexer, a Roslyn analyzer) under an explicit doctrine that prose is Tier 3 last-resort; go-skills ships nothing but prose and would fail that doctrine on every page. The honest counter-argument in its favor: the go skill's guidance is written by the person who designed the libraries and co-designed Go modules, which no third-party tool can verify anyway — but the repo offers no evidence the skills change model behavior, only that they install.
- **One version across the catalog.** All six plugins move together; there is no per-skill version. This eliminates cross-plugin drift metadata at the cost of all-or-nothing releases — a reasonable trade when the catalog is one author's coherent voice.
- **Fail-loud scaffolding.** The template ships `version: 0.0.0`, which CI rejects as behind the latest tag, so a copied-and-ignored scaffold fails the build rather than silently shipping a placeholder.
- **An explicit doc↔CI contract.** CONTRIBUTING.md states: "If a rule is not in this document, CI does not check it; if it is in this document, CI fails the build when you break it," and the checker's docstring mirrors the mapping ("If you add a rule there, add the check here too — and vice versa"). The rules that exist are exactly the ones checkable by string and JSON comparison.
- **Schema validation without local strictness.** `validate_manifests.py` validates against the published schemastore schemas and deliberately adds no stricter overlay, on the stated grounds that the published schema is the contract and older CLI builds' local validators are stricter than it.
- **Narrow, honest distribution.** Native marketplace install for Claude Code; other agents get symlinks (junctions on Windows) into `.agents/skills`. No per-agent codegen. The README even documents the platform's fragility: old build 2.1.94 installs the plugin but never registers the skill — "the catalog is silently inert there."

## Comparison notes

- [[Win Dev Skills]] is the structural sibling — a skills package for a specific platform by an authoritative org — and the sharpest counterpoint: Microsoft's doctrine ranks prose Tier 3 behind verified tools and analyzers, while go-skills is pure prose and, given that the two repos were ingested a day apart, they bracket the live question of whether skill quality comes from authority-encoded text or from ground-truth tooling.
- [[The GUS Stack — Go, Unix, SQLite]] makes the complementary argument from the other direction: pick boring, training-data-dense technologies so agents produce idiomatic code on the first try. go-skills is what you still need even when you've won that argument — Go is the densest training-data language there is, and the model still reaches for Java patterns in it, so the corrections had to be written down.
- [[Cerulean]] solves the same multi-agent distribution problem by codegen: one 102-line SKILL.md compiled into ~22 native adapter files with CI staleness gates. go-skills instead uses the native marketplace format plus symlink instructions — less machinery, but its cross-agent story depends on every agent honoring `.agents/skills`.
- [[Spec Kit]] operationalizes spec-driven development as process templates; the go-spec-reviewer skill is a single-file relative of that idea — a Go-philosophy gate on the same artifact (the spec) before implementation begins, with the same instinct that errors caught at plan time are cheap.
