# har-extractor

A CLI tool by azu that extracts response bodies from HAR (HTTP Archive) files into a directory tree, preserving the URL path structure as the filesystem layout. The core extract function is 63 lines of synchronous TypeScript — a study in what you can accomplish with a single well-chosen heuristic and a clean data model. Despite its simplicity, it solves a common debugging and archival workflow: taking a browser's network capture and turning it into browsable, grep-able local files.

---

## Architecture

har-extractor is a single-pass pipeline with three stages, all running synchronously in a flat iteration over `har.log.entries`:

```
HAR JSON → decode response body → URL-to-path conversion → write to disk
```

The library (`src/har-extractor.ts:46-63`) is published as an npm module with both programmatic and CLI interfaces. The CLI (`bin/cmd.js`) is a thin wrapper using the `meow` argument parser to map flags onto the `ExtractOptions` interface.

**Data model**: The tool depends on the `har-format` TypeScript type definitions (`@types/har-format`) for the HAR 1.2 spec. The key types are `Har` (the root object containing `log.entries[]`) and `Entry` (each request/response pair with `request.url`, `response.content.text`, `response.content.encoding`, and `response.content.mimeType`).

**No streaming, no concurrency**: All file I/O is synchronous (`readFileSync`, `writeFileSync`, `makeDir.sync`). For HAR files from single page recordings (typically a few MB), this is the right trade-off — async I/O would triple the line count for no benefit.

## Key Techniques

### URL-to-path conversion with `humanize-url` + `filenamify`

The conversion pipeline turns `https://en.wikipedia.org/wiki/.har` into `en.wikipedia.org/wiki/.har`:

1. `humanize-url` strips protocol, `www.`, and trailing slashes — giving you a clean host+path string
2. `filenamify` sanitizes each `/`-delimited segment for filesystem safety — replaces reserved characters, handles Windows-illegal names, truncates to 255 chars
3. The result preserves the site's directory tree as a local filesystem hierarchy

This is the core technique. Unlike content-addressed storage (which would produce opaque hashes), URL-as-path creates a navigable mirror of the original site. You can `cd` into directories and `grep` across files in a way that mirrors the request structure.

### The `index.html` insertion heuristic

The tool's most opinionated move (`src/har-extractor.ts:28-35`): when a URL path doesn't contain `.html` but the response MIME type is `text/html`, it appends `/index.html` to the output path. This handles the common case where `/wiki/.har` returns HTML — without this heuristic, the file would be named `.har` and a browser wouldn't render it. With it, the path becomes `en.wikipedia.org/wiki/.har/index.html` — openable, browsable.

This heuristic is tuned for browser-generated HARs from DevTools. It would misfire on API endpoints that accidentally return `text/html` MIME types, but that's an edge case the tool doesn't optimize for.

### Base64 decoding for binary content

HAR stores binary response bodies (images, fonts, wasm) as base64-encoded strings with `content.encoding: "base64"`. The `getEntryContentAsBuffer()` function (`src/har-extractor.ts:8-19`) detects the encoding flag and decodes accordingly — `Buffer.from(text, "base64")` for binary, `Buffer.from(text)` for text. Entries with no `content.text` (externally referenced files) are silently skipped.

## Design Decisions

**Simplicity as the primary value**: At 63 lines, har-extractor is deliberately minimal. It doesn't handle content-encoding decompression (assumes the HAR generator already decompressed), doesn't stream, doesn't recover from per-entry failures, and doesn't cache. Each of these would be a valid feature in a larger tool — but har-extractor's strength is that you can read and verify the entire source in under a minute.

**Optimized for browser Developer Tools output**: The tool assumes HAR files generated by Chrome DevTools or similar browser-based recorders, which typically (a) decompress content before saving, (b) are a few MB for a single page load, and (c) have meaningful URL structures worth preserving as filesystem paths. It would struggle with HAR files from long-duration proxy recordings or with externally-referenced binary content.

**URL structure as the output schema**: Rather than defining its own output format, har-extractor lets the site's URL structure define the directory tree. This means the output is immediately familiar — the path to the file is the URL path you'd see in the browser's address bar. It's a design choice that prioritizes human navigation over machine processing.

**Sync I/O as deliberate constraint**: All file operations block the event loop. For a CLI tool that processes one HAR file at a time and exits, this is correct — async I/O with Promises/callbacks would add ceremony without changing the user-visible behavior.

## Comparison Notes

**vs. [[atifact]]**: Both tools read HAR files, but for completely different purposes. atifact parses HAR files containing OpenAI/Anthropic API calls to extract conversation trajectories for agent observability — its HAR parser is 1,055 lines with multi-turn deduplication and SSE stream reconstruction. har-extractor parses HAR files from browser DevTools to extract web assets — 63 lines with a URL-to-path heuristic. They parse the same container format (HAR 1.2) for entirely different payloads.

**vs. WARC/web archiving tools (wget, HTTrack, ArchiveWeb.page)**: Full web archiving tools capture a site recursively by crawling links, handling redirects, and preserving HTTP headers in WARC format. har-extractor is a complementary tool: it works with HAR files that a browser already captured, extracting what was already recorded rather than crawling anew.

**vs. manual extraction from DevTools**: Chrome DevTools lets you save individual responses via "Save as HAR with content" and manually export assets. har-extractor automates the "extract everything" step — give it a HAR file, get the full directory tree in one command.

**vs. [[Components of a Coding Agent]]**: har-extractor is the anti-agent — zero AI, zero model calls, pure deterministic pipeline. A good reminder that many useful developer tools don't need LLMs at all.
