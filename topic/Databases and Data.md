# Databases and Data

Every database now wants to be the only database you need — and at the same time, the strongest engineering argument in the field is that you should use the smallest, simplest database that will do the job. These are not contradictory positions; they are two rational responses to the arrival of AI agents as database consumers. Converged databases promise agents a single surface to query without understanding the architecture underneath. Composable databases promise agents programmatic primitives they can orchestrate without learning a monolithic system. The tension between them is the database field's central argument right now, and it is sharpened by the oldest unsolved problem in the discipline: the object-relational impedance mismatch, which agents, like the ORMs before them, must navigate — and which the evidence shows they navigate badly.

---

## The Argument

### Convergence: every database wants to be the only database

The clearest expression of convergence is [[AliSQL]], Alibaba's MySQL fork that grafts DuckDB's columnar OLAP engine and native HNSW vector search onto a standard MySQL base. The strategy is pragmatic: do not ask users to switch databases, just add the capabilities they need to the one they already run. The DuckDB engine delivers roughly 200× speedup on analytical queries versus InnoDB, and the vector index supports cosine and Euclidean distance across up to 16,383 dimensions — all through existing MySQL tools and drivers.

[[NornicDB]] pursues the same strategy from a different starting point: a graph database (Neo4j-compatible via Bolt and Cypher) that adds vector search with GPU acceleration, temporal queries via MVCC, and an Ebbinghaus-based memory decay system that fades knowledge unless reinforced. The self-reported benchmarks claim 12–52× speedup over Neo4j on the LDBC Social Network Benchmark. The memory decay feature is particularly interesting for AI agent memory systems, where an ever-growing knowledge store without decay eventually overwhelms retrieval. [[LatticeDB]] is the embedded, single-file expression of the same convergence: a Zig property-graph store that folds HNSW vector search, BM25 full-text search, and a graph changefeed into one query layer with no server — the graph-plus-vector bet shrunk to a single machine for Graph RAG and agent memory rather than scaled to a cluster like [[AntFly]].

[[DocumentDB]] takes convergence to its logical extreme: it is not a database at all, but a wire-protocol compatibility layer that makes PostgreSQL speak MongoDB. Every MongoDB operation becomes a PostgreSQL function call on a native `bson` type — aggregation pipelines, indexes, RBAC, sessions, transactions all run through PostgreSQL's transaction system. This is convergence by absorption rather than by addition: instead of building new capabilities, you make an existing database speak a different protocol.

[[Dolt]] converges version control and SQL: Git semantics (fork, clone, branch, merge, revert) applied to database tables, with cell-level lineage tracking and MySQL compatibility. It is being used for AI agent memory systems where agents need to branch, experiment with, and merge shared state — a use case that would otherwise require both a database and a version-control system wired together by application code.

The counter-current to convergence is [[Aurora DSQL]], AWS's serverless PostgreSQL-compatible OLTP database. Where converged databases pull capabilities into one system, Aurora DSQL pushes components apart: stateless query processors in Firecracker MicroVMs, distributed adjudicators for commit-time conflict resolution, a Journal replication system, and sharded storage nodes — each an independent, horizontally scalable service. The design defers all coordination to commit time: reads proceed coordination-free via MVCC with precise timestamps, while writes use optimistic concurrency control resolved at commit. The result is 0-RTT consistent reads and 1–1.5 RTT commits regardless of row count across regions. It does not add OLAP or vectors; it focuses on doing one thing — multi-region OLTP — extremely well. This is convergence's mirror image: disaggregation that scales each layer independently rather than adding features to a monolith. Murat Demirbas, who worked on the team that built it, describes the counterintuitive takeaway: building a novel global production database felt like less effort than expected, credited to strong upfront design and strategic reuse of PostgreSQL's engine and AWS's internal infrastructure.

### The case for small and composable

The best-argued counter-position to convergence is that most workloads do not need a converged database — they need SQLite.

[[SQLite Is All You Need]] makes the benchmarked case: a single 343 MB SQLite file serving a social network with 50,000 users and 1 million posts, delivering 3,654 req/s on a mixed read-write workload from one Node process with no database server, no connection pool, and no network round-trips. The WAL journal mode is the key enabler: with a writer sustaining 1,000 writes/s, WAL delivers 5.6× the read throughput of the rollback journal, with p99 latency of 4.40 ms versus 133 ms and zero `SQLITE_BUSY` errors. The argument is explicit about limits: a single writer serialises all writes, there is no built-in failover, and recovery time is bounded by file-restore speed. Postgres becomes the right call when many writers contend on the same rows, when read replicas or automatic failover are needed, or when real analytics is required. "We might scale one day" is not a good reason to pay the infrastructure tax prematurely.

[[SQLite is All You Need for Durable Workflows]] extends this argument to the agent workflow domain: SQLite plus Litestream streaming to S3 is the right default for durable agent state. Each agent or tenant gets a small, self-contained database; Litestream provides asynchronous replication for backup and migration. The author is candid about the trade-off — Litestream replication is asynchronous, so a restore can miss the newest local writes if the volume disappears before copying — and notes that Postgres remains the upgrade path when higher availability or broader scalability is needed.

[[Graft]] takes SQLite composability further: it replicates SQLite databases to the edge via object storage, using page-level versioning for lazy fetching and partial views. There is no cluster, no consensus protocol, no database server — just object storage as the source of truth and SQLite at the edge. The comparison page maps the landscape: mvSQLite (needs FoundationDB), Litestream (backup only, no distributed writes), cr-sqlite (CRDTs for automatic conflict resolution), Turso/libSQL, rqlite (Raft consensus). Graft's stateless-on-object-storage architecture is operationally simpler than anything requiring consensus nodes.

[[bucketvcs]] demonstrates the same philosophy applied to Git hosting: a single Go binary that stores all repository data directly in cloud object storage. The bucket IS the repository; no database holds Git objects. The root manifest uses CAS (compare-and-swap via `PutIfVersionMatches`) with exponential-backoff retry for optimistic concurrency — no distributed lock service required. This is the composability philosophy applied to infrastructure: object storage as the universal primitive, with application-level concurrency control replacing infrastructure-level coordination.

[[zvec]] is the composability argument applied to vector search: an in-process library, not a service. Billions of vectors, millisecond search, `pip install`. The right answer when your vectors fit on one machine — and with modern hardware, that is billions. Like SQLite, it wins by not being a system you have to operate.

The boundary of this philosophy is where things break. [[How to Corrupt an SQLite Database]] catalogues every known failure mode: file overwrites from rogue processes, POSIX advisory locking pitfalls (close any fd → lose all locks across all threads), sync failures from hardware that lies about flushing, memory corruption in the application address space, and deliberate misconfiguration (`PRAGMA synchronous=OFF`, `journal_mode=OFF`). The document is both a warning and an implicit argument: SQLite's guarantees are strong, but they end where the environment betrays them. [[Learning a Few Things About Running SQLite]] makes this operational: a DELETE-heavy cleanup job locked the database for over 5 seconds, crashing other workers — the exact kind of concurrent-writer pain that eventually forces a migration to Postgres. Batch deletes into smaller chunks worked around it, but the experience gave Julia Evans "more appreciation for why someone might reach for Postgres when concurrent writes matter."

### The object-relational tension is not solved, and agents make it worse

[[The Vietnam of Computer Science]], Ted Neward's 2006 essay, diagnosed the fundamental problem: object systems model the world through identity, state, behaviour, and encapsulation; relational systems model it through predicate logic and truth statements. These models are "too different to bridge silently." Neward catalogued six specific fracture points — inheritance mapping, schema ownership, dual-schema maintenance, identity semantics, query language impedance, and the partial-object problem — and concluded that none of the six possible responses (abandon objects, abandon relations, manual mapping, ORM-with-escape-hatch, language-integrated relations, framework-integrated relations) was the right answer. The essay anticipated both the Hibernate/Entity Framework wars and the eventual industry settlement on option four: use an ORM for the 80% and raw SQL for the hard 20%.

[[Object-Relational Impedance Mismatch]] formalises this into nine categories of mismatch: encapsulation breaking across the object/relational boundary, data type incompatibilities (SQL strings have lengths and collations; OO strings do not), structural differences (nested objects versus flat relations), manipulative differences (declarative set operations versus imperative per-class methods), and transactional differences, among others. The philosophical framing — declarative versus imperative interfaces, set theory versus graph theory, schema-as-truth versus objects-as-truth — makes clear this is not a technical glitch but a clash of worldviews.

The new evidence is that agents suffer from the same structural problem. [[Constraint Decay]] shows that when LLM agents are asked to generate backend code with mandated architectural patterns, database backends, and ORM layers, performance drops by an average of 30 percentage points from loose to constrained specifications — a 40% relative loss. PostgreSQL as a required backend caused the largest single drop (−19.3 percentage points); ORM effects were smaller but still negative. Data-layer defects — incorrect query logic plus database/ORM runtime errors — drove roughly 45% of logic failures. The agents are not bad at coding; they are bad at holding an object model and a relational schema in their context simultaneously and translating correctly between them — the exact failure mode Neward described.

[[Dapper Performance Trap]] documents a specific, repeatable instance: when C# `System.String` is passed through Dapper's default parameter mapping, ADO.NET maps it to `nvarchar(4000)`. If the target column is `varchar`, SQL Server performs `CONVERT_IMPLICIT` on every row — defeating the index and causing full scans. The benchmark: 176× slower on a million-row table (23 seconds versus 0.13 seconds). The article notes that AI-generated Dapper code will produce this default every time because that is what the documentation shows. Everything works — it just works slowly, and you do not know why until you dig into execution plans.

[[BEAVER]] quantifies the gap between agent SQL capabilities and enterprise reality. On BIRD, the leading public text-to-SQL benchmark, LLMs achieve ~82% execution accuracy. On BEAVER — derived from real private enterprise data warehouses with hundreds of tables, cryptic column names, implicit join relationships, and domain-specific conventions — GPT-5.2 with the best agentic framework achieves 10.8%. Even with oracle hints for all five subtasks (table retrieval, join key detection, column mapping, domain knowledge, query decomposition), accuracy maxes out at 30.1%. Schema-linking subtasks prove largely solvable with hints; domain knowledge and query decomposition remain stubbornly hard. The chasm between BIRD's 82% and BEAVER's 10.8% is the reality check on claims that agents can "just query the database."

[[SQL Pagination — Offset vs Seek Method]] fills one specific piece of this puzzle: agents generating paginated queries should default to the seek method (keyset pagination) rather than offset, which degrades linearly with page depth. The seek method requires a deterministic `ORDER BY` — exactly the kind of non-obvious expertise that LLMs lack without explicit instruction, and exactly the kind of error that produces silently wrong or slow results rather than failures.

### Correctness is structural, not bolted on

[[Correct by Construction]] proposes a radical data quality methodology: decompose every dataset into anchors (entity IDs), attributes (values), and links (relationships), then enforce completeness, uniqueness, and a ban on NULLs at each level. Sentinel values like "UNKNOWN" and empty strings are treated as NULLs in disguise. JSON containers are banned outright — they hide structure from the schema. The author acknowledges this is "not how things are commonly done" and frames it as a response to the situation where you "have a problem with data quality, and you want to try a different approach." It is deliberately extreme, a whitelist methodology that prevents problems by construction rather than detecting them after the fact.

[[Write Snapshot Isolation]] applies the same "structural, not bolted on" philosophy to transaction isolation. Standard snapshot isolation aborts transactions when they attempt to overwrite recently modified data — but this both rejects some valid serial executions (false negatives) and permits some invalid ones (false positives). The root cause, per Remy Wang, is that SI checks for stale writes when it should check for stale reads. WSI changes the check from "did someone else write to this?" to "did I read something that has since changed?" — a one-line fix that achieves serializability. It aborts more transactions than standard SI, but the aborts are correct.

[[Anomaly Detection]] provides the monitoring layer for data quality at the other end of the sophistication spectrum: Welford's algorithm for running mean and variance in constant memory, hourly bucketing with zero backfill during quiet periods, and three independent statistical checks (total count z-score, percentage spike, per-user anomalies). No machine learning, no configuration, a hardcoded 2σ threshold. The entire detection engine fits in a single file. This is not competing with [[Correct by Construction]]; it is the pragmatic counterpart — "you probably did not build your data correctly by construction, so here is how to detect when it goes wrong."

[[Materialized Views Are Obviously Useful]] argues that databases should handle derived data maintenance, not application code. Sophie Alpert traces the progression from a simple `count(*)` query through caching, incremental updates, cache invalidation, and eventual consistency nightmares — all of which disappear if the database simply maintains the aggregated view. The prediction that "within a decade, most database systems will incorporate this capability" names a gap that most of the databases in this wiki have not yet filled.

### Semantic layers: one definition, everywhere

The problem: a business metric like "revenue per active user" gets defined in dbt, Looker, Metabase, Python notebooks, Slack bots, and AI agents — and each definition drifts. Three pages in this wiki converge on the same answer: define the metric once, in a source-controlled artefact, and let every consumer resolve from that definition.

[[Metrics SQL]] does this with a YAML-defined metrics view (measures and dimensions) queried through a SQL dialect that transpiles to engine-native SQL. Measure expressions like `revenue` expand to `sum(order_usd)`, GROUP BY is inferred, filters on computed dimensions are parameterised for injection safety, and an MCP server exposes the metrics layer to AI agents. The longer-term vision is semantic pushdown: OLAP engines natively supporting `MEASURE` as a first-class SQL keyword, making the middleware layer unnecessary.

[[Malloy]] takes a language-first approach: a semantic modelling language that compiles to dialect-specific SQL for eight engines. The core innovation is symmetric aggregates — correctly handling joined data without double-counting by path-prefixing expressions (`line_items.amount.sum()`). Originally developed at Google by a team that included Looker's creator, Malloy is the open-source alternative to SaaS semantic layers: you write `.malloy` files, the compiler generates SQL, the model is the durable artefact.

[[KTX Context Layer for Data Agents]] goes further: it ingests metadata from dbt, Looker, Metabase, and live databases into a git-versioned wiki plus an executable semantic layer, then exposes it all through 11 MCP tools. The architecture wraps every LLM-powered write in three defences: worktree isolation (writes invisible until merged), skill-based tool gating (agents can only use tools their loaded skill exposes), and pre-merge validation (failed writes are reverted). The positioning is deliberate — a "context layer" rather than "agent memory," emphasising shared, reviewed, durable definitions over per-agent ephemera. Compared to [[Metrics SQL]], KTX is more automated in bootstrapping definitions from existing tools but has a less clean SQL interface; [[Metrics SQL]] is the cleaner query surface for humans, while KTX has richer agent-native tooling.

[[DAB]] (Microsoft's Data API Builder) solves the adjacent problem of giving agents database access: auto-generated REST, GraphQL, and MCP endpoints over SQL Server, PostgreSQL, MySQL, and Cosmos DB. The MCP server with custom tool configuration turns "give agents database access safely" from an architectural problem into a middleware configuration.

[[The Oracle Is the Asset]] makes a broader claim that bears on semantic layers: when compilers become cheap to generate (via LLMs), the scarce, durable asset shifts from the implementation to the reference behaviour — the test suite that defines correctness. Applied to data, this means the metric definition is the durable artefact; the generated SQL is regenerable on demand. Sam Ruby calls this a Drucker inversion: you manage what you measure becomes you own the spec the compiler answers to, and the implementation is regenerable. The same pattern holds whether the compiler targets JavaScript (Roundhouse), SQL ([[Metrics SQL]], [[Malloy]]), or agent-facing MCP tools ([[KTX Context Layer for Data Agents]]).

### Data movement as a first-class concern

[[The Log — Unifying Abstraction for Real-Time Data]], Jay Kreps's 2013 essay, established the intellectual framework: the append-only log is the natural data structure for data flow between systems. It enables decoupling producers from consumers, turning each subscriber into an independent time-traveller, and collapsing the O(N²) point-to-point integration problem into O(N) connections to a central log. The essay also reframes stream processing as continuous data processing — a generalisation, not a niche concern — and grounds the argument in LinkedIn's experience building Kafka.

The practical reality of CDC is that it is harder than it looks. [[Postgres CDC in ClickHouse, A Year in Review]] — a field report from PeerDB's first year inside ClickHouse after acquisition — documents the journey from a handful of users to 400+ customers replicating over 200 TB per month. The surprising finding: "the amount of iteration required to make the system feel *boring*" — meaning reliable, invisible, and fast. Long-running transactions, replication slot backpressure, schema changes, and edge cases discovered only when a customer hits them at midnight: these are not architecture problems but operational ones, and they require "hundreds, sometimes thousands, of smaller capabilities and edge cases working together." The PostgreSQL-compatible query layer they are building — effectively, making ClickHouse speak Postgres — is convergence by another name.

[[Streambed]] shows the composable alternative: a single Go binary that streams Postgres WAL changes, writes Parquet files to S3, commits Apache Iceberg metadata, and embeds a DuckDB query server that speaks the Postgres wire protocol — so you query Iceberg tables with `psql`. No JVM, no Kafka, no Spark, no external catalog. The architecture is deliberately simple: a single goroutine reads WAL, decodes pgoutput messages, buffers rows per table, flushes to Parquet, and acknowledges the replication slot. Correctness is maintained by a conservative ACK formula that never advances the slot past unflushed data. The testing investment is exceptional for a solo project — Jepsen-style simulation with chaos injection that continuously validates Postgres and Iceberg remain consistent.

[[DocDB — Stripe's Zero-Downtime Database]] takes data movement to production scale: Stripe's internal MongoDB-based DBaaS serving 5 million QPS across 2,000+ shards with 5.5 nines of reliability, processing $1.4 trillion in payments in 2024. The centrepiece is a zero-downtime data movement platform that makes resharding, version upgrades, and tenancy migrations all the same operation — a six-phase migration (register intent → bulk import with 10× throughput gain from sorted writes → bidirectional CDC replication → correctness check → millisecond traffic switch via version gating → commit) that runs under live production traffic. The platform is the primitive; scale, upgrades, and isolation are all applications of it.

### Agents as database consumers: the new problems

The arrival of AI agents as database consumers is not a future trend — it is already reshaping requirements. But the evidence suggests the gap between what agents can do with databases and what production systems need remains large.

[[AI-Assisted Database Work — The Machine Reads, The Human Decides]] documents nine real consulting engagements where AI was used to read, classify, and extract from existing database artefacts at volume. The common pattern: the machine reads at scale and proposes; a human verifies and decides. These are not hard problems; they are large, tedious, low-judgement reading tasks — extracting business rules from 400K lines of legacy PL/SQL, reverse-engineering an undocumented vendor schema from DDL and value distributions, mapping 900 columns across two company schemas during M&A diligence, diagnosing why a compliance document's one-cent reconciliation had persisted for years. In every case, the AI's value was reading at volume; the human's value was knowing what the AI did not know it did not know — the blast radius of a database-wide configuration change, the compound-noun ambiguity in abbreviated German column names, the fact that `CUSTOMER_STATUS` meant Active in one company and Archived in the other.

[[Long Live Systems of Record]] argues that agents do not kill systems of record — they raise the bar for what one looks like. Jamin Ball reframes "system of record" not as a product category but as the answer to "where does the truth live" in an enterprise. When an agent is instructed to "calculate ARR by segment and send a deck to the board," it needs a canonical table to query. Agents are inherently cross-system and inherently action-oriented — they dance across CRM, CPQ, and billing, changing state rather than just running reports. This forces a separation between the UX of work (a chat window) and the source of truth for work (a canonical customer record). The valuation insight: "an agent platform that becomes the place where metric definitions live starts to look much more like a source of truth," and the multiple follows "the stickiness of the truth, not the buzzword on the slide."

[[SQL Fraud Patterns (Fixel Smith)]] demonstrates that for all the talk of agents and ML, fraud detection in transaction data "is mostly SQL." Six composable patterns — velocity, impossible travel, amount anomalies, suspicious merchants, off-hours, and window-function primitives — built in roughly the order you would apply them to a new dataset. The window-function primitives are the meta-pattern: once materialised, fraud rules collapse to WHERE clauses ("three filters, that's it"), shrinking the iteration loop from weeks to hours because analysts express fraud hypotheses as SQL filters instead of engineering tickets. This matters for the agent discussion because it shows what the target looks like: agents querying fraud patterns will need the same kind of composable, filter-based access that human analysts use today.

### Operations at scale

[[ClickBench Playground]] is the largest interactive database comparison platform in existence: roughly 100 database systems behind a common interface, each preloaded with 100 million records, queryable side by side. The engineering story — a single bare-metal machine running Firecracker microVMs with elastic memory via swap-to-page-cache, BtrFS compression fitting 100 systems into 7.5 TB, and VMs resetting from snapshot after any query error — is itself a lesson in operational pragmatism. Alexey Milovidov's experiments surfaced uncomfortable truths: some entrants over-optimised for the default 43 queries, some non-commercial versions had dataset-size thresholds just above the default, and some systems stopped working entirely under concurrent query load. The broader finding: most databases cannot run unattended for long periods without crashing, OOMing, or infinite-looping. Only ClickHouse could be configured to run reliably on tiny hardware.

[[PgDog]] tackles the operational problem from the proxy layer: a single binary that combines connection pooling (50,000+ transactions/s per thread, no connection pinning), load balancing (read/write split, replication lag detection, automatic failover), and sharding (configuration-driven, cross-shard transactions via two-phase commit, sharding key mutation). The tagline — "Scale Postgres *n* times" — and the production claim of 1 million+ queries/second on 10 TB+ of sharded data make the case that the database itself does not need to converge if the proxy layer handles distribution.

[[We Replaced Redis with MySQL for Inventory Reservations]] is the best case study in this wiki for "your existing database might already be enough." Shopify replaced Redis with MySQL for inventory reservations and survived Black Friday 2025 at $5.1 million/minute peak sales. The key technical decisions: one row per sellable unit (enables `SKIP LOCKED` concurrency), bounded inventory pools capped at 1,000 rows, composite primary keys reducing InnoDB row locks from two to one, `READ COMMITTED` isolation to eliminate gap locks, consistent lock ordering to prevent deadlocks, and `UNION ALL` batching for multi-item carts. The hardest lesson was not about database design: "the real bottleneck wasn't what we were observing and measuring." Per-caller SQL comment tagging revealed that other checkout processes were holding connections too long — reservations were the straw that broke the camel's back. After cleanup, 50% of reads and 33% of transactions were removed from the primary. The article is an argument against premature infrastructure complexity: "If you're reaching for Redis, Kafka, or a custom coordination layer for high-throughput mutual exclusion, your existing database might already be enough."

[[Replace Athena with DuckDB (Lambda)]] makes the same argument for analytics: DuckDB on Lambda is 75–86% cheaper than Athena for S3 Parquet queries. DuckDB's `httpfs` extension reads only relevant Parquet columns via HTTP range requests, so Lambda execution time grows sub-linearly with data volume while Athena's scan cost grows linearly. The composability philosophy again: a small, focused tool beats the managed service on both cost and performance for this workload.

### Data tooling

Several pages cover tools that make database work more visible and navigable. [[Shaper]] powers SQL-driven dashboards with DuckDB — write SQL, get charts, with a casting syntax (`::BARCHART_STACKED`) that mixes presentation with query logic. [[sql-crack]] is a VS Code extension that transforms SQL queries into interactive execution flow diagrams, with column lineage tracing, CTE expansion, and workspace-wide dependency analysis across 13 SQL dialects — entirely local, no telemetry. [[SiftRank]] ranks datasets by relevance to a natural-language prompt using LLM pairwise comparisons, delivering deterministic rankings from a nondeterministic oracle in seconds for pennies.

[[Data Engineering for Large Models]] is a 28-chapter open-source textbook covering the complete LLM data pipeline: pre-training data cleaning, multimodal alignment, synthetic data generation, RAG architecture, and enterprise DataOps platforms. Its core framing — "data is the new oil, but only if you know how to refine it" — captures the data-centric AI argument that data quality improvements consistently outperform model architecture improvements at the margin. [[GraphRAG]] (Microsoft) tackles the retrieval side: building knowledge graphs from documents for structured retrieval that significantly outperforms naive vector similarity on cross-document synthesis and holistic summarisation tasks, though building the graph is expensive.

[[LLM Wiki]] is the architectural pattern underlying much of this wiki itself: a three-layer system where raw sources are immutable, the wiki is LLM-owned, and a schema document defines structure and workflows. The key insight is compounding rather than just filing — each new source triggers updates to related pages, not just a new page — which keeps the wiki a growing synthesis rather than a pile of disconnected summaries.

### Decentralised infrastructure

Three pages explore the idea that centralised database services are not always the right answer. [[Radicle]] is a peer-to-peer, local-first code collaboration stack built on Git — a sovereign alternative to GitHub/GitLab where repositories replicate across peers via cryptographic identities and gossip protocol, and issues, patches, and code reviews are stored as Collaborative Objects within Git. [[bucketvcs]] makes Git hosting itself decentralised: a single Go binary backed by cloud object storage with no database for Git objects. [[Graft]] applies the same pattern to SQLite: edge replication via object storage with no cluster required. These are different domains — code collaboration, Git hosting, database replication — but they share the conviction that object storage plus application logic can replace infrastructure services for a meaningful class of workloads.

### The Alibaba stack

Three pages — [[AliSQL]], [[zvec]], and [[OpenSandbox]] — come from Alibaba and form a coherent open-source data and AI infrastructure stack. [[AliSQL]] handles the database layer (OLTP + OLAP + vectors in MySQL). [[zvec]] handles the embedded vector search layer (billions of vectors, in-process, `pip install`). [[OpenSandbox]] handles the AI application sandboxing layer (Firecracker/gVisor/Kata isolation, multi-language SDKs, MCP server integration). Together they rival Western equivalents as an open-source portfolio, and they are worth evaluating as a stack rather than as individual tools.

## Where the Sources Disagree

**Convergence versus composability.** [[AliSQL]] and [[NornicDB]] bet that one database doing everything is better than several databases doing one thing each. [[SQLite Is All You Need]], [[Graft]], and [[zvec]] bet the opposite. The evidence does not resolve this — it splits by use case. Converged databases win at operational simplicity under moderate scale (the 95% case); composable databases win at cost, debuggability, and avoiding unnecessary infrastructure. The real question is not which is better but where the crossover point lies, and that depends on factors — team size, traffic pattern, data volume, operational maturity — that neither camp's benchmarks control for.

**SQLite versus Postgres as the default.** [[SQLite Is All You Need]] argues SQLite is sufficient for production web workloads far larger than most teams will ever see, and that premature infrastructure is a tax paid for traffic you do not have. [[SQLite is All You Need for Durable Workflows]] extends this to agent workflow state. But [[Learning a Few Things About Running SQLite]] shows the operational reality: concurrent writers cause timeouts, `ANALYZE` is an undiscoverable fix for slow full-text search, and backup via `VACUUM INTO` OOM-kills the process. These are not arguments against SQLite — Evans still calls her Postgres-to-SQLite migration a great choice — but they are evidence that "SQLite is all you need" has operational asterisks that the benchmarks do not surface.

**Build versus buy at scale.** [[DocDB — Stripe's Zero-Downtime Database]] makes the case for building your own database layer: security baked in from the start, a minimal battle-tested API surface, and a data movement platform that unlocks horizontal scaling, version upgrades, and tenancy migration as applications of the same primitive. The build-versus-buy framework is explicit: build when it drives long-term strategic advantage, requires unique reliability/security/scale controls, or provides better 3–5 year ROI. [[PgDog]] represents the buy (or at least adopt-open-source) alternative: drop in a proxy, configure sharding in a TOML file, no application code changes. Both approaches work; the choice is about whether your database layer is a differentiator or infrastructure.

**ORM: fundamental flaw or workable compromise?** [[The Vietnam of Computer Science]] and [[Object-Relational Impedance Mismatch]] argue the mismatch is structural, not solvable by better tooling. [[Constraint Decay]] shows that agents suffer from the same structural problem — the 30-percentage-point accuracy drop when ORM layers are mandated is empirical evidence that the impedance mismatch is real and damaging in practice. But the industry has largely settled on Neward's option four (ORM for the 80%, raw SQL for the hard 20%), and the databases in this wiki that are adding vector search, graph traversal, and temporal queries to SQL are arguably making the problem worse by increasing the surface area that ORMs — and agents — must navigate.

## What's Missing

**Agent-aware database patterns.** Agents generate queries differently from humans: more repetitive, less optimised, prone to the [[Dapper Performance Trap]] class of errors where everything appears to work but performance silently degrades. Database patterns specifically for agent-generated workloads — query plan guards, automatic parameter type correction, cost-based query rejection — do not exist yet. [[SQL Pagination — Offset vs Seek Method]] fills one small piece of this: agents generating paginated queries should default to seek method and must extend `ORDER BY` clauses to be deterministic. But a systematic treatment of agent-aware database design is a gap.

**Data quality for agent-generated data.** [[Correct by Construction]] addresses human data pipelines. When agents generate and store data at machine speed — without the implicit quality checks that human data entry provides — the quality problem changes character. There is no "Correct by Construction for agent-generated data."

**Streaming and real-time implementations.** [[The Log — Unifying Abstraction for Real-Time Data]] provides the theoretical foundation: the append-only log as the unifying abstraction across databases, replication, data integration, and stream processing. [[Streambed]] and [[Postgres CDC in ClickHouse, A Year in Review]] cover the CDC side. But the stream processing implementations (Kafka, Flink, RisingWave, Materialize) and the patterns for building streaming applications on top of them are not yet covered.

**Database migration patterns.** [[AI-Assisted Database Work — The Machine Reads, The Human Decides]] provides the most detailed public field report on AI-assisted migration: business-rule extraction, schema reverse-engineering, dialect-drift verification. But the operational question of what happens when you outgrow one of the databases in this wiki — the path from SQLite to Postgres, from MySQL to AliSQL, from a single-node deployment to a sharded one — is mostly undocumented. [[SQLite Is All You Need]] names the breakpoints (many writers contending on the same rows, need for read replicas, real analytics over hundreds of millions of rows) but, like [[SQLite is All You Need for Durable Workflows]], does not describe the migration experience itself. [[Learning a Few Things About Running SQLite]] shows this is not just architectural — it is operational: the concurrent-writer timeout cascade is exactly the kind of scaling pain that triggers a migration, and the path from "cleanup in small batches" to a real migration strategy is the missing chapter.

**Database reliability and failure modes beyond SQLite.** [[How to Corrupt an SQLite Database]] is the only page in the wiki that systematically catalogues when database guarantees fail — the boundary between the library's promises and the environment's betrayals. [[ClickBench Playground]] surfaces a related dimension: most databases cannot run unattended for long periods without crashing, OOMing, or infinite-looping. The operational maturity gap between databases is as important as the correctness gap, and much less studied. A "How to Corrupt a Postgres Database" or a comparative reliability survey does not exist yet.
