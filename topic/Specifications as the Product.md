# Specifications as the Product

The specification, not the implementation, is now the durable product of software engineering. Code is becoming a compilation target — regenerable in minutes from a good spec, worth less over time rather than more, discardable when the models improve. This claim is no longer speculative: it is the working assumption of the most productive AI-assisted engineering teams, and the evidence spans compiler design, agent swarm economics, enterprise platform migration, and the canonical precursor to the entire line of thought — Bezos' 2002 API mandate at Amazon, recounted in [[Stevey's Google Platforms Rant]], which required every team's service interface to be "designed from the ground up to be externalizable." The live disagreements are about what form a spec should take and how much formalism is enough, not about whether the inversion is happening.

---

## The Argument

### The Inversion: Code Becomes Disposable

[[Stevey's Google Platforms Rant]] is the ancestral text. In 2011, Steve Yegge compared Amazon and Google across every dimension and found Amazon ahead on exactly one: platform thinking. Bezos' mandate — all teams expose data through service interfaces, all inter-team communication goes through those interfaces, no back-doors, interfaces designed as externalizable on pain of termination — transformed Amazon from a product company into a platform company. The API spec became the product; the implementation became an implementation detail. Yegge's Golden Rule ("Eat Your Own Dogfood") and his theory of Accessibility — that software must be accessible to everyone, and the only way to achieve this at scale is through platforms that let third-party developers build the right thing for every user — are the same structural insight, applied at different altitude.

Twenty years later, the same inversion is happening at the level of individual codebases. [[The Dark Factory is a DOT File]] captures it bluntly: "Software is cheap now. Specs are the expensive part." The pipeline DOT file is the reusable artifact; the factory code is *dorodango* — polish it, throw it away, rebuild from spec. When code is fundamentally wrong, you regenerate it rather than debug it. The pipeline spec can mix deterministic shell commands and LLM-powered nodes strategically, applying expensive probabilistic generation only where it earns its keep.

[[Write Only Code]] pushes this to its logical conclusion: if nobody reads the generated code, the spec is the only human-readable artifact. The critical metric becomes Slop Radius — how far unintended behaviour can spread before detection — rather than code review thoroughness. The engineer transitions from author and reviewer to systems designer and constraint writer.

[[Agent Swarm Model Economics]] completes the compiler analogy. Each capability jump — autocomplete → line → block → file → spec — raises the abstraction level. At swarm scale, "what was scarce... is the right description of intent." The swarm becomes a probabilistic compiler from spec to code, with frontier-model planners decomposing goals and cheaper workers executing them. The SQLite experiment — implementing the 835-page SQLite spec in Rust without source code, test suites, or internet access — passed 100% of sqllogictest across multiple model mixes. Every model mix eventually converged; the difference was in efficiency, not capability.

[[The Claude C Compiler]] confirms the pattern from the compiler domain. Chris Lattner observes that agents implement known abstractions well but invent nothing: the compiler reproduces well-established LLVM/GCC patterns rather than originating novel approaches. The scarce resource shifts from writing code to deciding what deserves building. Lattner's operational insight: "well-documented systems gain dramatic advantage" as AI amplifies structure, while poorly structured code scales into incomprehensibility faster than before.

[[Simplicity in the Age of AI-Assisted]] explains why the economics favour this inversion. LLMs don't change what good programming looks like, but they enable cheap rebuilds without inherited complexity. A feature like "sticky header with cross-device persistence" can be re-implemented without the accumulated layers — databases, migrations, APIs, containerisation — that grew around the original. The hard part is the human part: recognising which complexity is essential and which is inherited. The LLM will not question your architecture; you must.

### What Counts as a Spec?

The sources converge on the *fact* of the inversion but diverge sharply on what a spec ought to be. The positions form a spectrum from narrative prose to formal languages, with no clear consensus about where the sweet spot lies.

**Narrative plans.** [[How to Write a Good Spec for Agents]] defines five principles for AI-oriented spec writing: start with a high-level vision and let the AI draft details, structure like a professional PRD with six essential areas, break tasks into modular prompts, build in self-checks and constraints, and iterate continuously. The three-tier boundary system — always do / ask first / never do — is a pragmatic response to the "curse of instructions": model performance drops as instruction count increases, so modular spec files beat monolithic prompts. [[Compound Engineering]] builds a whole methodology around this: the four-step loop of plan → work → review → compound, where planning and review together should consume 80% of an engineer's time. "Plans are the new code" — the plan document is the most important artifact. The 50/50 rule (half your time on features, half on improving the system that produces features) is the organisational prescription.

**Structured specs with stable IDs.** [[Specsmaxxing]] argues that markdown specs are better than no specs but still insufficient. The `feature.yaml` format gives each requirement a stable Acceptance Criteria ID (ACID) that threads through code comments and test annotations, creating a bidirectional traceability matrix between spec and implementation. A requirement tagged in the YAML as `AUTH-1` appears as `// AUTH-1` in the code and in test coverage reports. The prescriptive philosophy — specs describe how the system *should* behave — stands in deliberate opposition to descriptive approaches. The Acai.sh dashboard shifts code review from file-by-file diffs to requirement-by-requirement acceptance.

**Living specs with deltas.** [[OpenSpec]] introduces the spec delta: a diff showing how requirements evolved alongside code changes. Reviewers see the change in intent, not just the change in implementation. Specs live in the repository as persistent documentation organised by capability, surviving beyond individual chat sessions. The approach integrates with over 30 coding platforms and is deliberately lightweight — "10 minutes thinking things through" before code, incrementally building specs rather than writing them wholesale. [[Spec-Driven Development]] formalises this as a triangle — specs, tests, and code in continuous feedback — and introduces Plumb, a tool that intercepts commits to extract decisions from diffs and agent traces. The core insight: implementing code clarifies intent, and that clarification feeds back into improving the spec.

**Schema and contract specs.** [[Spec-First Development at Benchling]] shows the enterprise version: each object declares its shape and behaviour through a unified contract once, and every platform capability consumes it generically. Adding a new object means one schema declaration, not N integration adapters. The integration point moves from per-platform implementations to a single shared contract — the spec as the single source of truth.

**Pipeline specs.** [[The Dark Factory is a DOT File]] advocates for workflow specs in Graphviz DOT format — human-readable, version-controllable, familiar to anyone who has drawn an architecture diagram. Each node declares whether it needs an LLM, a human gate, or a deterministic verification command. The pipeline is the blueprint; the runner implementation is disposable. The convergence of independent teams on this three-layer architecture (LLM client, agent loop, pipeline engine) without coordination is what the source calls the Attractor Pattern: the structure is discovered, not invented.

**Typed signatures for LLM behaviour.** [[Prompt Debt]] diagnoses a specific form of technical debt: natural language prompts were never meant as a specification language for engineering. The imprecision of prose paired with probabilistic models means every hot-fix added to a prompt risks regressing earlier instructions. The examples are damning: ChatGPT instructs the model eight times not to reply, Claude Code tells Opus seven times to return multiple tool calls, Fable restates one copyright rule six times. The prevention strategy has two principles: specify behaviour with measurements (evals, metrics, typed constraints), not prose; and stop writing prompts by hand — search the prompt space algorithmically. [[DSPy — Programming Not Prompting]] is the framework that operationalises this: typed signatures define a task as inputs and outputs, modules control how the signature executes, and optimisers tune prompts against a scoring function until quality converges. The prompt becomes a disposable compiler artifact — the same inversion applied to the natural-language layer itself.

**The formal end of the spectrum.** [[Rewrite All the Code All the Time]] argues that structured natural-language specs — EARS syntax, YAML acceptance criteria, BDD scenarios — share a fatal flaw: formal keywords wrapped around freeform phrases leave ambiguity exactly where behaviour is decided. The terminal destination of the spec-as-product thesis is not better-structured markdown but formal languages with clear mathematical semantics — the only kind of spec that can be handed to an *adversarial* implementer without human oversight. [[Lean Software Scaling Laws]] extends this argument: the language you write specifications in matters for AI predictability, and some languages are inherently better spec languages because their invariants survive scaling. By measuring frozen-LLM perplexity over codebases across languages, one could rank languages by their suitability as spec targets — and if a language like Lean shows a demonstrably better scaling exponent, the investment case for formal-methods adoption becomes quantitative rather than religious.

**Specs beyond code.** [[Engineering Standards Enforcement at Cloudflare]] demonstrates the spec-as-product thesis applied to organisational policy. Cloudflare's Codex expresses engineering standards as RFCs using SHOULD/MUST, feeds them into AI reviewers as compact JSON with stable slug identifiers, and gates enforcement behind a lifecycle state. The system has flagged nearly 230,000 violations and blocked 16,000 merges; a separate spec reviewer has assessed nearly 600 technical design documents against Codex rules since May 2026. The RFC is the durable artifact; the reviewer agents are consumers of it. [[Tom Barraclough — Sovereign AI Policy]] takes the inversion to civilisation scale: what if law shipped as structured, versioned, granularly referenceable datasets rather than PDFs? The DocRef platform demonstrated drafting a new API standard from existing regulatory corpus in an afternoon — work that traditionally takes nine months. [[BESSER]] provides a reference point at the formal extreme: in BESSER's "model once, generate everywhere" paradigm, the domain model *is* the spec, and 15 deterministic code generators compile it to working software across multiple stacks. Unlike prompt-driven generation where the translation is probabilistic, BESSER's generators either compile or they don't — making it a useful benchmark for the "how formal does the spec need to be?" question.

### The Economics: The U-Curve and the Accounting Problem

[[AI Agents Need Clear Specs]] provides the missing economic framing. Total cost traces a U-shaped curve against specification completeness. At zero spec, costs are deferred and fragmented — token burn, correction loops, repeated human re-engagement — invisible to management but real. At full formal specification, costs are front-loaded in human effort but back-load almost nothing. The minimum sits at well-structured acceptance criteria or BDD scenarios — not at either extreme, and not at the same point for every task type. Single-agent bounded tasks need structured intent; multi-agent pipelines push the sweet spot decisively right because interpretive drift compounds across handoffs. "The handoff is the product" — every agent boundary needs a contract with schema, invariants, and validation checks.

The key insight is that **spec validation is a distinct cost category** between "write spec" and "run agent," and it is never zero. A spec can fail in invisible ways — internal inconsistency, missing edge cases, being precisely what was written but not what was meant. An agent faithfully executing a flawed spec produces output where you must unwind both code and reasoning. Skipping validation means paying later at higher interest with worse diagnostics.

[[Unit Economics of AI Software]] adds a structural caveat. The zero-marginal-cost property that makes code "disposable to regenerate" is the same property AI erodes. When every user interaction carries real inference cost, "just rebuild it from spec" solves the generation problem but not the operating problem. The spec is durable; the inference bill is recurring. Both can be true, but teams that treat code as disposable without modelling the regeneration cost — which falls every year but is not yet zero — are making an incomplete calculation.

[[Prompt Debt]] sharpens the economics further. The spec must be measurable, not merely written. A prose spec is still the same lossy natural-language medium as a prompt, and suffers the same structural problems: imprecision amplified by probabilistic models, spurious correlations, the need to fight the weights with repetition. The durable spec needs hard edges — evals, metrics, and typed constraints that can score candidate outputs. This is what makes model portability achievable: when behaviour is defined by measurements rather than prose, evaluating a new model takes hours instead of weeks.

### The Process Layer

Several sources address the engineering process that surrounds the spec, independently converging on similar patterns.

[[Compound Engineering]] is the most fully articulated methodology: a four-step loop (plan → work → review → compound) where the compound step — capturing what worked, what didn't, and encoding it into the system — is what separates AI-assisted engineering from traditional development. The 50/50 rule allocates half of engineering time to building features and half to improving the system that produces features. The plugin ships with 26 specialised agents, 23 workflow commands, and 13 skills. The five stages of AI adoption (manual → chat → agentic-with-review → plan-first → idea-to-PR → parallel-cloud) provide a maturity model. Stages 3 and above are where compound engineering begins.

[[Trycycle]] implements plan-strengthen-review loops with a specific architectural insight: every review round uses a fresh agent with no memory of previous rounds, and every planning round spawns a fresh agent, so stale context never accumulates. A hill-climbing process — write plan, send to a planning-issue finder, deepen on the same reviewer if issues are found, hand findings to a fresh planning synthesizer that rewrites holistically — repeats up to five planning rounds and eight review rounds. It is expensive in tokens, thorough in quality.

[[Verbose Deployment]] applies the pipeline approach to deployment: a 10-phase pipeline where each phase is an independently useful composable skill. The pipeline adapts to the project — it detects the test runner, build tool, hosting platform, and browser automation framework rather than assuming them. Self-improvement is built in: each run may reveal a command that fails on a specific platform, and the skill files are meant to be edited.

[[Prefix Effects]] reveals that naming is itself a form of specification. Function names act as "alignment surfaces" that shape all subsequent agent-generated code: `secure_create_user` silently begets bcrypt hashing and password fields; `energetic_create_user` produces 54% more decorators and asyncio usage. These naming effects propagate within semantic domains and weaken across domain boundaries. The implication for spec writing is that naming conventions are not cosmetic — they are part of the spec, and the first code committed to a repository is disproportionately influential.

[[Agentic Engineering at Kenn]] is the production operator's endorsement of the whole loop: Superpowers turns a settled design into a spec, a separate agent reviews it adversarially until it converges, implementation happens in small pieces with roborev verifying each step — and then the spec is deliberately *not* retained in the repo, converted instead into "living architecture documents" that serve humans and future agents. The spec is the product, but only its durable parts survive the build.

### The Social Layer

[[Zero Alignment]] argues that the current focus on individual developer productivity — one person commanding a fleet of agents — misses the fact that software is a team sport. When implementation becomes cheap and fast, the bottleneck shifts from "how do we build it?" to "should we build it?" Existing coordination tools (GitHub, Jira, Linear) were not designed for agentic development: planning is fragmented, implementation accelerates dramatically, and review happens too late. The pull request bears impossible weight as a coordination mechanism. What's needed are integrated environments combining planning, communication, context-sharing, and development — multiplayer, not single-player.

[[speedrift-ecosystem]] sketches a cross-repo coordination layer that partially addresses this. Its control plane observes distributed task graphs across repositories, detects stalls and drift, and plans bounded corrective actions. The architecture separates execution (who runs tasks) from judgment (what to do), with local repositories maintaining authority over their task graphs while a central plane coordinates visibility. This is the spec-as-product thesis applied to the process layer itself: the task graph is the durable specification of what needs doing, and the agent assignments are the disposable execution.

## Where the Sources Disagree

**Descriptive vs. prescriptive specs.** [[OpenSpec]] explicitly defines specs as describing how the system currently behaves; [[Specsmaxxing]] insists specs describe how the system *should* behave, and calls the descriptive approach fundamentally wrong. This is not a minor semantic disagreement. A descriptive spec is a living document that follows implementation; a prescriptive spec is a constraint that drives it. The choice determines whether the spec can serve as a contractual boundary between agents — an agent executing against a prescriptive spec has clear pass/fail criteria; an agent executing against a descriptive one has only approximate guidance.

**Natural language vs. formal semantics.** [[How to Write a Good Spec for Agents]] and [[Compound Engineering]] treat structured markdown as sufficient for production work, with modularity and explicit boundaries as the defence against ambiguity. [[Rewrite All the Code All the Time]] argues this is an intermediate form — useful, but no more the destination than 1960s flowcharts were for programming languages. The claim is that natural language (even structured natural language like EARS or Gherkin) is permanently ambiguous, and only formal languages with mathematical semantics can support truly automatic code generation. [[DSPy — Programming Not Prompting]] occupies a middle position: typed signatures with structured I/O provide hard edges without requiring full formal verification. [[Prompt Debt]] strengthens the formalist case by documenting the pathologies of prose-as-spec in production systems.

**Spec granularity.** [[How to Write a Good Spec for Agents]] argues for modular, per-domain spec files to avoid the curse of instructions. [[The Dark Factory is a DOT File]] presents a single pipeline DOT file as the natural unit. [[Spec-First Development at Benchling]] argues for one unified contract across all platform capabilities. No source provides a framework for choosing among these, and the right answer almost certainly depends on system architecture and team size.

**The spec author.** [[How to Write a Good Spec for Agents]] and [[Compound Engineering]] treat spec writing as a human activity — "nothing beats an organic, pasture-raised, hand-written spec." [[OpenSpec]] leans into AI-assisted spec generation from rough intent. [[AI Agents Need Clear Specs]] proposes a hybrid: an agent produces a first draft from rough intent, a validation agent stress-tests it, and humans review the result. The disagreement is about whether AI can write specs at all, or whether spec writing *is* the act of software engineering and therefore the part that most demands human judgment.

## What's Missing

**Spec testing.** We have tools for testing code against specs ([[Trycycle]]'s review rounds, [[Verbose Deployment]]'s verification phases) but no general-purpose tools for testing specs against themselves — checking for internal contradictions, missing edge cases, or ambiguity before any code is generated. [[AI Agents Need Clear Specs]] identifies agent-mediated validation (draft → adversarial attack → refine) as a partial answer, but this is not a tool; it's a pattern.

**Spec evolution tracking.** [[OpenSpec]] has spec deltas that show what changed. [[Spec-Driven Development]]'s Plumb extracts decisions from diffs. But nobody has built the git-blame equivalent for requirements: who changed this constraint, when, and what was the outcome? Linking spec changes to the system behaviour they produced would close the feedback loop and make specification a falsifiable discipline.

**Formal methods as unrealised terminal state.** [[Rewrite All the Code All the Time]] argues convincingly that structured natural-language specs are an intermediate form, but no current tool bridges the gap from a `feature.yaml` or a PRD to a formal specification with mathematical semantics. [[Lean Software Scaling Laws]] proposes a research programme (measure perplexity scaling across languages) that could quantify the case for formal methods, but has not been run. The claim that formal specs are the destination is logically sound and empirically untested.

**Cross-repo spec management.** Current tools assume specs live within a single repository. [[speedrift-ecosystem]] hints at cross-repo coordination via task graphs but does not solve spec synchronisation across service boundaries. [[Specsmaxxing]]'s dashboard supports tracking a single feature spec across frontend, backend, and microservice repos, but this is unproven at team scale.

**Machine-enforceable specs outside policy domains.** [[Engineering Standards Enforcement at Cloudflare]] demonstrates machine-enforceable specs for organisational policy, but the approach has not been generalised to application-level specifications. Closing the loop from spec to automated enforcement — not just review-before-merge but continuous verification in production — remains open.
