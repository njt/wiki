# MCP and Tool Protocols

An agent is only as useful as the tools it can reach — and, more precisely, as the tools it is allowed to reach. What this set of sources establishes, taken together, is that the transport is not the decisive variable. A tool earns its place by clearing three gates the sources keep returning to: its description must survive the harness's context assembly, its output must be shaped for a model that matches intent semantically and cannot infer what a human would, and its identity and permissions must be settled in advance, because an agent stalls the moment a task needs a human to approve something mid-flight. Where the sources genuinely disagree is on the surface itself — MCP server, CLI, or something else — and the disagreement resolves along one line: the interface the model already knows wins for the tools it already knows, while MCP's stateless HTTP form has won the enterprise case by letting one server reach many clients with no server-side state.

---

## The Argument

### The model selects; the application calls

The foundational correction comes from [[AI Agents In-Depth — Function Calling, MCP and Tool Use Under the Hood]]: an LLM does not call tools. It selects a tool and fills in its parameters; the agentic application makes the actual call. By the same logic, MCP is not a universal format for the JSON you send to models — that "model context" is handled per-provider by SDKs — but a protocol for distributed tool servers (tools, resources, templates, and notifications; the streaming HTTP transport exists because of the notifications). The talk's advice is architectural, not dogmatic: MCP is worth having when it earns its keep, and you don't need it when simple function calling suffices. It also catalogues the failure modes no protocol can fix — the hammer-nail problem (an image generator pressed into QR-code service), tool trust (a wrong calculator answer accepted at face value), non-determinism (same prompt, different output), and security leakage (a card number handed to a tool without hesitation).

### Three surfaces, and where each wins

[[Building Agents for Production Systems with MCP]] sets out the canonical three ways an agent reaches a system. Direct API calls work simply and become an M×N problem at scale. CLIs are lightweight and fast locally but are limited to systems with a shell and do not scale to cloud. MCP is the standardised option — one server, built-in auth and discovery, reaching many clients — and the source argues it becomes "the critical layer that compounds" as production agents move to the cloud. Its design patterns are the sharpest practical guidance in the set: build remote servers, group tools around intent ("fewer, well-described tools consistently outperform exhaustive API mirrors"), and design for code orchestration — Cloudflare's ~2,500 endpoints collapsed into two tools and roughly a thousand tokens.

But the sources immediately pull in different directions, and the divergence is the heart of the theme. [[MCP Is Dead; Long Live MCP]] argues the whole CLI-versus-MCP debate lost its nuance: local MCP over stdio often adds pure overhead over a CLI, while remote MCP over streamable HTTP is a "game changer" and the linchpin of enterprise adoption — centralisation, server-side secrets, telemetry, and standardised delivery of prompts and resources. [[The MCP Gateway Iceberg]] arrives at the same place from the field: Sierra's gateway to 45+ SaaS tools succeeded by "not fighting the weights" — for GitHub and AWS it exposed the native `gh` and `aws` CLIs, which agents already know from training data, rather than proxying through MCP servers. [[Mirage (VFS)]] takes the logic to its limit: if agents already speak bash, make every service look like a filesystem — `grep` across Slack, `cat` a GitHub pull request — instead of inventing per-service tool names. The rebuttal is written into the same source: the filesystem metaphor is lossy, and structured APIs flattened into date-named JSON files force the agent to learn bespoke path conventions. From the CLI side, [[Printing Press]] generates agent-native CLIs (plus a skill and an MCP server) from API specs, betting on local SQLite mirrors and compound commands over raw HTTP; [[10 Principles for Agent-Native CLIs]] supplies the discipline CLIs need — non-interactive by default, `--json` everywhere, errors that teach, safe retries with explicit mutation boundaries, and a compounding tier of consistent vocabulary, three-layer introspection, and two-way I/O, designed agents-first so humans benefit too.

The reconciliation the evidence supports: the surface is not a religion. The model's prior knowledge is the load-bearing variable. Well-known tools work best as the CLIs the model already speaks; the long tail of internal and third-party systems is where the declared, schema'd, discoverable surface of MCP earns its keep.

### The interface is the context window

The most concrete warning in the set is Microsoft's account of how coding agents actually use a technology, which models the whole thing as an information cascade: context assembly, interpretation, tool selection, invocation, response processing, code generation, iteration. Tool descriptions compete for space in the context window before the model ever sees them; selection is semantic matching, not keyword search; and a single over-long response — 3,000 tokens of documentation where 200 would do — is "drag" that pushes the rest of the context out. Two of its lines deserve to travel: "was my tool called?" tells you almost nothing, and error messages are no longer for humans, they are for agents that take them literally.

This reframes everything upstream. The "fewer, well-described tools" pattern is really a context-window strategy, as are tool search (deferring tool definitions until needed) and programmatic tool calling (processing results in a sandbox rather than the context). And it is why [[AI-Ready APIs — Postman AWS Competency]] insists the bottleneck is API readiness, not model selection: an agent cannot infer intent from ambiguous documentation, so an OpenAPI spec that omits auth scopes, misrepresents response schemas, or skips error codes fails silently. PayPal's MCP server worked because it was written so "humans and agents read them the same way," cutting time-to-first-call from an hour to a minute. The same principle, seen from the far end, is the Game Boy hacking exercise that put an MCP server in front of Ghidra: the thing that matters is the feedback loop — give an agent a way to see whether it is achieving its goal, then let it iterate.

### Authentication and identity: the real gating function

If the surface is discoverability, auth is permission to act — and the sources are unanimous that this is where agents stall. [[Authenticating MCPs]] is the most grounded field report: three patterns (OAuth via SSO, no auth, token-in-URL), the discovery that Claude.ai accepts only a bare URL with no custom headers or OAuth initiation, and the real reason auth matters — dynamic tool registration, where the server returns a different tool list per user so only the merchandising team ever sees the stock-level write tool, and tool descriptions themselves can be personalised. [[CSharp MCP Cross App Access]] shows the standardised form of the same need: token exchange (RFC 8693) plus a JWT bearer grant (RFC 7523) lets an agent act on a user's behalf across downstream services without repeated consent.

The spec moved to meet this. [[Bringing MCP 2026-07-28 to Claude]] — the fifth spec release — hardened auth around production OAuth 2.0/OIDC so servers plug into Entra and Okta without workarounds, and vendors such as Figma, Intuit, Netlify, PostHog, Xero, and Zoom cited the stateless core as the enabler for scaling. [[Stateless MCP]] explains why that change was technical and not cosmetic: collapsing initialize-then-call into a single HTTP request removed server-side session state and made MCP deployable as an ordinary web workload. Willison's case is a security case — explicitly declared, auditable MCP tools are easier to reason about than granting an agent arbitrary shell and `curl` access.

Identity runs deeper than OAuth. [[Cloudflare Temporary Accounts for Agents]] and [[Cloudflare Wallets]] answer the same problem — an agent has no stable identity and no native way to pay. Temporary accounts let `wrangler deploy --temporary` provision a 60-minute account a human later claims; wallets give agents API keys with spending caps and allow-lists, on the theory that a small hard limit grants more real freedom than a large soft one. They matter to this theme because every tool ultimately sits behind an account.

### Structured outputs, and the governance that rides on them

What a tool returns is as load-bearing as what it takes. [[OpenAI Structured Outputs]] documents the guarantee side: schemas the model must conform to (strict mode, `additionalProperties` off, everything required), the two forms (function calling versus `response_format`), and the edge cases — incomplete responses, refusals, content filters. But the sources are more interesting where they use schema conformance as governance. [[Malloyyo]] exposes a database to agents through a curated semantic model, routing every query through a restricted loader that blocks `import`, raw SQL, and anything outside the model, and parks the generated SQL on a channel the agent never sees. [[Building an AI Agent in Rails (Ionescu)]] makes the same move at the application layer: encode authorisation into the function calls themselves, so the model gets scoped data without ever holding unrestricted access. [[The MCP Gateway Iceberg]] states the rule for multi-tenant systems — "an agent can't misuse what it never sees" — and enforces it with a multi-pass audit that separates candidate identification from a final model judgement on identity and sensitivity.

### MCP as the front door to whole systems

The fullest expression of the theme is the pattern where MCP is not an add-on but the entire interface to a product. [[InsForge]] and [[Nubase]] are both "Supabase for agents": complete backends — Postgres, auth, storage, functions — whose primary user is a coding agent driving them through MCP tools, with row-level security doing the authorisation at the database. [[DAB]] does the same for databases, generating REST and GraphQL alongside an MCP server. [[Maguyva]] is narrower but instructive: a remote MCP server handing agents a deterministic, pre-indexed "map of the codebase" so they stop hallucinating functions. [[AgentMail]] gives agents two-way email — inboxes, threads, attachments, webhooks — as an API rather than a one-way notifier. [[Control Plane MCP Server]] is the first-party template: a service-account token, curated prompts and resources, and a documented initialisation flow. And [[Agent Host Protocol (AHP)]] is the sibling protocol to watch: not MCP but a JSON-RPC server in the lineage of LSP and DAP that gives multiple clients a synchronised view of agent sessions — a reminder that "tool protocol" is a growing family, not a single standard.

The gateway pattern ties it together. [[The MCP Gateway Iceberg]] shows what it costs to run one surface to many tools at company scale — a single owner, humans validating agent conclusions with an inspector, native CLIs where they win, and a REST extension mechanism for the gaps — and what it buys: plumbing that increasingly improves itself.

### Tools are not knowledge

A recurring correction: MCP grants tool *access*, not *how to reason*. [[Building Agents for Production Systems with MCP]] draws the line — skills teach procedural knowledge, and plugins bundle the two, a data plugin shipping a handful of skills alongside several MCP servers. [[Organizational Intelligence Systems]] sharpens it into a recipe: MCP connects the data, but the skill file is what turns retrieval into analysis, and an expert-review MCP layer grounds the output in named frameworks with citations. Without the skill you get a data dump that is "easy to agree with and difficult to act on."

## Where the Sources Disagree

**CLI versus MCP is a live, unresolved split.** Anthropic's production-systems guidance treats CLIs as a local-only stopgap that "doesn't scale to cloud" and positions MCP as the layer that compounds. [[MCP Is Dead; Long Live MCP]] retorts that this framing is a hype-cycle artefact: local stdio MCP is often pure overhead over a CLI, and the genuine value is confined to remote HTTP MCP. [[The MCP Gateway Iceberg]] lands somewhere else again, finding native `gh` and `aws` beat MCP proxies outright for those two services. The disagreement is substantive because it decides where effort goes; the most defensible reading of the combined evidence is that the axis that matters is local-versus-remote and individual-versus-organisation — but the sources do not actually agree, and neither side offers a controlled comparison.

**Token efficiency is claimed on both sides without a shared measure.** CLI advocates point to training-data familiarity and progressive `--help`; [[MCP Is Dead; Long Live MCP]] counters that chained extraction is not unique to CLIs and cites Vercel's finding that a full doc index in AGENTS.md *improved* performance. Anthropic answers from the MCP side with the ~2,500-endpoints-to-two-tools example. These are directionally useful claims measuring different things.

**Whether MCP is a security win is genuinely contested — by the same author, across time.** Willison once flagged MCP's prompt-injection risks; [[Stateless MCP]] now argues the inverse, that declared tools are safer than shell access. [[Authenticating MCPs]] shows the messy middle, where Claude.ai's URL-only connectors pushed a token-in-URL workaround that violates MCP's own spec, and [[The MCP Gateway Iceberg]] reports agents actively cheating — reading local tokens and falling back to raw HTTP. The honest summary is that MCP's security rests on enforcement, not on the protocol's existence.

## What's Missing

- **Measurement.** [[The MCP Gateway Iceberg]] and the Microsoft cascade both insist "was the tool called?" is nearly useless, but no source supplies a working lift-versus-drag metric or an A/B of CLI against MCP on the same task.
- **The model's prior knowledge is asserted, not verified.** "Don't fight the weights" and "muscle memory for agents" rest on the claim that models know `gh` and `aws` from training — a claim no source tests, and one that erodes as training cut-offs age.
- **Failure modes are catalogued, not solved.** Tool trust, non-determinism, and the hammer-nail problem are demonstrated in [[AI Agents In-Depth — Function Calling, MCP and Tool Use Under the Hood]] but no source offers a remedy beyond observation.
- **The client side is thin.** Auth is documented from the server's perspective; what Claude.ai, Codex, or Copilot *should* do differently is mostly wish-listing.
- **The standards are in motion.** The 2026-07-28 spec is weeks old, [[Agent Host Protocol (AHP)]] is an explicit draft expecting breaking changes, and Cross App Access is young. A page built from these sources is a snapshot of a moving target.
