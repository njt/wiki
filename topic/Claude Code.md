# Claude Code

Claude Code is best understood not as an assistant but as a steering surface: a small, fixed vocabulary of extension points — CLAUDE.md files, rules, skills, subagents, hooks, plugins, and MCP servers — that differ in when they load into context, whether they survive compaction, and how deterministically they enforce. Almost every useful piece of advice in this corpus is downstream of that fact. The craft reduces to three moves: curate what enters a limited and degrading context window; route work to the cheapest model that can do it well; and replace "please don't do that" with a deterministic guard wherever correctness genuinely matters. Where the sources disagree — on hand-curating CLAUDE.md versus letting the model grow it, on a single strong model versus tiered delegation, and on whether prompt-level instruction is enforcement at all — they disagree about how much of that machinery can be trusted, not about the machinery itself.

---

## The Argument

### A harness, not a chat window

The most useful reframe comes from Anthropic's own material. In [[How Claude Code Works in Large Codebases]], the Applied AI team is explicit that "the harness around the model matters more than the model itself": Claude Code navigates a codebase by reading files, grepping, and following references, with no embedding index to maintain, so how well it finds its way is a function of the CLAUDE.md files and skills that tell it where to look. [[Steering Claude Code]] enumerates the vocabulary precisely — seven methods for delivering instructions, each with a different loading trigger, compaction survival, and context cost. The principle that falls out is that a file's placement is a claim about when it should occupy the model's attention: CLAUDE.md loads every session and persists; unscoped rules are mechanically identical to CLAUDE.md; path-scoped rules load only when the matching files are touched; skills load only their name and description at session start, the full body on invocation; subagents run in a fresh context window and return only a final message.

[[Claude Code Mastery]] and the [[Claude Code Cheat Sheet]] supply the mechanical detail — two scopes (a project `.claude/`, committed and shared; a global `~/.claude/`, personal), settings cascading through user, project, and local files. The mental model the corpus converges on is that project files describe the project and global files describe you, and that the folder is a protocol rather than a pile of configuration.

### CLAUDE.md: the highest-leverage file, and the fight over how small it should be

Every source that ranks the components puts CLAUDE.md first, but they disagree on size and authorship, and that disagreement is the most instructive thing in the corpus. [[Writing a Good CLAUDE.md]] argues from instruction-following capacity — frontier models track roughly 150–200 instructions and the system prompt already consumes about 50 — that less is more, that the file should be hand-crafted, and that `/init` scaffolding is a mistake because "CLAUDE.md is too leveraged for automation." [[Steering Claude Code]] sets the target under 200 lines and warns that in shared repositories the file grows as every team appends instructions, whether or not the current task is relevant. [[Tuning Claude Code Into a Better Engineering Partner]] proposes 8,000 characters as a ceiling. Boris Cherny, in [[How Boris Uses Claude Code]], offers the sharpest test: for every line, "would removing this cause Claude to make a mistake? If no, cut it."

Against the hand-curation school sits an almost opposite practice: let the model write its own rules. Cherny calls Claude "eerily good at writing rules for itself," and the Claude Code team maintains CLAUDE.md as a running record of the model's mistakes. These are not quite contradictions — a generated starter is not the same as a grown ledger — but they embody a real split between treating the file as a document you author and as a ledger the system accumulates. A further wrinkle: [[Writing a Good CLAUDE.md]] documents the injected reminder that CLAUDE.md "may or may not be relevant," arguing that non-universal content invites the model to ignore the whole file — which is exactly Rocklin's complaint in [[AI Zealotry]] that CLAUDE.md is "frequently ignored," and his prescription to enforce standards through hooks instead. And [[How Claude Code Works in Large Codebases]] adds a maintenance dimension most sources miss: instructions written for one model "can work against a future one," so teams should review configuration every three to six months.

The same principle generalises beyond code. [[Organizing Claude Code for Product Work]] restates it for product management: past the basics, results stop depending on how well you prompt and start depending on how well you file — a good prompt improves one session, a good file improves every session after it. Its three-folder scheme sorted by rate of change, with CLAUDE.md kept small because "the map points, the files carry," is the context-curation thesis applied to a filing system rather than a codebase.

### Procedures in skills, facts in CLAUDE.md, enforcement in hooks

The second durable principle is that *when* an instruction loads should follow *what kind* of instruction it is. [[Steering Claude Code]] states it plainly: procedural knowledge — deploy runbooks, release checklists, review processes — belongs in a skill, not CLAUDE.md, which is for facts Claude should always hold. Skills achieve this through progressive disclosure: only about 100 tokens of frontmatter load at session start, the full body on invocation, and [[Claude Code Skills System]] documents that invoked skills are re-attached after compaction within a combined budget, oldest first. This is the mechanism behind the context-engineering advice in [[A Guide to Claude Code 2.0]]: agents are "token guzzlers," typical sessions run 200–500K tokens, and skills "solve prompt bloat by loading domain expertise only when needed."

The most important sentence in the corpus, though, concerns enforcement. [[Steering Claude Code]]: "Never do this doesn't work as a prompt instruction." It is followed most of the time and fails under pressure, in long sessions, or under prompt injection; "a real guardrail needs to be deterministic" — hence hooks and permissions. [[How Intercom Uses Claude Code]] is the worked example at scale: a PreToolUse hook intercepts raw `gh pr create` commands, hooks block edits to merged PR branches, and permission prompts feed a classifier that writes GREEN/YELLOW/RED policies back into settings. The prompt states the intent; the hook enforces it. [[Teaching the Agent Our Craft]] makes the same division concrete in a single TDD flow, where a PreToolUse hook confines the test-writer subagent to test directories.

That sentence also casts a shadow over the community skill ecosystem, because most of it is pure prompt engineering. [[Load-Bearing Assumptions]] — a 295-line markdown specification with no runtime code — is the cleanest case, and its own assessment concedes the skill "is all pleading" measured against the determinism of [[Structural Backpressure Beats Smarter Agents]]. The same is true of [[Decision Framework Skill]], [[Socrates Skill]], [[Thought Refiner Skill]], [[A Smart Bear Skills]], and [[Simmer Skill]]: they are restraint mechanisms rather than capability mechanisms. Their value is structure — a four-phase gate, an anti-pattern list, a 38-question framework compressed into adaptive questioning — and they trust the base model to follow it. The corpus is honest that this trust is the weak point.

### Two genres of skill, and the unit of reusable expertise

The marketplace material shows skills consolidating into two genres. One is procedural: [[How Intercom Uses Claude Code]]'s 13 plugins and 100-plus skills, [[SDDW (Spec-Driven Development Workflow)]]'s seven-step spec pipeline, [[Teaching the Agent Our Craft]]'s `/story-writer` and `/tdd-build`, the [[2389 Plugin Marketplace]] catalogue, and [[Trading Ideas — Claude Equity Research Plugin]]'s research framework. The other is decelerative — skills whose whole job is to slow the model down. [[Socrates Skill]] refuses to give direct answers; [[Decision Framework Skill]] never asks all of its questions; [[A Smart Bear Skills]] "refuses to let you off the hook." The observation in [[Decision Framework Skill]] — that in a landscape of acceleration tools, a deceleration tool is a genuinely novel category — generalises: the best skills add restraint and structure rather than new powers, and the corpus's recurring rule is that if you have prompted something twice, it belongs in a skill.

Intercom matters beyond raw scale because it treats the extension points as infrastructure with an owner: session events instrumented into Honeycomb, transcripts auto-classified by Haiku into "missing skill / missing tool / repeated failure / wrong info," weekly jobs fact-checking CLAUDE.md, the plugin marketplace shipped to company Macs via JAMF. [[How Claude Code Works in Large Codebases]] names that owner — an "agent manager," or at minimum a single DRI — and claims that without it "good setups can stay tribal" and adoption plateaus. That is the enterprise through-line of the whole theme.

### Cost, context, and the cheapest model that can do it

The third craft axis is economic. [[A Guide to Claude Code 2.0]] observes that effective context windows are "probably 50–60%" of nominal, and that degradation is why you should not start a complex task halfway through a conversation. [[Tuning Claude Code Into a Better Engineering Partner]] names the symptoms ("context rot") and prescribes fresh sessions and handoff templates. The structural responses recur across sources: `/clear` over `/compact` ([[claude-code-config (Trail of Bits)]], which adds that a session staying within its context budget "produces better code than one that compacts three times to limp across the finish line"); subagents for side tasks whose intermediate results you will never reference again ([[Steering Claude Code]]); and parallel git worktrees, on which [[How Boris Uses Claude Code]] (five local instances plus cloud) and the phone-first setups of [[Domenic Denicola's Agentic Coding Setup]] and [[Claude Code on the Go]] all converge. Worktrees recur often enough that the corpus treats parallel sessions as the most underrated unlock.

On model routing the sources genuinely split. Cherny uses Opus "for everything" on the argument that superior steering and tool use make it faster overall than a smaller model that needs more correction. The opposite case is tiered delegation. [[The Advisor Strategy]] is the formally benchmarked version: a Sonnet executor consults an Opus advisor only at hard decisions, gaining 2.7 points on SWE-bench Multilingual at 11.9% lower cost, and a Haiku executor with an Opus advisor more than doubles its solo BrowseComp score at a fraction of Opus's cost. [[Thrifty (Tiered Delegation for Claude Code)]] is the same shape expressed as a skill — Haiku builds against a Sonnet-written contract, Sonnet patches only on residual failure — claiming roughly 64% cheaper than Opus at equal gate quality. Those numbers come from the vendors and authors and should be read as such, but the pattern they share — a strong model plans and verifies, a cheap model executes — recurs often enough to stand as the wiki's working answer to "how do I spend less on Claude Code."

### Verification is load-bearing, and the model is itself steerable

Cherny's claim that verification is "probably the most important thing" for a 2–3x quality improvement, and the Claude Code team's "give Claude a way to verify its own work," sit at the centre of the product's philosophy. The concrete forms in the corpus: plan mode treated as a design document reviewed by a second, fresh session ([[Claude Code Mastery]]); TDD gates with the RED step confirmed before implementation ([[Teaching the Agent Our Craft]]); judge calibration against score inflation ([[Simmer Skill]]); and assumption verification as a first-class phase ([[Load-Bearing Assumptions]]). [[Dynamic Workflows in Claude Code]] gives the official diagnosis of why a single context window needs this help — agentic laziness, self-preferential bias, and goal drift, especially after compaction — and proposes isolating subagents in their own windows with focused goals. The human's role shifts from writing code to building feedback loops, which is the same conclusion [[A Guide to Claude Code 2.0]] reaches: the system is engineered so that "your task is mainly to use your judgement and prompt it in the right direction."

But there is a dissenting voice, and it deserves its place. [[Guiding Opus 4.8 Back to Sanity]] argues from inside the model that the conduct layer — verification, caution, pushback — is already so heavily weighted, and written in the language of obligation rather than permission, that it displaces the user's original request ("object replacement"). Its repair is not "be more direct," which the model will perform as another virtue, but a structural floor defining when a response is invalid. Set next to the official happy-path material, this is the corpus's one philosophical fault line: the product team wants more verification, and a critic wants less performed vigilance. [[Prompting Claude Fable 5.1]] shows the official response continuing in the concrete register — effort levels do not mean the same amount of thinking across models, scope drift is addressed with "the request is the deliverable," thinking blocks are bound to the exact conversation that produced them — while [[Claude's System Prompt]] documents the leaked Opus 4.6 instruction layer the critic is describing. The two camps are not refuting each other; they are steering at different altitudes.

## Where the Sources Disagree

**A single strong model versus tiered delegation.** Cherny's Opus-for-everything case rests on steering and correction overhead; Thrifty, the advisor strategy, and Domenic Denicola's multi-model review panel rest on measured cost. The routing evidence is better-supported for high-volume mechanical work, while the single-strong-model case is strongest for interactive steering, where correction is the dominant cost.

**Hand-curated CLAUDE.md versus model-grown rules.** [[Writing a Good CLAUDE.md]] says curate by hand and avoid `/init`; the Claude Code team lets the model commit its own rules after mistakes. Reconcilable in principle — a starter is not a ledger — but they imply different theories of what the file is for.

**Deterministic enforcement versus prompt-level instruction.** Anthropic's "never do this doesn't work" stands against a skill ecosystem built almost entirely on prompt engineering, and [[Load-Bearing Assumptions]] names the cost itself. The corpus resolves this by role: hooks and permissions for what must not fail, prompts and skills for what only needs to usually work.

**Prompt for more vigilance, or less.** The product material wants verification; [[Guiding Opus 4.8 Back to Sanity]] argues the model is already over-vigilant and displaces user intent. Unresolved.

**How far to trust the model with the machine.** Domenic Denicola runs both harnesses with no approval prompts and full sudo access, on the grounds that aligned models are not malicious; Cherny and [[claude-code-config (Trail of Bits)]] pre-allow or deny rather than skip, and Nune Isabekyan's phased self-removal only came to trust "allow all" after isolating projects to a single server to shrink the blast radius. The disagreement is velocity against safety, and the corpus does not settle it.

## What's Missing

The efficiency claims — Thrifty's 64%, the advisor's 11.9% and 2.7-point gains, the repeated "2–3x" quality figure — all trace to their vendors or authors; there is no independent measurement in the evidence. The security and supply-chain risk of installing third-party skills and plugins (`npx skills add`, `/plugin`) is barely examined; [[claude-code-config (Trail of Bits)]] and [[CEOS (Claude + EOS)]] are the exceptions, and CEOS's refusal to build a dashboard with a write token unless a password is present is the one genuinely careful posture in the set. Evidence about the model's actual instruction layer is a leak (Opus 4.6) and a paywalled critique (Opus 4.8) — partial and version-specific. Version churn is visible even within a single publisher's pages: one `.claude/` folder anatomy describes `commands/` as a separate mechanism, and its own comments already flag that commands have been merged into skills per the official docs, while skill and plugin counts drift between a publisher's README and its repository. Anything numeric here goes stale quickly. Enterprise-managed deployment — MDM, managed settings, managed marketplaces — is named but thin, and the desktop app's behaviour of killing sessions when the client closes is mentioned only once, as a complaint.
