# Agent Orchestration

Agent orchestration is actually three problems bundled together: agent-to-agent coordination, human-to-agent coordination, and state persistence across both. The first has a dominant answer — hierarchical role separation — discovered independently by teams building at radically different scales. The second is converging on task boards and dependency graphs as the coordination surface. The third has settled on a shared set of primitives — file-based memory, worktree isolation, atomic task claiming, ephemeral sessions with persistent state — that matter more than any particular orchestration framework. What nobody has solved yet is cross-agent learning: agents in current orchestration systems do not learn from each other's discoveries.

---

## The Argument

### Flat Coordination Fails; Hierarchy Works

This is the most robust finding in the evidence. [[Scaling Long-Running Agents]] documents Cursor's experiments: flat self-coordination with shared files and locking reproduced every pathology of poorly-managed human teams — agents held locks indefinitely, avoided difficult tasks, and twenty agents delivered the effective throughput of two or three. The fix was planner/worker/judge separation: planners map the codebase and generate tasks recursively, workers execute without coordinating with each other, and judge agents evaluate completion. [[How Hightouch Built Their Long-Running Agent Harness]] arrived at the same conclusion independently, finding that DAG-based agent frameworks failed for open-ended marketing tasks and that separating planning from execution — with an `update_plan` tool allowing the agent to modify its approach mid-task — was essential. [[Agent Swarm Model Economics]] provides the economic confirmation: Cursor's old flat-coordination swarm produced 68,000 commits of thrash, over 70,000 merge conflicts, and 54 crates where 9 sufficed; the new tree-structured swarm produced under 1,000 conflicts and converged on the answer at roughly one-eighth the cost.

The hierarchy takes different shapes depending on the task. [[maestro]] uses PM/Architect/Coder roles with the Architect reviewing but never writing code — preventing the failure mode where the designer papers over design mistakes during implementation. Coders terminate between stories for forced context freshness. [[Gas Town's Agent Patterns]] uses Mayor/Polecats/Witness/Refinery with the Mayor as the single human interface and the Refinery handling merge conflicts creatively. [[Cord]] provides five primitives (spawn, fork, ask, complete, read_tree) for agents to build task trees dynamically at runtime rather than having developers predefine the structure — the spawn vs. fork distinction (clean slate vs. sibling context injection) is the key innovation. [[The Grid — Agent Identity Architecture|The Grid]] uses domain-based handoffs encoded in identity files: each program has a distinct domain (Patch: coordination, Index: research, Rez: building, Crit: verification), and handoffs are deterministic ("hands to X when Y") rather than model-discovered. This is coordination through specialisation, not hierarchy.

[[Building an Advanced Agentic Harness]] provides the cleanest decomposition of why hierarchical separation works: Planner/Worker/Critic role separation splits a single confused prompt into three narrow agents with single contracts, each independently testable and swappable. The orchestrator becomes deliberately thin — it assembles context, gets a plan, executes with budget-charging callbacks, verifies with pressure-aware degradation, and re-plans on missing-information errors rather than retrying blindly. [[TDD Coordinator (Corazonn)]] implements the same principle as a Claude Code slash command, with a mandatory Rule of Two: every work product — test and implementation alike — is reviewed by a different agent before it counts as done. [[Mole]] applies the same split to deep research, but pushes the judge out of the peer role: planner/executor/verifier are pipeline *stages* with independently attributable spend, and the verifier's confidence is *computed* from the claim graph rather than judged by a model.

The autonomous loop pattern — [[Ralph]], [[Fleet of Agents (sermakarevich)]], [[Fleet Supervisor (sermakarevich)]] — is a degenerate case of hierarchy: a single agent iterating through a task list, with the human acting as planner. [[Ralph]] is a bash `while` loop calling `claude -p` with a fix plan on disk; its power is that "nothing in the agent changed" — the loop is a dumb re-invocation mechanism over a structured task file. [[Fleet of Agents (sermakarevich)]] walks through five steps from a single agent writing task context to disk, through an on-disk TODO queue, a bash loop for unattended execution, parallel agents with atomic task claiming via beads, and finally agents that can stop and ask questions when blocked. [[Fleet Supervisor (sermakarevich)]] is the production-grade version: ~4,700 lines of Python managing a pool of agent subprocesses with pluggable coder backends, config hot-reload, context-pressure detection, automatic retry, worktree isolation, a web UI, and MCP-based human-in-the-loop. [[What Ralph Wiggum Loops Are Missing]] maps the graduation path from freeform markdown loops to structured dependency tracking, arguing that Ralph and more sophisticated coordinators are stages on the same learning curve, not competitors. [[Loop Engineering]] generalises the pattern: designing systems that prompt agents autonomously, rather than prompting agents directly — with automations, worktrees, skills, plugins, sub-agents, and persistent state as the six essential components.

### The Coordination Surface Between Humans and Agents

Kanban boards have emerged as the dominant human-agent interface, but the evidence suggests they are a local maximum, not the final answer.

[[Managing Agents via Kanban Boards]] (Geoffrey Litt) is the clearest articulation: a Notion board where a "blocked" checkbox visually signals when an agent needs human input, and a CLI tool blocks execution until the human responds. The workflow emerged from use, not from design — the author describes gradually building it up step by step, calling it "malleable software." [[ralph-ban]] implements the same idea as a TUI with vim navigation, five columns, SQLite backing, and 2-second polling sync across CLI, hooks, and TUI sessions. [[weft]] is the web-native version on Cloudflare: Workers for routing, Durable Objects for state, Workflows for durable agent loops with automatic checkpointing, and all state-mutating actions requiring human approval. [[vibe-kanban]] tried to be the comprehensive solution — 10+ coding agent support, inline diffs, PR generation, dedicated workspaces — and is now sunsetting. The lesson: tooling for managing agents is a thin layer on top of existing workflows; the value accrues to agents and platforms, not middleware.

[[Mission Control — Bhanu's 10-Agent Squad on OpenClaw]] is the best-published production multi-agent reference architecture: 10 specialised agents with file-based memory, heartbeat loops every 15 minutes (staggered to avoid cost spikes), a Convex-backed Kanban board with six stages from Inbox to Done, and three autonomy levels. The practical advice is hard-won: start with 2–3 agents, stagger heartbeats, and build a UI above three agents because logs and chat alone become unmanageable.

Beyond flat boards, [[workgraph]] provides a persistent task graph stored as JSONL on disk where "agents can come and go, the graph remains." Claims, handoffs, evidence, failures, and human judgment points are all first-class operations. [[poietic]] extends this with an explicit methodology ("graph work") and organisational form (public-benefit corporation), treating the dependency graph as the durable artifact and agents as ephemeral workers — all processes publicly visible and inspectable. [[speedrift-ecosystem]] takes the idea furthest: a central control plane that observes distributed task graphs across repositories, detects stalls and drift, and dispatches corrective actions under policy, maintaining full audit trails. The module names — coredrift, specdrift, datadrift, archdrift, yagnidrift — reveal the scope of ambition.

[[Tracker]] formalises workflow orchestration as a static DAG defined in `.dip` files, with conditional routing, checkpoint/resume, parallel fan-out, and sentinel-protected audit trails. Its design deliberately optimises for correctness and auditability over runtime flexibility — parenthesised condition expressions are rejected at parse time rather than silently mis-evaluated, and the engine fails loudly on unknown outcome statuses. [[barnstormer]] builds living product specs as kanban cards with event sourcing and phase-gated workflows, producing portable DOT, Markdown, and YAML artifacts.

[[Zero Alignment]] frames the meta-problem that all of this sits inside: existing orchestration tools are single-player interfaces. When implementation becomes cheap and fast, agreeing on what to build becomes the bottleneck. One developer with 24 agents and zero alignment produces chaos regardless of the orchestration pattern. "Software is not made by one person in a vacuum. It's a team sport."

### Context Management IS Orchestration

Across every source, the same set of techniques recurs. These are not implementation details — they are the orchestration primitives themselves.

**File-based memory.** Agents write their state to disk because the model forgets everything between runs. [[Mission Control — Bhanu's 10-Agent Squad on OpenClaw]] uses five explicit layers: session memory (JSONL conversation logs), working memory (WORKING.md, read first on wake), daily log memory (YYYY-MM-DD.md), long-term memory (MEMORY.md, curated key facts), and identity memory (SOUL.md and AGENTS.md). [[Ralph]] uses a fix plan file plus an AGENT.md that the agent updates with discovered best practices, creating institutional memory across loops. [[Fleet of Agents (sermakarevich)]] uses TASK.md, PLAN_AND_PROGRESS.md, and FINDINGS.md per task — "you stop being the agent's memory." [[Loop Engineering]] puts it bluntly: "The model forgets everything between runs so the memory has to be on disk."

**Worktree isolation.** Running multiple agents in the same directory causes file conflicts — even when agents edit different files, a shared git index means commits can include each other's uncommitted changes. [[Parallel Coding Agents Guide]] makes the case: git worktrees give each agent its own working directory, branch, and staging area while sharing the git object store, taking seconds to create and costing minimal disk space. [[Orca]], [[Agent of Empires]], [[Dorothy]], and [[Fleet Supervisor (sermakarevich)]] all implement worktree isolation. [[Loop Engineering]] identifies worktrees as one of five essential loop components.

**Ephemeral sessions with persistent state.** [[Gas Town's Agent Patterns]] describes agents whose sessions are "disposable by design" — identity and tasks stored in Git, sessions killed and fresh ones spun up, with "seancing" to let new agents ask predecessors about unfinished work. [[maestro]] terminates coders between stories for forced context freshness. The pattern appears across the board: the agent process is cheap and replaceable; the task state is the durable artifact.

**Atomic task claiming.** When multiple agents pull from the same queue, race conditions are inevitable. [[Fleet of Agents (sermakarevich)]] and [[Fleet Supervisor (sermakarevich)]] solve this with beads (`bd`), a SQLite-backed task database where `bd update --claim` atomically assigns a task to a claimer. The supervisor's spawn loop stays dumb — ~15 lines of bash or ~45 lines of Python — while the atomicity guarantee lives in the queue. Beads also manages dependencies, preventing tasks with unfinished parents from being picked up.

### The Economics Are Now Measurable

[[Agent Swarm Model Economics]] provides the first detailed cost breakdown of coordination quality. Cursor's old flat swarm cost $10,565 in API spend and produced 68,000 commits (mostly thrash). Their hierarchical hybrid — Fable 5 planner with Composer 2.5 workers — cost $1,339, with the entire worker fleet at $411. Workers carried at least 69% of tokens in all runs, but planner tokens dominated cost. The centrepiece experiment — implementing the SQLite spec (835 pages) in Rust without access to source code, test suites, or the internet, graded against sqllogictest — passed ~2/3 of the suite in the first hour, and every model mix eventually reached 100%. The thesis: few moments in a large task genuinely require frontier intelligence; split the work accordingly.

[[AI Agents Need Clear Specs]] adds the specification dimension: in multi-agent pipelines, underspecification is not sloppy — it is expensive. Every agent boundary where specification is loose introduces interpretive freedom that compounds across handoffs. "Strongly typed interfaces between agents" — schema, invariants, validation checks — are not bureaucratic overhead; they are the cost of preventing drift from cascading into hallucination at machine speed. The total cost of specification traces a U-shaped curve: minimal spec has near-zero upfront human effort but high downstream costs; full formal spec front-loads human effort but back-loads almost nothing. The minimum sits around well-structured acceptance criteria, not at zero.

### Background Monitoring as Distinct from Coordination

[[Pi Observers]] introduces a pattern orthogonal to the coordination taxonomy: persistent observer agents that watch but never participate. Observers trigger on lifecycle events (before_agent_start, turn_end, tool_execution_end, agent_settled), propose short advisories, and a reconciler gates what reaches the main agent — deduplicating by fingerprint, enforcing a per-turn advisory budget, and ranking by priority. Unlike workers in a planner/worker/judge hierarchy, observers never do the work; they are a quality-control layer running alongside it. This is monitoring, not coordination, and it is a pattern few orchestration systems implement.

### Cross-Harness Orchestration

A small but significant thread in the evidence asks whether orchestration should span different agent harnesses, not just different models within one harness. [[bb — The Agent Orchestrator as Normalizer]] provides the most principled adapter architecture: a two-shape model where in-process protocol adapters handle JSON-RPC-native providers like Codex, and bridge-process adapters host SDK or ACP clients for Claude and Pi. Each adapter owns its event translation, and the runtime never interprets provider-specific wire content. The architecture normalises each harness's traffic into a shared thread-event model. [[acpx]] provides one CLI surface wrapping 16+ coding agents over the Agent Client Protocol, with persistent sessions, prompt queueing, cooperative cancel, and a flow runtime for multi-step TypeScript workflows. [[Warp Agent CLI]] delegates across different harnesses — Claude Code, Codex, and others — as interchangeable workers, built on a terminal multiplexing architecture that manages PTY connections with a layer of indirection between agent and shell.

## Where the Sources Disagree

**Static vs. dynamic decomposition.** [[Tracker]] and [[maestro]] define workflows upfront — the DAG is authored before execution, which enables validation, simulation, and linting. [[Cord]] lets agents discover task trees at runtime via spawn and fork primitives, which handles tasks where decomposition is not known in advance. [[Tracker]]'s `manager_loop` handler partially bridges this gap with iterative supervision, but the child pipeline structure remains static. The trade-off is genuine and task-dependent.

**Centralised vs. per-repo coordination.** [[speedrift-ecosystem]] argues for a central control plane supervising work across repositories — observe, prioritise, plan, execute, record. [[workgraph]] argues for per-repo task graphs where each repository maintains local authority. This mirrors the monorepo vs. polyrepo debate and probably has the same answer: it depends on organisational structure.

**Kanban simplicity vs. graph sophistication.** Flat boards work for independent tasks. Complex dependencies, parallel execution, and conditional branching need a DAG. Most real projects contain a mix of both, and no tool handles the transition from one to the other gracefully.

**Human approval vs. bounded autonomy.** [[weft]] requires human approval for all state-mutating actions. [[speedrift-ecosystem]] allows bounded autonomous action under policy ("can restart safe services, cannot rewrite unrelated local work without a trace"). The right answer depends on blast radius and reversibility, but no general framework exists for deciding which approach to use for which operations.

**The orchestrator as product vs. as feature.** [[Agent Orchestration for the Timid]] concludes, after testing five orchestration tools, that Claude-native skills and slash commands beat all of them — the author plans to "lean harder into Claude-centric features for orchestration than introduce the overhead of any of these orchestrators." But [[Dorothy]], [[Orca]], [[Agent of Empires]], and [[klaw.sh]] are full products with real user bases. [[Loop Engineering]] suggests the answer is that both are correct at different stages: practitioners find patterns first, then patterns become platform features — as when Claude Code shipped built-in task management and dependency tracking.

**Cross-harness orchestration: bridge or permanent need?** [[bb — The Agent Orchestrator as Normalizer]] and [[acpx]] invest heavily in protocol translation and normalisation. The open question is whether this is a temporary bridge as harnesses converge on common protocols like ACP and MCP, or a permanent architectural need as harnesses differentiate rather than converge.

## What's Missing

**Cross-agent learning.** Agents in orchestration systems do not learn from each other. If Worker A discovers a debugging pattern, Worker B starts fresh. [[Loomkin]]'s Keeper processes with failure memory and shared discoveries via PubSub are the closest thing to shared learning, but it is built on Erlang/OTP ([[Process-Based Concurrency BEAM OTP]]) — the BEAM's actor model, with isolated processes, message passing, supervision trees, and per-process garbage collection, is what every agent framework ends up reinventing ([[Distributed Systems]]). The pattern has not been implemented in the mainstream Python/TypeScript agent ecosystem.

**Coordination cost measurement.** Only [[Agent Swarm Model Economics]] provides hard numbers comparing coordination approaches. Without measurement, comparing orchestration patterns remains impressionistic. [[Building an Advanced Agentic Harness]] proposes multi-dimensional budgeting — tokens, tool calls, wall time, and estimated dollars tracked simultaneously with a single `pressure()` scalar driving graceful degradation — but this is a design proposal, not a deployed measurement system.

**Failure recovery at the orchestration level.** [[Building an Advanced Agentic Harness]] contributes the cleanest error-classification primitive: `classify_error()` maps failures into four categories — transient, tool misuse, missing information, policy violation — and the recovery policy follows from the class. Transient errors get exponential backoff with jitter; missing-information errors trigger informed re-planning; policy violations halt immediately. Most orchestration systems approximate this with ad hoc retry loops. [[Loomkin]]'s self-healing teams via OTP supervision trees are the most principled answer, but Python-based systems mostly retry or give up.

**Multi-player orchestration.** Every tool in the evidence is a single-player interface. [[Zero Alignment]] identifies the gap: software is a team sport, but orchestration tools treat it as a solo activity with AI assistants. GitHub Next's Ace prototype points toward multiplayer sessions backed by cloud microVMs, but nothing is shipping.

## Also on This Theme

- [[Omnigent]] — open-source infrastructure attempting cross-harness agent orchestration, mentioned alongside [[bb — The Agent Orchestrator as Normalizer]] and [[Warp Agent CLI]] as part of the same movement
- [[Orchestrator - Worker Skill]] — a single skill file combining orchestrator and worker roles rather than separating them, trading separation of concerns for reduced coordination overhead
- [[Agent-Building Playbook (Ramparte)]] — an open pattern language that names the same findings as transferable pearls: 16 orchestration patterns (workflows-vs-agents, single-threaded-default, three-primitives, match-topology-to-the-work) each with an explicit "when NOT to" contraindication
- [[Paperclip]] — an open-source "company runtime" that layers org charts, per-agent budgets, board-level governance, and multi-company isolation on top of any heartbeat-capable agent; one of the few tools attacking the governance and cost-control gaps named above rather than the coordination patterns that already have answers
