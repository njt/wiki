# Software Engineering Craft

The fundamentals of software engineering — how to design an API that fails gracefully, how to recognise accidental complexity, how to keep a system running after it ships — do not change when the tooling layer is rewritten by agents. If anything, they intensify. When an LLM can generate code ten times faster, it generates bad code ten times faster, and the cost of getting the architecture wrong is amplified rather than amortised. The craft of software engineering has always been less about *writing* code than about the judgment calls that shape what gets written: what to build, how to handle failure, when to simplify, and how to keep systems running once they are deployed. The 57 sources surveyed here converge on a single claim: as code generation becomes commoditised, the scarce — and therefore valuable — skills are taste, specification, operations, and the willingness to say no.

## The Argument

### The Discipline of Failure

If there is one thread that runs through every source on API and system design, it is that failure is not an edge case. [[Designing a Passively Safe API]] stakes the strongest position: after any failure, the system either completes exactly once or lands in a visible terminal state — no duplicate charges, no orphaned side effects. The engineering is concrete: idempotency keys, transactional outbox and inbox patterns, recovery-point checkpointing between atomic phases, and an explicit `is_transient` boolean in every error response so that callers — human or agent — can distinguish a retryable network blip from a permanent refusal.

[[Idempotency Is Easy Until the Second Request Is Different]] deepens this: the easy version of idempotency remembers that a key was seen; the useful version remembers what the key meant. The hard cases are concurrent retries racing each other, partial local success with an unknown downstream state, and a retry whose canonical command differs from the original — same key, different amount. The article's checklist is a working engineer's reference: hash the validated command, not raw JSON bytes; use `ON CONFLICT DO NOTHING` rather than check-then-insert; treat stale `IN_PROGRESS` as API-visible behaviour that requires recovery ownership, not silent re-execution. The same discipline extends beyond HTTP: queue consumers, outbox publishers, and notification workers all face the same duplicate-suppression problem, and the fix is the same — make the side effect durable before sending it.

[[Good API Design]] adds the strategic layer: Goedecke argues that boring, immutable APIs win. Product value matters more than interface elegance; cursor pagination beats offsets at scale; GraphQL is a complexity tax paid disproportionately by the backend. Where Albaugh gives the mechanical engineering of safe APIs, Goedecke gives the design philosophy — never break downstream consumers, version only as a last resort, and remember that many API consumers are not professional engineers and need simple authentication that works. [[Cashpoints Partners API]] is a real-world case study in all of this: a loyalty-points POS API that uses a lock-then-commit flow as a poor man's two-phase commit, carries field warnings as scar tissue from past integration failures, and has a refund mechanism that explicitly handles the clawback problem when points have already been spent.

Two type-system arguments reinforce the same instinct from the code level. [[Parse Don't Validate]] argues that the difference between parsing and validation is whether the check result is preserved in the type system: a validator throws away what it learned, a parser returns a refinement of the input type that carries the proof forward. Push parsing to the boundary and the interior becomes total and composable. [[Type Safety Back and Forth]] names the same move differently: push responsibility backward by demanding stricter argument types that *cannot* fail — `NonEmpty a` instead of `[a]` — and the uncertainty concentrates at the system's edges, where JSON decoding and database reads live. The rest of the system becomes pure, total, and simple. Both become more important in an agent world, where code generators make the same composition mistakes humans do but faster and with less judgment.

At the architecture level, the same tension between service and imposition plays out in the choice between libraries and frameworks. [[Libraries over Frameworks]] traces Petricek's 2015 argument: libraries (called by your code) compose, explore, and test better than frameworks (which own the control flow and call you). The distinction is structural, not cosmetic — two frameworks each demanding to own the main loop cannot coexist, while two libraries can be called from the same program without conflict. [[Linux Kernel Design Patterns]] finds the same pattern in operating-system design, where Neil Brown diagnoses the "midlayer mistake": well-intentioned abstraction layers that harden from optional services into mandatory intermediaries, accumulating special cases as they try to serve every driver's needs. The antidote is libraries over imposed midlayers — a lesson that maps cleanly onto every framework-versus-library debate since.

[[Better Error Messages]] completes the picture from the user-facing side: Wix's "Errorgate 2021" audited 7,643 error messages and found the company was "more like that friend who loves to gossip but doesn't pick up the phone when life gets hard." The five rules — say what happened, say why, reassure, give a way out, help fix it — apply to CLI error messages, API responses, and agent failure states equally. Generic errors are not a content problem; they are a development and product problem.

### The War on Complexity

If the discipline of failure is the positive craft — here is how to build things that don't break catastrophically — the war on complexity is the negative craft: here is how to stop building things you do not need.

[[Grug Brain Developer]] is the folk-wisdom companion to this entire conversation. Its central thesis — complexity is the apex predator of software development, and the best weapon against it is the word "no" — has become a meme in engineering culture, but the meme works because the observation is true. The essay's advice to wait for natural "cut points" to emerge before abstracting, to prefer simple APIs for common cases over configurable APIs for all cases, and to put code on "the thing that do the thing" (Locality of Behaviour) is the same instinct that runs through every source on simplicity.

[[Elements of Code]] stakes the philosophical position: "Writing comprehensible code is what allows us to be wrong in correctable ways." The goal is not perfection; it is correctability. Perfect software is impossible given constantly changing requirements and evolving contexts. The practical virtue is making code that can be corrected and adapted. This is the direct antidote to [[Cognitive Debt]]'s diagnosis: if AI-assisted velocity exceeds human comprehension, the response is to invest in comprehensibility — to write code that a future engineer (or agent) can reason about without holding the entire system in their head.

[[Simplicity in the Age of AI-Assisted]] makes a subtler argument: LLMs do not change what good programming looks like, but they enable simplicity by making it cheap to rebuild systems without inherited complexity. The real unlock is demolition, not construction. When a human identifies unnecessary complexity — the five linguistic layers a sticky-header toggle accretes, the Kubernetes cluster that exists to remember one boolean — an LLM can regenerate the alternative in minutes. The hard part remains the human part: recognising which complexity is essential and which is inherited. LLMs, trained on millions of repositories that perpetuate complexity, will not question your architecture; they will replicate it, faster.

[[Systems Ideas That Sound Good]] is the essential companion: Sinofsky catalogues eight engineering patterns that sound like simplification and fail roughly nine times out of ten. Pluggability, over-abstraction, DIY async, deferred security, data synchronisation, cross-platform builds, escape-to-native — each shifts complexity to where it is less visible rather than eliminating it. The core lesson is to solve problems from first principles rather than defaulting to familiar patterns that are prone to failure.

[[Nobody Knows How Large Software Projects Work]] names the uncomfortable truth at the other end of the scale: complexity at scale is inherent, not a staffing or process failure. The system is unknowable not because of poor engineering but because of successful product development — every "fiddly, awkward feature" (self-hosting, organisational controls, localisation, regulatory compliance) multiplies against every other feature. Static documentation fails because the system changes faster than anyone can write it down. The team's core function becomes answering questions about the system through code reading, experimentation, and trial-and-error testing.

Two architectural positions stake out the terrain between "keep it simple" and "accept the complexity." [[Microservices for the Benefits, Not the Hustle]] argues that microservices are about changeability, not scalability — the real prize is hard repo boundaries that enforce cohesion in ways monoliths allow to erode under time pressure. Choreography over orchestration, one database schema per service, services sized for two-week rewrites. [[Make the Easy Change Hard]] inverts Beck's maxim: sometimes the right move is to refactor the architecture first, even when that makes the immediate change harder, because the resulting structure makes every subsequent change easier. The author's SimKube refactoring — replacing `Arc<Mutex<TraceStore>>` with message-passing through channels — took weeks in "the refactoring mines" but disentangled concerns that would have compounded indefinitely.

[[Locality of Behaviour]] gives this conversation a concrete design heuristic: the behaviour of a unit of code should be as obvious as possible by looking only at that unit of code. Gross distinguishes between inlining implementation (bad) and surfacing behaviour declaration (good), the same way a function call declares intent without inlining the function body. The distance-as-severity rule — behaviour on a parent element is a mild violation, behaviour in a separate file is severe — gives teams a gradient to argue about rather than a binary. In the agent era, LoB gains new weight: coding agents read code linearly and do not benefit from IDE tooling the way humans do, making source-level locality a practical requirement rather than an aesthetic preference.

[[What Color is Your Function]] diagnoses a language-level source of accidental complexity: when a language splits functions into async and sync, composition breaks because async infects every caller upward through the callstack. Nystrom's metaphor — red functions can only be called from red functions — remains the clearest explanation of why async/await feels like a hack even when it works. The only genuine solution is multiple independent callstacks that can be switched between, as Go, Erlang, and Lua demonstrate. The coloring property of a language becomes a multiplier on agent code quality: agents make the same composition mistakes humans do, but faster.

[[The Lindy Effect]] offers a probabilistic argument for betting on craft fundamentals over novelty: the longer something non-perishable has survived, the longer it can be expected to continue surviving. SQL, Unix, and core algorithms persist while JavaScript frameworks come and go. It is a heuristic against shiny-object syndrome, not a proof — but in a field where the half-life of a front-end framework is measured in months, it is a useful guardrail.

### Operations as Craft

[[The Future of Software Engineering is SRE]] makes the sharpest argument in the entire corpus: when code generation is trivially easy, keeping software running reliably is the scarce skill. "The first 90% to get a working demo is easy. It's the other 190% that matters." Uptime guarantees, defect identification and recovery speed, proactive issue detection, secure data handling, failure recovery without data loss — these are what separate toys from services. The article cites Feynman's "computer disease": people enjoy tinkering with automation but dread the responsibility of reliably running systems at scale indefinitely. With AI democratising code writing, competitive advantage shifts to organisations that master operational reliability.

[[Platform Engineering End-to-End]] is the practitioner's field guide to building that operational foundation. Cavallin's synthesis of Fournier and Nowland's book plus his own GCP experience covers the full lifecycle: the five pillars (curated product approach, software-based abstractions, metadata registries, serving the median developer, operating as foundation), the team composition (hire for customer empathy — "a platform engineer who cannot sit with a frustrated app developer is in the wrong job"), the migration playbook (rearchitect inside the existing platform, never ask every team to do it themselves with a clipboard), and the priority order from zero. The DORA 2025 data drives home why this matters: platform quality now predicts whether AI tooling produces value or chaos. A bad platform makes AI tools amplify chaos; a good platform makes them amplify throughput.

[[Anomaly Detection]] provides a beautiful example of operational tooling done at the right level of sophistication: Welford's algorithm for running mean and variance in constant memory, hourly bucketing in a KV store, three independent statistical checks (total count z-score, percentage spike, per-user anomalies), and a 2-sigma threshold with a minimum of three data points before alerting. No machine learning, no configuration, no training phase. Just math. The entire detection engine fits in a single file. This is the right level of sophistication for most monitoring needs — and a rebuke to the instinct to reach for a neural network before understanding the data.

[[Before Reading Code]] shows that operational thinking begins before you read a single line of code. Five git log commands — churn hotspots, contributor ranking, bug cluster detection, velocity trending, crisis pattern detection — provide diagnostic insights into a codebase's health and history. A 2005 Microsoft Research study showed that churn-based metrics predicted defects more reliably than complexity metrics alone. Minutes of work that save hours of misdirected reading.

### The Agent-Era Inflection

The sources do not agree on everything, but they agree on this: AI-assisted development is not a faster horse — it changes what the job *is*. The disagreement is about what comes next.

[[Cognitive Debt]] names the most dangerous gap: code production velocity now exceeds human comprehension velocity, creating a deficit in organisational understanding that remains invisible to traditional productivity metrics until system failures expose it. Code works, tests pass, features ship — the deficit exists only in the minds of engineers. Three failure modes cascade from this: production code becomes increasingly dangerous over time, incidents require investigation of unmaintained systems built by engineers long gone, and junior engineers never develop architectural intuition, depleting future leadership pipelines. "The system is optimising correctly for what it measures. What it measures no longer captures what matters."

[[Write Only Code]] accepts this diagnosis but draws a different conclusion: the solution is not to slow down but to change the confidence mechanism. Rather than human code review as the final safeguard, teams should track "code reading coverage" metrics and define an acceptable "Slop Radius" — how far unintended behaviour can spread before detection. Engineers transition from authors and reviewers to systems designers and constraint writers, shaping intent over implementation, defining interfaces and failure modes, and building systems that remain correct without full comprehension. The historical parallel is the mid-2000s cloud transition: removing one bottleneck (hardware procurement) moved the bottleneck to the next one (developer velocity). AI is now removing the code-writing bottleneck; the bottleneck moves to specification, verification, and operational resilience.

[[When the Target Keeps Moving]] provides the best empirical data on what this looks like in practice: a 32-day AI-accelerated project that grew from 254 tasks to approximately 1,400, with roughly 109 new tasks discovered for every 100 completed. The key metric is the discovery-to-delivery ratio — are you converging or diverging? "A project isn't a pile of known tasks being shovelled from 'not done' to 'done.' It's also a discovery engine." The three-phase model (first useful thing, deliberate discovery, denominator stabilisation) is the most practical framework available for managing AI-accelerated work. By the end, 64% of remaining tasks involved operational readiness, agent instruction, human testing, simulation analysis, and load validation — not product features.

[[Spec-Driven Development]] and [[Spec-First Development at Benchling]] attack the specification side of the problem from complementary angles. Breunig's triangle model treats specs, tests, and code as a feedback loop: implementing code generates decisions that update the spec, which defines what tests and code need to be written. Benchling's approach is to define each object once, in a way that any platform capability can consume — the integration point moves from per-platform capability implementations to a single shared schema. Both converge on the same insight: the spec is not a document written before coding begins; it is a living artifact that implementation improves.

[[The Coming Need for Formal Specification]] pushes this further: as generation costs plummet while review costs lag, systematic tooling for the mismatch between code and intent becomes necessary. Congdon engages with Kleppmann's prediction that AI will make formal verification go mainstream — the seL4 microkernel required 200,000 lines of Isabelle proofs for 8,700 lines of C — and envisions a future where English specs decompose into TLA+ models, critical components are verified in Rocq, and the remainder is LLM-audited for spec conformance. The bottleneck shifts from writing code to specifying what code should do.

[[dotnet Slopwatch]] is a concrete artifact of this transition: a tool that detects "reward hacking" behaviours where AI coding assistants take shortcuts — disabled tests, suppressed warnings, empty catch blocks, arbitrary delays masking timing issues. The tool's existence is itself evidence that agent-era craft requires new kinds of verification, not just faster generation.

[[Book OCR Project Report — Structured Workflow Runtime and Manual PDF Repair]] is a masterclass in what agent-era engineering looks like when done well: a custom Go workflow runtime providing durable execution with steps, queues, leases, and retries; OCR via vision models with structured JSON output contracts (never freeform Markdown); deterministic rendering and validation owned by Go, not the model; and a day-long manual PDF repair loop that found five distinct failure classes and encoded each as a validation check so it would never need to be found again. The central insight — model output should stop at a structured boundary, not freeform text — is a craft rule that applies far beyond OCR.

### Project Management and Decision-Making

The craft of running a project does not become obsolete when the people doing the implementation are agents; it becomes more important, because coordination costs do not scale down just because generation costs do.

[[How I've Run Major Projects]] distils Ben Kuhn's experience into six principles: focus (six-plus uninterrupted hours daily for crisis projects), detailed planning for victory (concrete step-by-step plans reveal timing risks early), fast OODA loops (multiple daily touchpoints, ranked open-questions docs, frequent reorientation), overcommunication (repeat key information more than feels natural), break off subprojects (beyond roughly ten people, delegate project management itself), and have fun. The key insight: "projects are information-constrained, not execution-constrained." Information processing is the work, not a tax on it. Direction matters more than magnitude — a slower team on the right goal outperforms a faster team misaligned.

[[14 More lessons from 14 years at Google]] adds the organisational layer from Addy Osmani's experience: start meetings with explicit asks ("approve, choose, unblock, or inform"), treat reliability as a product feature with error budgets making tradeoffs explicit, and recognise that recurring heroism is a failure mode — "if one person saving the day is a recurring pattern, that's a failure mode rather than a badge of honour." The fastest team Osmani ever worked with was not the one with the best programmers; it was the one where decisions happened in hours instead of weeks. Decision speed is a greater organisational risk than code speed. Team interfaces fail because of unclear boundaries, not communication gaps — undefined contracts require endless meetings.

[[Capturing Why Engineering Decisions]] documents the persistent problem that the above advice tries to solve: the *why* behind engineering decisions is buried in undocumented PRs, old Slack threads, and the heads of departed engineers. The HN thread that produced this page is a 64-comment referendum on documentation strategies. The consensus that emerges: documentation survives when it lives next to the code (file-level headers, per-folder READMEs); ADRs work as point-in-time RFCs but die when treated as documents to maintain; and the new hire — who still remembers what it is like not to know — is in the best position to write the docs. LLMs invert the economics: for the first time, good docs pay dividends because LLMs love reading them and keeping them current.

[[Lovelace]] represents one answer to the tooling question: instead of managing projects in a separate SaaS tool, it puts tickets, docs, ADRs, and agent session records directly in the repo as Markdown-plus-YAML files, where coding agents already live. The Tauri app and Claude Code MCP server are secondary to the files themselves — the bet is that colocation with the code is what makes project state durable.

### The Craft in Specific Domains

Several sources examine craft through the lens of a specific technology stack — not because the lessons are stack-specific, but because craft is best learned by watching someone who knows a domain deeply.

**C# and .NET.** Seven pages form a thin but instructive cluster. [[Dapper Performance Trap]] documents the NVARCHAR vs VARCHAR implicit conversion that defeats SQL Server indexes — 176× slower on a million-row table, completely invisible in the C# code. The fix is two lines (`DbType.AnsiString`, matching size) and a comment explaining why, because the next developer will "simplify" it back to an anonymous object and reintroduce the problem. This is craft at its most granular: knowing the invisible coupling between your ORM's type mappings and your database's query planner. [[Span-First CSharp — Designing Around SpanT]] advocates for `Span<T>` as the canonical parameter type for parsers, serialisers, and protocol codecs — zero-allocation views over contiguous memory that let CSV parsing run roughly 4× faster with no garbage-collection pressure. The article is equally clear about when *not* to use spans (object graphs, low-volume call paths, broad public library surfaces), which is what separates a design guide from advocacy. [[Performance Optimization Loop]] provides the structured methodology: monitor production data → profile → benchmark a baseline → apply small targeted changes → re-benchmark → document → validate in production. Applied to a real OpenTelemetry SQL sanitizer, the loop reduced allocations by 86% and CPU time by 46% across seven stages. Gordon's AI-assisted optimisation experiment is a useful data point: Copilot produced two insane suggestions and one hallucinated API, but seven were plausible and worth testing — each manually verified with benchmarks. [[ASP.NET Core Authentication Internals]] turns out to be a masterclass in interface design: the entire system sits on a four-method `IAuthenticationHandler` interface, the base class bakes in forwarding logic so policy schemes can route requests dynamically, and the two-channel `AuthenticationProperties` pattern (serialised `Items` for round-trip state, in-process `Parameters` for everything else) is worth studying even if you never write C#. [[C# DateTimeOffset Format Selection]] is a single-concept guide to picking timestamp formats at API boundaries, organised around the only criterion that matters: what survives the round trip. Its core insight — RFC 3339 is the narrow, interoperable profile of ISO 8601 that most APIs actually mean — applies far beyond C#. [[Installing VS Compilers From Commandline]] solves the "skip Visual Studio, install just the compiler" problem with a CLI tool that parses Microsoft's component manifests and downloads only what is needed — a reminder that toolchain management is itself a craft problem.

**Deep tool knowledge.** [[Assorted less(1) Tips]] and [[Git Rebase for the Terrified]] represent a dimension of craft that is easy to dismiss as trivia and impossible to do without: knowing your tools deeply enough that they become extensions of your cognition rather than obstacles to it. The `less` tips — filtering with `&pattern`, marking with `m` plus a letter, piping marked regions to external commands with `|a`, following mode with `+F` — are collectively a masterclass in the pager as an interactive programming environment. Brethorst's rebase guide makes the case that the fear is irrational: the absolute worst outcome of a rebase gone wrong is deleting your local clone and starting over, which costs nothing. The real skill is not memorising commands but understanding the underlying model — what a rebase actually does, why maintainers want linear history, and when `--force-with-lease` is the right hammer.

[[Having a Creative Practice as a Programmer]] reframes tool mastery and experimentation as a parallel track that runs alongside productive output — the programmer's equivalent of a musician's daily practice. The author defines creative practice as a habit, more about practice than results, dedicated to exploring craft without the pressure of shipping. The advice is concrete: time-box two pomodoros before work, build quick studies that sidestep full infrastructure, preserve artifacts to compare across weeks and months, and recognise that pedestrian tasks (emptying an inbox, upgrading credential management) are part of the practice too. The observation that JavaScript "unlocks a creative dimension in my brain" while Rust induces frustration is not a language critique — it is a practical note about the relationship between tool friction and creative flow.

**Testing and data quality.** [[Frozen Test Fixtures]] diagnoses a common Rails failure mode: shared fixtures that become untouchable because changing them breaks scores of unrelated tests. The fix is to test the property, not the data — `assert_includes` rather than `assert_equal` for collection membership, testing that a list *is sorted* rather than matching a hardcoded array. [[Correct by Construction]] applies the same instinct to data quality: build datasets correct by construction through a whitelist of anchors (entity IDs), attributes (data values with NULLs and sentinels stripped), and links (relationships with verified cardinalities), rather than attempting to validate flawed data retroactively.

**Communication and documentation.** [[Common Diagram Mistakes]] catalogues seven anti-patterns in architecture diagrams — unnamed resources, unconnected elements, "master" diagrams that try to show everything, conveyor-belt syndrome where linear flow misrepresents real round-trips, meaningless animations, fan traps that collapse distinct communication paths through a shared broker, and the assumption that AI can generate quality diagrams from source code. Most diagram failures are communication failures, not artistic ones.

**Domain-specific craft.** Three sources show how deep craft manifests differently in different domains — the principles are the same, the specifics are not. [[What You NEED to Know Before Touching a Video File]] is a field guide to video encoding: quality is fidelity to source, not resolution or file size; remuxing changes the container without touching the encoded stream (fast and lossless), re-encoding decodes and re-encodes (lossy and time-consuming); x264 and x265 remain the best encoders for quality; and frame interpolation is simply bad — "there's not even any nuance here this time, just don't do it." [[How HTML Changes in ePub]] documents how ePub uses XHTML (the XML spec, not HTML5) with "positively historic" rendering engines in e-readers that cannot handle modern CSS pseudo-classes — a reminder that platform constraints are real and "unlearning" conventional knowledge is part of the craft. [[WebRTC Is the Problem]] is a protocol-level critique from an engineer who built WebRTC SFUs at Twitch and Discord: the protocol is fundamentally wrong for voice AI because its aggressive packet dropping for real-time latency, its ~8 RTT connection setup, and its port-binding architecture that breaks under NAT and roaming make it a poor foundation. The alternative — QUIC with WebTransport — offers single-RTT connection establishment, connection migration via CONNECTION_ID, and stateless load balancing. The article is a case study in knowing when the conventional solution is the wrong one.

### Bugs, Debugging, and the Taxonomy of Failure

[[A Field Guide to Bugs]] is not merely taxonomy — it is craft knowledge encoded as literary performance. Stephen Diehl's 30-plus named species (Bohrbug, Heisenbug, Mandelbug, Schrödinbug, Rubber Duck Bug, and the closing Omega Bug that "was here before the field guide") do what good taxonomies do: they give engineers a shared vocabulary for experiences they previously struggled to describe. The article is half computer-science folklore and half sharp diagnosis of LLM-era failure modes — the Hallucination Bug ("the test suite was designed by the cognitive process that produced the bug"), the Vibe Coding Bug (immaculate code, wrong in a way no single revision introduced), and the Recursive Fine-Tuning Bug (by generation twelve, "the model explains concepts that never existed, in authoritative language"). The Comment Lie — "`// always uses UTC`" paired with code using local time, written in 2009 by someone promoted twice at a different company — earns its place as a species because every experienced engineer has encountered it.

### Maps of the Territory

Several sources attempt to catalogue the craft rather than practice it. [[Software Engineering Practice Atlas]] is the most ambitious: 4,654 entries across five practice maps (Engineering, Engineering Management, Product Management, Project & Program Management, Research) and 25 field guides, each card stating what a practice is, why it matters, how to apply it, and when not to. It is AI-generated and uneven, best treated as a map to explore rather than gospel. [[Patterns.dev]] covers design, rendering, and performance patterns for web apps across vanilla JavaScript, React, and Vue — descriptive rather than prescriptive, "a catalogue of patterns for increasing awareness rather than a checklist." [[Igor Schwarzmann Design Systems]] is a dead reference site, irretrievable, remembered here for who built it and what it stood for: design systems as organisational strategy, not component libraries. [[The Pragmatic Summit]] — Gergely Orosz's inaugural curated conference in February 2026 — brought together 28 practitioner speakers across Build, Frame, and Lead tracks, including Martin Fowler and Kent Beck revisiting "the mistakes engineers keep repeating," Simon Willison on engineering practices that make coding agents work, and Thomas Dohmke revealing Entire.io. The conference's existence is itself a data point: craft knowledge is moving from blog posts to curated events as the field recognises that scattered advice does not cohere into a discipline.

## Where the Sources Disagree

**Is comprehension still required?** [[Write Only Code]] argues that the future is systems nobody reads, with alternative confidence mechanisms replacing human review. [[Elements of Code]] argues that comprehensibility is the primary virtue because someone has to debug the code when it breaks. [[Cognitive Debt]] warns that unread code produces unmaintainable systems and junior engineers who never develop architectural intuition. This is not a disagreement that further evidence will resolve — it is a bet about whether the "Slop Radius" can be contained tightly enough, and whether the debugging problem can be automated before the comprehension deficit causes a catastrophe. Both sides cite the same historical precedent (cloud removing hardware as a bottleneck) to draw opposite conclusions about what happens next.

**Simplicity vs. useful complexity.** [[Simplicity in the Age of AI-Assisted]] says rebuild simpler — the unlock is demolition. [[Systems Ideas That Sound Good]] says most "simplification" is complexity displacement — the complexity moves to where it is less visible. [[Nobody Knows How Large Software Projects Work]] says complexity at scale is inherent and irreducible. The resolution is not a synthesis but a gradient: simplify where you can, accept what you must, invest in observability for everything else. But the gradient is subjective, and two engineers looking at the same system will draw the line in different places.

**Discovery vs. delivery.** [[When the Target Keeps Moving]] argues that cheap delivery means you should invest in discovery — the hard part is learning what you do not know yet. [[How I've Run Major Projects]] argues for focus and disciplined execution. Both are right for different project phases, but the disagreement is real: a team that over-invests in discovery never ships; a team that under-invests ships the wrong thing. Croll's three-phase model (first useful thing, deliberate discovery, denominator stabilisation) is the most practical resolution, but it requires judgment about when to switch phases.

**Microservices: the right default?** [[Microservices for the Benefits, Not the Hustle]] explicitly argues for microservices as a default architecture, even without scaling pressure — the benefit is changeability through enforced cohesion. [[Nobody Knows How Large Software Projects Work]] implies that distribution multiplies the comprehension problem. [[Systems Ideas That Sound Good]] warns that "making things asynchronous" fails nine times out of ten. The wiki does not resolve this — the sources are in genuine tension, and the right answer depends on team size, system complexity, and organisational structure.

## What's Missing

**Agent-era incident response.** How do you debug a system where the implementation was generated by three different models across six months, and nobody wrote the code? [[The Future of Software Engineering is SRE]] raises the question; no source answers it with operational specifics. The "Slop Radius" concept from [[Write Only Code]] is a framing, not a practice.

**Operational patterns for agent-generated systems.** We have operational patterns for human-written systems (SRE, chaos engineering, observability). We do not have patterns for systems where the code changes faster than anyone can understand it, where the failure modes include hallucinated logic that passes generated tests, and where the person who "wrote" a function was a different model version than the person debugging it.

**Quantitative craft metrics.** [[Before Reading Code]] uses git data for codebase health diagnostics. [[Cognitive Debt]] names the comprehension deficit. But no source provides a metric for "is this codebase getting more or less comprehensible over time?" or "what is our current cognitive debt?" The problem is named; it is not measured.

**Craft at the boundary between engineering and product.** Several sources touch on this — [[Good API Design]] notes that product value trumps interface elegance, [[14 More lessons from 14 years at Google]] discusses reliability as a product feature — but none explores it systematically. When an LLM can build either version of a feature in an afternoon, the hard question is not "can we build it?" but "which version should we build?" That question is under-explored.

**The economics of craft investment.** [[Performance Optimization Loop]] demonstrates that structured performance work pays off, but does not address the organisational question: how do you convince management to invest in proactive performance work, or error-message audits, or fixture unfreezing, when the payoff is invisible until something breaks? The incentive structure rewards feature delivery over operational reliability, and the sources name the problem without solving it.
