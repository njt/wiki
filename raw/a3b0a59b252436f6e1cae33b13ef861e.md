The speaker's falsifiable claim is that building apps this way in Grist beats other vibe-coding platforms because Grist's spreadsheet-database architecture (references instead of queries, built-in UI, access rules, self-contained file format) eliminates deployment, infrastructure, and permission-auditing work that other app builders force the agent — and you — to do.

Key points

Two build modes demand two prompting styles. "From prompt" (no existing data) calls for a carefully structured three-part prompt: use case and data, important views and workflows, user permissions. "From spreadsheet" (migration) calls for a planning phase before any building.

Let the model do domain research. For the electrician work-order tracker, the speaker didn't name fields at all — instead asking Claude to "perform desktop research to find typical workflow statuses and safety procedures," leveraging LLM training rather than micromanaging.

Planning phase as audit trail. For migration, Claude is told to produce a markdown plan file ("Do not build it in grist yet") broken into three stages — data structure and formulas, views, permissions — which the speaker keeps as a record of "what did we say we were going to build? What did we actually build?"

A test for spreadsheet complexity: could you explain the spreadsheet to someone else without confusing yourself, and do you have more hidden sheets than unhidden sheets? Either yes means build in stages.

Agents overbuild. Left unchecked on the brewery spreadsheet, Claude added purchasing workflows and pages that were never in the original Excel — the reason for the harness.

Five reasons vibe coding in Grist works: (1) the app is live immediately, no deployment step; (2) human or bot can edit — "anything that it can do, I can do"; (3) everything is built to fit — linking tables is a reference column, "one line of code"; (4) the app is a self-contained file you can copy, template, download, roll back; (5) access rules are auditable in the UI by the business owner.

Access rules are enforced server-side, even inside custom widgets — viewing as "Marcus" filtered his data even in the HTML/JS widget Claude wrote.

Custom widget code lives in the document's metadata — no more manually uploading HTML/JavaScript; the MCP connector also injects instructions (dummy data, Grist-native styling, light/dark mode) the agent wouldn't follow on its own.

Claude applied database best practices unprompted — collapsing separate fermentables/hops/flavorings sheets into one ingredients table with a category column.

Tools, practices, and methodologies

Grist MCP connector — connects Grist to AI agents (Claude demonstrated; any agent works); calls Grist's internal tools to build documents directly rather than just advising. Free Grist plan includes 3,000 MCP calls; Pro for more.

Three-part prompt structure for greenfield builds — use case and data, important views and workflows, user permissions; be deliberately "robotic" on permissions to avoid confusion.

Two-phase migration workflow — planning phase (markdown plan file, three stages, explicitly forbid building yet) then building stage-by-stage with feedback between stages for complex spreadsheets.

Structure-only download — download a Grist document's structure without data to let agents work on templates without exposing sensitive data (Pierre's tip, endorsed by the speaker).

"View as" feature — impersonate users in the UI to audit access rules in seconds; the speaker calls it essential when "your head will roll if the wrong person sees the data."

?style=light URL parameter — strips navigation and creator panels for embedding widgets in iframes or saving screen space.

Import from Airtable — brings over references, simple formulas, even choice colors; complex formulas come over as text descriptions.

Widget collapse trick — drag a widget upward to shrink it to a linked full-screen-openable tile that retains filtering.

Snapshot awareness — Claude can read snapshots (read-only) to recover from mistakes, e.g., "hey, you did it better in this other snapshot."
