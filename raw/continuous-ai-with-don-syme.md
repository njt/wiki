Continuous AI is a distinct category alongside CI and CD. CI establishes that software works (deterministic). CD establishes that software is correctly deployed (deterministic). Continuous AI covers the subjective activities — bug triage, documentation, performance improvement, duplicate detection, issue labeling — that need to run on a permanent, operational basis within a bounded context, but don't have binary pass/fail outcomes. Don is explicit: "We don't say we're putting AI into your CI. No, no, no, no, no, no. We don't do that at all. It's CI CD, they stay as they are."

The shift that matters is from individual productivity to situated, collaborative automation. The AI industry has a blind spot: massive focus on chat modality and individual productivity, but not enough on automation that lives in a shared, bounded context (the repo) where teams collaborate. Continuous AI is about folding AI into the change/event-driven rhythm that already governs how software teams work.

Bounding context is non-negotiable. AI "goes off the rails unless you're situated inside some bounded context." The repo is the natural boundary — it defines what inputs the automation gets, what outputs it can produce (a PR, an issue), and has a firewall around it. This is why CI/CD is the right analogy: people already understand bounded automation in that form.

The repo is a site of production, not just a factory. Don pushes back on the factory framing as too narrow — a film studio is also a site of value production. Factories imply identical repeating tasks on a pipeline; AI use is broader. But the factory analogy works when there are repeating tasks coming through.

CI/CD's organizational model is the template for AI automation. When an organization adopts CI/CD, it tells developers: "here's a place called the repo, where we give you permission to automate within that bound." Developers get limited cloud resources (compute, network, storage) without asking the cloud team for a machine or a budget. Continuous AI should go the same way — empower maintainers closest to the software to decide how to use AI, with cost centers and policies flowing up to the organization.

Guardrails determine speed. "The stronger the train tracks, the faster you can run." In automated mode, you must be able to sleep at night. Information flow integrity matters: don't make private repos accessible to agents in public repos, don't triage issues from untrusted contributors by default, force opt-in for risky actions.

Human review is the bottleneck — so the factory creator's job is to equip the reviewer. Don's framing: "My job as a factory creator is to deliver high quality pull requests where the reviewer is equipped with all the information they need." This means evidence (before/after CI timings), risk assessment, trade-offs, and quality gates that throw away trash before it reaches the human.

Cost control is the missing feature in the harness discussion. GitHub Agentic Workflows has explicit cost controls — per-run cost visibility, budgeting, and a model comparison feature ("examination testing") that runs the same work with multiple models simultaneously to see which performs best. Don: "It's the thing that's missing from the harness discussion."

One workflow that does multiple things beats an agent zoo for production use. Don's collaborator Pelle de Hallio runs "Pelle's Agent Zoo" with dozens of workflows to explore the space. But for maintaining real repos, Don prefers a single broad-spectrum workflow (his is called RepoAssist) for conceptual simplicity, cost control, and attention management across multiple repos.

3. Tools, Practices, and Methodologies

Continuous AI (concept)
The category of subjective, AI-driven activities (triage, labeling, documentation, performance improvement, duplicate detection) that need to run on a permanent, operational basis within a bounded context. Use it to frame AI automation as a discipline parallel to CI/CD — not embedded in it.

GitHub Agentic Workflows
GitHub's implementation of continuous AI — intelligent automation running coding agents (Copilot CLI, Claude Code, Gemini CLI) with strong guardrails inside GitHub Actions. Now in public preview. Use it as the default in-repo automation platform; bring your own model and key. Open source.

RepoAssist (pattern/workflow)
Don's personal broad-spectrum repository assistant workflow — labels issues, does first-response research, optionally implements PR fixes (never auto-merges). Use it as a model for consolidating multiple automation tasks into one workflow for simpler cost control and attention management.

Pelle's Agent Zoo
A documented collection of 20-40 agentic workflow patterns (code improvement, performance, styling, etc.) published on GitHub's workflow site. Use it as a pattern library to explore what's possible — but Don cautions that maintaining a zoo of separate workflows is a maintenance burden for production use.

Side repo pattern
Running automation in a separate "side repo" that targets a monorepo or other repos. Use it to control who can write and run the automation (separate auth boundary) while keeping the target repo clean.

Examination testing
A feature in GitHub Agentic Workflows that runs the same work with multiple models at the same time, picks the first model's result, but logs comparative performance. Use it to evaluate which models work best for your specific workflow. Critical detail: must run simultaneously because models will find each other's answers in the shared ledger if run sequentially.

Goal chasers (continuous goal chasers)
A workflow pattern that runs once daily, making incremental progress toward a defined goal (e.g., accessibility bugs), producing one PR per day. Use it for enterprise-scale backlogs where a slow, cooperative cadence is preferable to dumping 1,000 PRs at once.

Skill libraries
Reusable markdown-based skill definitions that can be imported into agentic workflows, either by reference or by checking them into the repo. Use them to share automation logic across repos — the execution stays in the workflow, the skill spans repos.

GitHub CLI extension (GHAW)
The CLI extension for GitHub Agentic Workflows, which itself has agentic workflows checking its terminal output styling. Example of dogfooding: the tool improves itself.

Quality gate stacking
The practice of building as many automated quality gates as possible before the human review point — CI green, evidence attached, risk documented. Use it to reduce human review fatigue; the factory's job is to never send trash to the reviewer.

Automated pushes to PR branches
GitHub allows automated pushes to pull request branches (especially those created by the automation itself). Use it for loops that fix failing CI — find red PRs, make extra pushes to get them green — without auto-merging.

4. Unanswered Questions and Omissions

What happens when human review can't scale? Don insists the human is always in the loop at the PR merge point. Guy pushes back hard: "That's not a sort of, that's an untenable sort of destination, right?" Don acknowledges the pressure toward auto-merge but doesn't offer a path beyond "we're being responsible." The talk doesn't address how teams already drowning in PR review should handle a step-change increase in PR volume.

How do you evaluate agentic workflow quality itself? Guy asks directly: how do you know your automation isn't degrading over time, especially with self-improving loops? Don deflects to "the human is in the loop" and mentions GitHub Actions' built-in limitations on self-modifying workflows. He doesn't address evals, metrics, or how to define "correct behavior" for subjective automation beyond vibes.

Cross-repo and org-level context is acknowledged but unsolved. Don admits "we have work to do on making sure that the repo is not the only notion of context that works effectively." Multi-repo collections, org-level automation, and enterprise-spanning workflows are raised as real needs but left as future GitHub work. The monorepo coalescing pressure — driven by agents needing cross-repo context — is identified as a tension but not resolved.

Security model is sketched, not specified. Don mentions information flow integrity, not exposing private repos to public-repo agents, and defaulting to ignoring untrusted contributor issues. But there's no discussion of prompt injection via issue bodies, secret exfiltration through agent tool calls, or what happens when an agent with write access to a repo is fed malicious content. These are the actual attack surfaces for agentic workflows.

No discussion of what happens when agents produce subtly wrong work that passes quality gates. The factory analogy assumes trash is obviously trash — "the can's got a crush on it." But AI's failure mode is plausible-looking-but-wrong work that passes CI, passes style checks, and gets merged. This is the hardest review problem and it's not addressed.

No data on merge rates, cost per PR, or time savings. Don mentions "70-80% PR merge rates" for some zoo workflows and "cents to a dollar" per run, but there's no systematic data on whether continuous AI actually improves outcomes, what the ROI is, or how it compares to human-only workflows at scale.

The relationship between continuous AI and loop engineering is left fuzzy. Guy explicitly asks whether these are different words for the same thing. Don says "some of those conversations are orthogonal" and that loop engineering concepts "can flow very freely" into continuous AI — but doesn't draw a clear boundary or explain when you'd use one framing vs. the other.

No mention of testing, test generation, or test quality. For a talk about software factories, the absence of any discussion about how AI-generated changes are tested — beyond "CI green" — is notable. Who writes the tests for the agent's output?
