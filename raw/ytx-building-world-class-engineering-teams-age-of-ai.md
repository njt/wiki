AI-native teams start with mindset, not just tools. Rajeev stresses that teams must “really believe in doing AI native work” and working with agents. Some Atlassian teams still code traditionally, but AI-native ones write “zero lines of code” manually—everything is orchestration of agents.

The bottleneck is shifting left and right of code. With coding becoming “free,” the hard parts become planning/specking (left of code) and deployment/incident resolution (right of code). Atlassian is re‑tooling the entire SDLC around this.

Roles are collapsing into overlapping Venn diagrams. PMs are becoming product engineers, designers are becoming design engineers, and the distance between PM, design, and engineering is shrinking. Thomas: “The product manager is becoming a product engineer and the designer is becoming a design engineer.”

Productivity gains are real, but the point is creativity, not headcount reduction. Rajeev reports PRs per engineer up 89%, issue cycle time down 42%, 51% of security vulnerabilities caught by agents. Yet the goal is “what can you create now with AI that you could not create before” and “how can you have that much more joy?”

Context is the magic ingredient for agent performance. Atlassian’s RoboDev beats Devin on SWE‑bench by leveraging the “teamwork graph”—who works with whom on which PRs and Jira issues—to give agents rich context.

Distributed teams get a new advantage from agents. Thomas argues agents act as always‑available “pairing partners” for brainstorming, code review, and research, evening out the competitive disadvantage of remote work versus in‑office whiteboarding.

Engineering leaders can code again, and span of control will increase. Rajeev sees leaders reconnecting with code via agents. He predicts flatter orgs with managers having 20–50 direct reports, fewer management layers, and less pure “leadership management.”

Token costs invert traditional budgeting. Thomas warns that as developers get more productive, flexible token costs skyrocket, creating pressure to slow down some developers—a problem large‑company managers must solve with finance.

Coding is fun again. Both speakers emphasize that agents remove drudgery (build errors, unit tests, boilerplate) and bring back the joy of building, especially for hobby projects and rapid prototyping.

Tools, practices, and methodologies

RoboDev (Atlassian’s internal coding agent): A coding agent used across the entire SDLC—code generation, code review, CI/CD, incident resolution. Built on Anthropic’s model but beats Devin on SWE‑bench by leveraging Atlassian’s “teamwork graph” for context. Used by all Atlassian engineers.

Teamwork graph: Atlassian’s internal knowledge graph that maps who works with whom on which PRs and Jira issues. Provides rich context to agents, dramatically improving their output quality.

Confluence for left‑of‑code speccing: Engineers and PMs put intent, specs, and comments into Confluence; agents read those comments and run RALPH loops to generate code. Shifts the artifact of record from code to the spec.

Loom (video messaging): Used to express intent and thoughts via video, which is then fed into AI agents to produce better artifacts. Part of Atlassian’s push to move beyond text‑only specs.

Cursor Composer: Mentioned by Thomas as a tool he used to generate a cookie policy implementation in a React app in seconds. Example of an agent that handles non‑coding tasks quickly.

Devin (Cognition AI’s agent): Referenced as a coding agent that some CTOs use overnight to build features, then check in the morning. Symbol of how leaders are re‑engaging with code.

Replit / Lovable: Low‑code/no‑code platforms that PMs, marketers, and assistants are using to build prototypes and automate parts of their work, blurring the line between builders and non‑builders.

Codex Mac app (OpenAI): Thomas used it to build three native Mac menu‑bar apps in SwiftUI without looking at the code. Demonstrates the speed and accessibility of agent‑assisted development.

AI‑native SDLC: Atlassian’s holistic approach: ideation → coding → deployment → production, all augmented by agents. Not just a coding assistant but a rethinking of the entire lifecycle.

Verification over inspection: Instead of line‑by‑line code review, teams are shifting to verifying inputs/outputs, guardrails, and system behavior. Code review bots may eventually negotiate directly with coding agents, removing the human bottleneck.

Forcing yourself not to look at the code: A practice Thomas observes among AI‑native developers: they start greenfield projects by voicing intent through prompts and reasoning, deliberately avoiding reading the generated code to build the skill of managing agents.

Unanswered questions and omissions

How do you manage token costs at scale without stifling productivity? Thomas flags the inversion where more productive developers burn more tokens, forcing managers to potentially slow them down. No solutions are offered—just the problem statement.

What happens to junior engineers when senior engineers become “masters of agents”? The talk focuses on up‑leveling existing engineers, but doesn’t address how juniors learn fundamentals, develop taste, or gain the context needed to effectively prompt and verify agents.

How do you ensure quality and security when humans stop reading code? Rajeev mentions shifting to verification of inputs/outputs, but the specifics of guardrails, testing strategies, and what “verification” actually entails in an agent‑driven pipeline are left vague.

What about the legacy codebase problem? Rajeev admits agents struggle with complex projects on old codebases and that “we’ll get there very soon,” but no concrete approaches for bridging that gap are discussed.

How do you prevent the “Homer Simpson car” when agents auto‑merge and auto‑deploy? Thomas raises the risk of feature bloat without human curation, but the talk doesn’t explore process changes (e.g., how product management adapts) to prevent this.

What are the implications for team morale and culture when roles collapse? The blurring of PM/design/engineering is presented as positive, but potential friction, ownership confusion, or resistance from specialists isn’t addressed.

How do you handle the language and communication barrier when prompting in English? Thomas notes that non‑native speakers struggle to describe features in English, making markdown‑based prompting a “nightmare.” No mitigation strategies are offered.

What does the career ladder look like in a world with fewer managers and flatter orgs? Rajeev says “managers and leaders, it’s a little tougher” and there might be fewer of them, but doesn’t sketch what advancement looks like for those who don’t want to stay pure ICs.

How do you maintain institutional knowledge when code is generated and not deeply understood? The shift away from reading code line‑by‑line raises questions about long‑term maintainability and debugging when the original human intent is buried in prompts, not in the code itself.

What about the ethical and legal dimensions of AI‑generated code? No mention of IP ownership, licensing, compliance, or bias in generated code—elephant‑in‑the‑room topics for any organization adopting agents at scale.
