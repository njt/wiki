# “My Credentials, Please”: Detecting Filesystem Capability Laundering in MCP Servers at Scale

###### Abstract

The Model Context Protocol (MCP) standardizes how AI agents invoke external tools. MCP servers expose tools through a declared contract consisting of a name, description, and argument schema. In typical local deployments, client-side approval of a tool call grants the underlying server process broad host filesystem permissions rather than restricting it to the declared operation.
We study the resulting vulnerability class, *filesystem capability laundering*, where attacker-steered arguments cause a tool to access sensitive host files outside its declared contract and deployment scope.
We analyze this capability gap across three layers: server-category screening (L1), per-tool contract analysis (L2), and bypassable path-validation checks (L3).
We design MCP-FSD to catalog MCP servers, infer least-privilege boundaries per tool, plant credential fixtures outside those boundaries, and evaluate exploitability and sandbox containment via paired dynamic execution.
Across 21,097 MCP servers from nine registries, 787 of 4,806 triaged servers (16.4%) exhibit filesystem capabilities despite non-filesystem functional classifications. Dynamic three-case validation confirms 150 vulnerable instances under tested sandbox policies. Coordinated disclosure yielded 13 security advisories, including two CVEs in Anthropic’s Git MCP Server.

###### Keywords:

Model Context Protocol Filesystem Security Sandbox Static Analysis AI Agent Security Dynamic Validation Tool-Use Security## 1 Introduction

The Model Context Protocol (MCP) [17] has become the standard interface through which AI agents invoke external tools, data sources, and services. An MCP server implements tools that a client discovers through tools/list and invokes through tools/call. The tool’s name, description, and argument schema form its *declared contract* [28].

MCP supports client-provided filesystem roots [27], and tool definitions can include output schemas and behavioral annotations [28]. However, the MCP specification delegates per-tool filesystem enforcement entirely to individual server implementations or host environments. The security question is whether attacker-influenced arguments can steer a tool’s effects beyond the scope justified by its contract and deployment context.

Path-traversal flaws are documented in the agent harness itself: Claude Code’s prefix-match bypass [6] and symlink-following [5] let crafted arguments escape the harness’s intended scope. For locally launched servers, the code that accesses files instead runs in a separate server process. While the client’s approval prompt gates execution based on declared arguments, the spawned server process executes with ambient host filesystem permissions. An ostensibly benign operation can therefore access and expose host credentials through ordinary tool output. We call this vulnerability class *filesystem capability laundering*: an out-of-scope filesystem capability is exercised under the guise of an innocuous tool contract.

We examine the gap at three layers. At the *server-category* layer (L1), we compare inferred filesystem capability flags against the server’s functional classification (primary_type). Because non-filesystem servers (e.g., memory or code development) often perform legitimate local persistence, category mismatches serve as coarse screening signals. At the *tool-name* layer (L2), a tool’s narrow operation can reach files beyond its intended scope: git_add can stage an out-of-repository file whose contents a later diff returns (CVE-2026-27735, §5.2). At the *defense-bypass* layer (L3), an existing path check can be defeated: the Filesystem MCP Server’s string-prefix check admitted sibling directories sharing the allowed prefix (CVE-2025-53110 [30]). Figure 1 illustrates the staging-and-diff disclosure sequence.

We build MCP-FSD (Filesystem Scope Detection), a framework that catalogs MCP servers across registries, discovers each server’s tools inside per-repository sandboxes, screens candidates with MCP-aware static filters, and dynamically validates each one against an inferred least-privilege boundary. Across a catalog of 21,097 servers from nine registries, 787 of 4,806 triaged servers (16.4%) receive a filesystem capability flag without a FileSystem category label. Dynamic validation yields 150 adjudicated instances under tested policies. We select 13 additional findings for coordinated disclosure and document two Git MCP Server CVEs (§5).

We make three contributions:

- • 
We characterize and formalize how attacker-influenced MCP tool arguments expose filesystem capabilities beyond a tool’s contract and deployment scope. 
- • 
We design MCP-FSD to connect source screening and inferred per-tool boundaries to executable evidence, evaluating exploitability, benign operability, and sandbox containment across three complementary dynamic validation cases. 
- • 
We measure ecosystem-scale screening signals, confirm 150 vulnerable instances through dynamic validation under tested sandbox policies, and present Git case studies showing how repository operations expose host credentials. 

We evaluate these contributions through five research questions (§4). RQ1: how frequent are screening signals, and what evidence supports them? RQ2: how many candidates survive three-case dynamic validation? RQ3: what were the outcomes of coordinated disclosure? RQ4: how do violations distribute over language, registry, and tool category? RQ5: how often does a confirmed instance need a format-wrapped payload rather than a bare traversal string?

## 2 Background and Threat Model

### 2.1 Threat Model

We study local stdio MCP servers [26] launched as separate processes. In typical local deployments, the server runs with the user’s ambient filesystem permissions, and the client’s tool-approval prompt enforces no per-tool path restrictions on the underlying process [7, 15, 31]. Process isolation alone does not restrict access to the host filesystem unless explicit sandbox policies are applied. Figure 1 traces the resulting dataflow, from the content that carries the adversary’s argument to the file bytes that leave in the response.

The adversary influences the value of an argument that drives a side effect, through content the agent ingests as untrusted input [16, 44, 34]. The agent supplies it to a tool whose contract appears benign, and the spawned server exercises a host capability outside what that contract implies. We measure filesystem disclosure: an attack succeeds when the MCP response contains the contents of a file outside the tool’s legitimate scope. The evaluation begins at tool invocation and assumes that the agent issues the tested call or sequence and that the server has host permissions to access the target file. Arbitrary server-code modification and compromise of the OS sandbox are outside this model.

### 2.2 Filesystem Capability Laundering

An MCP tool exhibits *filesystem capability laundering* when its declared contract does not cover the filesystem effect its arguments can steer. Three conditions characterize the mechanism: (i) an implemented effect exceeds the scope justified by the tool contract and deployment, (ii) attacker-influenced arguments select the filesystem target, and (iii) the call is admitted while the surrounding controls fail to constrain that effect.

The three layers describe different aspects of this mechanism: L1 supplies candidates through category/capability screening, L2 identifies the per-tool contract/effect gap, and L3 identifies a defeated implementation control. They are not mutually exclusive: a missing or bypassable path check can implement a per-tool scope violation.

Prompt injection can influence the argument passed to a tool by affecting the model’s instruction-following [24, 25]. In contrast, capability laundering centers on the resulting server-side effect. Missing validation or flawed path checks (e.g., path traversal or symlink resolution) provide the underlying implementation mechanisms [1, 22].

#### Evidence for the intended boundary.

Grounding an intended boundary relies on a hierarchy of evidence. For each finding, the contract and deployment context must establish why the accessed target lies outside legitimate tool operation (§5.3).

### 2.4 Problem Statement and Challenges

Five challenges guide the design of MCP-FSD (§3).

C1: Large, heterogeneous ecosystem. MCP servers are distributed across registries, languages, and packaging conventions. Tool discovery requires source collection, language-specific installation, and transport handling before candidates can enter a common validation pipeline.

C2: Implicit filesystem boundaries. A path parameter indicates where an argument can point, but does not establish which locations are authorized. MCP-FSD combines the declared contract with deployment evidence, such as a selected repository root, to construct the policy hypothesis used during testing.

C3: Library-mediated accesses. Tool handlers often delegate filesystem operations to third-party libraries. For example, git_add passes its file list to GitPython. Source review identifies this call, while dynamic testing determines whether the resulting contents reach an MCP response.

C4: Semantically diverse inputs. A tool may accept a single path, a list of files, or a structured document containing a reference. Payload generation must synthesize schema-valid inputs so execution reaches the underlying filesystem operation.

C5: Connecting filesystem analysis to MCP. Filesystem analysis [20] must identify the callable MCP tools behind each finding and how their effects become observable. MCP-FSD uses tool associations, schemas, response construction, and stdio execution to connect source-level candidates to reproducible calls.

## 3 MCP-FSD Design

MCP-FSD runs in two passes (Figure 2). The *measurement* pass crawls registries, discovers each server’s tools and schemas, and assigns capability-triage labels. The *validation* pass applies four MCP-aware static filters (§3.1), infers a least-privilege boundary per tool (§3.2), and confirms exploitability with three-case dynamic validation against that boundary (§3.3). The primary disclosure oracle checks for fixture contents in the MCP response. Selected instances use other transcript evidence (§4.3).

### 3.1 Static Screening

MCP-FSD uses an LLM to identify tool registrations, handlers, and path parameters. It examines how these parameters reach filesystem operations and whether the code validates them. MCP-FSD records each candidate in the Static Analysis Results Interchange Format (SARIF), with its rule, source location, affected tools, parameter, sink, and rationale. We classify each finding into five rule categories spanning CWE-22 (path traversal) and CWE-59 (link resolution): *PT-001* missing validation, *PT-002* prefix-match containment, *PT-003* URL traversal, *PT-004* symlink TOCTOU (time-of-check-to-time-of-use), and *PT-005* blacklist filter. A small long tail of specialty rules that a language model proposes is reported separately.

The scan reviews the server repository and can flag visible library calls for dynamic testing without reconstructing their effects. It does not exhaustively analyze dependency internals. We call one SARIF result at a reported fix site an *emission*. A finding in a shared helper may affect several tools but produce only one emission. Emissions and dynamically confirmed instances therefore use different counting units.

Four MCP-aware filters select candidates for dynamic testing based on whether they can plausibly return out-of-scope file contents. *M1* ranks SARIF findings tagged to MCP tools [21]. *M2* reads the tool schema for path-shaped parameters. *M3* inspects response construction for a plausible file-content return. *M4* keeps only candidates that run as stdio MCP servers. These lightweight filters prioritize high-probability candidates for dynamic testing without the overhead of whole-program taint tracking.

For the disclosure-oriented pass, M1 prioritizes file-content sinks over write-only or shell findings. M2 identifies the argument that reaches the sink, including entries in a tool’s file list. M3 distinguishes a response containing file text from one reporting only derived metadata: a line count or schema descriptor cannot satisfy the credential-content oracle. M4 checks whether the candidate can be exercised in the local stdio harness. It excludes hosted services whose runtime cannot be reproduced.

#### Worked screening example.

For git_add, the reviewed handler connects the schema’s files parameter to repo.index.add(files) without a repository-containment check, recorded as a PT-001 SARIF candidate. M1 associates it with the MCP tool and M2 identifies its path input. The disclosure observation comes from git_diff_staged, so M3 uses the explicitly stated staging-and-diff sequence rather than treating a staging acknowledgment as file content. M4 checks the stdio launch. While this evaluation validates this specific multi-call chain, dynamic validation confirms whether the final response discloses fixture contents.

### 3.2 Boundary Inference Algorithm

For each candidate that passes static screening, boundary inference constructs the least-privilege scope used by payload generation and sandbox validation. MCP-FSD derives the scope from the tool’s legitimate operation rather than from the suspected bug: read-write access covers the working directory, while read-only access covers the server binary, dependency tree, and required system-root subtree. The fixture planner then places the credential fixture outside every allow scope and the benign marker inside the working scope.

#### Algorithm.

Algorithm 1 uses four signals: launch configuration , path-bearing schema fields , the tool description , and repository source signals . The language model drafts a candidate policy from . MCP-FSD extends the policy to cover runtime requirements identified in , then tests whether a benign invocation succeeds.

#### Subroutines.

ExtractRoots reads the launch tuple: the working directory the client starts the server in, any --root-style launch argument, and path-valued environment variables. PathParams walks the JSON Schema and returns the fields whose type, name, or format encodes a path, so payload generation targets the appropriate argument (C4). HandlerPathRefs identifies literal and constructed paths and access modes in the reviewed handler code. LMDraftPolicy asks the model for a candidate glob policy from those roots, fields, and the description. Cover extends the policy to include identified runtime dependencies (such as language runtimes, libraries, and system configuration paths). SplitRWRO partitions the result into a read-write and a read-only half according to whether each parameter is written or only read at the observed sites.

#### Checks and example.

Before dynamic testing, MCP-FSD checks that the policy covers identified runtime requirements and leaves a non-empty out-of-scope region for the fixture. For git_add this yields /ws/** read-write and dependencies read-only, with the benign file inside /ws and the credential fixture outside. The three-case test then replays staging followed by a diff (§5.2).

The repository needs write access for the index and object-database updates required by staging, while runtime dependencies need only be readable. The credential fixture must lie outside both sets: placing it outside the working tree alone would be insufficient if a read-only runtime allowance still covered it. The benign invocation checks that these permissions support the intended staging-and-diff operation.

### 3.3 Payload Generation and Dynamic Three-Case Validation

#### Dynamic payload generation.

For each path-shaped parameter, MCP-FSD first fixes two targets from the inferred boundary: the malicious target is the planted out-of-scope credential fixture, and the benign target is the in-scope marker file. A language model then proposes concrete argument forms, seeded with published path-traversal exemplars, and refines them against the tool schema, the inferred boundary, and observed responses until the malicious attempt reaches the fixed credential target or the attempt budget is exhausted. For a tool that parses structured input, it wraps the same target in a format-valid container, for example a BPMN, glTF, DOCX, or PNG file, or a Terraform body. The model varies the argument form while the target stays fixed. MCP-FSD resets test state and replays the same converged payload or stated call sequence with and without the sandbox.

Response-disclosure validation uses three cases. Other effects require separate evidence rules (§4.3). PoC 1 runs the malicious payload without the sandbox and succeeds only when the response contains the planted credential contents (C2–C3). PoC 2 runs the benign in-scope payload with the sandbox and requires the expected successful operation with no denial event. PoC 3 replays PoC 1’s malicious payload with the sandbox and requires absent credential contents plus an explicit denial or a non-disclosing response.

This three-case protocol isolates exploitability from containment: PoC 1 confirms that the exploit succeeds on an unconfined host; PoC 2 verifies that the inferred sandbox policy preserves legitimate, in-scope functionality; and PoC 3 demonstrates that the sandbox neutralizes the exploit under that exact policy. Together, these cases establish that detected disclosures represent genuine vulnerabilities remediated by least-privilege containment.

We distinguish explicit containment, where the response exposes the operating-system denial, from silent containment, where the response is empty or non-disclosing without an exposed denial. A silent response alone does not identify which syscall was blocked. Throughout, we call this enforcement *operating-system process isolation*, reserving “kernel-enforced” for backends that provide kernel-level enforcement such as Landlock or Seatbelt [2, 4, 18].
All 150 dynamically adjudicated instances in §4.3 pass this three-case gate, providing the containment evidence discussed in §6.1.

Per candidate, MCP-FSD records the three parsed response transcripts and the reproducer script, along with source citations, the inferred sandbox policy, runtime details and, when available, a sink citation pinned to a specific file and line. The verdict adjudicator reads this per-candidate record.

## 4 Evaluation

### 4.1 Experiment Setup

#### Data collection.

We catalog 21,097 listings from nine registries, including 17,919 open-source entries. The measurement pass selects local open-source servers, excluding forks, archived repositories, remote-hosted services, and unavailable code. Successful startup and discovery produce the triage input. The validation pass then screens and tests selected candidates.

The triage step classifies each server across twelve functional categories (primary_type), such as FileSystem, CodeDev, and KnowledgeRetrieval, derived via LLM analysis of tool descriptions rather than external registry tags.

#### Implementation and corpus funnel.

MCP-FSD comprises 7,486 executable lines of Python and shell plus 618 lines of analysis prompts. Dynamic validation runs each candidate in nono v0.43.0 [2], a macOS Seatbelt sandbox. Static analysis returns results for 4,292 servers and flags 2,818 of them for potential vulnerabilities (20.3% and 13.4% of the 21,097-server catalog, respectively).

#### Units of analysis.

Our evaluation distinguishes four units of analysis: *servers* (catalog and triage entries); *static emissions* (individual SARIF finding sites, where a shared helper may affect multiple tools); *dynamic instances* (unique tool-policy pairs confirmed via three-case replay); and *disclosure packages* (curated multi-tool findings bundled for vendor remediation).

#### Triage snapshot and selection bias.

The final triage snapshot contains 4,806 servers, with static analysis evaluated on the successfully cloned and parsed subset. The funnel is selective: only 7,222 of 21,097 catalogued servers (34.2%) reach the measurement pass, the post-measurement corpus is 97% Node and Python, and pulsemcp supplies 84% of measurement-pass startups. Our prevalence estimates and per-registry comparisons describe this locally runnable open-source corpus rather than an idealized, uniform distribution across all ecosystems.

### 4.2 RQ1: Screening Signals and Evidence

The L1 signal combines the triage’s multi-label primary_type field and four filesystem capability flags (file-related call, path input, file read, and file write), extracted via LLM analysis of tool discovery summaries. Among 4,806 servers, 787 (16.4%) exhibit at least one filesystem capability flag despite lacking a FileSystem category classification. Because routine persistence mechanisms do not necessarily violate a tool’s contract, and absent external ground-truth labels across the entire catalog, this category mismatch serves as a coarse initial screening signal rather than a definitive violation metric.

At the static-emission level, MCP-FSD emits 10,304 findings across the 2,818 flagged servers (65.7% of the 4,292 with results), with missing path validation as the largest individual rule category (Figure 4). Combined, the defense-bypass rules (PT-002–PT-005, 61.6%) outweigh PT-001 missing-validation (36.4%). Rule families rank differently when counted by confirmed instances rather than static emissions: a single repository can emit many findings across sibling tools, increasing the weight of whichever rule it carries. Each emission has a severity level: 61.8% are reported at error level, 29.8% at warning, and 8.4% at note.

URL-traversal emissions include candidates that do not disclose local files, so static counts remain separate from dynamic outcomes.

### 4.3 RQ2: Confirmed Instances

MCP-FSD confirms 150 instances, each adjudicated under the three-case dynamic validation (§3.3) against the inferred least-privilege boundary. For 136 of the 150 instances, adjudication relies on exact credential-marker matching: PoC 1’s response contains the planted secret string, whereas PoC 3’s response contains no marker bytes. For the remaining 14, the adjudicator evaluates corresponding evidence from other transcript features (write side-effects, response-shape changes, or external-CLI outputs).

### 4.4 RQ3: Disclosed Outcomes

We reported 13 findings, including two CVEs in Anthropic’s Git MCP Server (§5). MCP-FSD dynamically validates git_add with a full three-case PoC. The git_init finding is static because its disclosure is indirect: it seeds a repository that downstream Git tools then read. Both CVEs have been patched upstream.

Among the 13 packages, 11 cite source-level mechanisms or configuration as evidence, including validators, storage-base constants, and shell argument handling. These evidence sources span a spectrum of enforcement: a base directory may lack runtime checks, while an overbroad allowlist or shell-quoting flaw exhibits a distinct authorization boundary from a containment bypass. Two packages rely on contract-implied scope boundaries without explicit path validation at the read sink. All 13 packages were submitted for coordinated disclosure, with upstream fixes or CVE assignments pending at the reporting cutoff.

We prioritized findings where either a source-level control is bypassed or the project publicly commits to a narrow scope that the implementation does not enforce, because those reports have a per-server fix without requiring a protocol change.

### 4.5 RQ4: Violation Distribution

The flagged population follows the same concentration as the corpus: pulsemcp dominates the registry axis, and Node/Python dominate the language axis. At the sink level, 54.3% of emissions are Node-ecosystem files and 42.6% are Python files. All other languages together account for under 3.1%. Python leads PT-001 missing-validation (53.8% within-rule share), while Node leads every bypass-style rule at 57%–63% (Figure 5a). This distribution reflects structural tooling gaps: the MCP TypeScript SDK provides no built-in path-containment primitive (such as a safePath() utility), leaving Node servers prone to flawed custom checks (accounting for 54.3% of all emissions). Conversely, Python servers frequently omit validation checks entirely (53.8% of PT-001). These patterns indicate distinct remediation paths: default allowlist helpers for Python and standardized path-containment primitives for TypeScript.

### 4.6 RQ5: Payload Forms

We categorize the payloads synthesized by the iterative generation loop (§3.3) by their converged input format (bare traversal paths versus format-valid containers). Across the 150 confirmed instances, 144 (96.0%) use the bare traversal form, while 6 (4.0%) require a format-valid container. Among the 38 confirmed instances that bypass an explicit source-level validation check, 32 (84.2%) use the bare form and the same 6 (15.8%) require wrapping.

Format-valid fixtures ensure that tools parsing structured inputs (such as glTF, DOCX, or Terraform configurations) accept the payload before executing underlying filesystem calls. An unformatted traversal string rejected by an input parser would leave the tool’s access to the target untested. While 96.0% of vulnerable tools accept bare paths, structured tools necessitate format-valid containers to expose the laundering path.

## 5 Case Studies

Two CVEs in Anthropic’s Git MCP Server illustrate L2 laundering across distinct boundaries. MCP-FSD flags both and dynamically validates git_add (§4.4).

### 5.1 Case 1 (L2): Unscoped Repository Creation in git_init (CVE-2025-68143)

The git_init handler initializes a repository at the supplied repo_path:

Root cause. The handler passes the caller-supplied repo_path directly to Repo.init(), without verifying containment within the configured workspace. Any writable filesystem location becomes a valid initialization target. Impact. When an attacker-influenced argument names a sensitive directory such as ~/.ssh, git_init converts that directory into a Git repository. Subsequent Git tool calls such as git_add and git_diff_staged then operate inside it legitimately and return raw file contents, including SSH private keys, as diff output to the agent. In this deployment, the selected workspace defines the intended scope for repository creation. The issue was assigned CVE-2025-68143 [13]. The fix removes git_init from the server (released as version 2025.9.25). The upstream advisory credits Yarden Porat for the initial report and one of our co-authors (@0dd) for developing the upstream patch. We contributed independent vulnerability analysis and remediation.

Under this workspace boundary, the vulnerability satisfies all three capability-laundering conditions (§2.2): repository creation exceeds the authorized workspace scope (i), caller-supplied arguments steer the filesystem target (ii), and the server executes the initialization without containment (iii), enabling subsequent credential extraction.

### 5.2 Case 2 (L2): Path-Traversal Staging in git_add (CVE-2026-27735)

The git_add handler stages the supplied files list:

Root cause. The handler does not check whether paths in files stay within the repository root before staging. The affected _to_relative_path() function in GitPython returns relative paths without validating their containment. Paths containing ../ then reach _store_path(), which reads the file bytes into Git’s object database. The contents are stored by Git even though the source file lies outside the working tree. The fix, released in 2026.1.14, delegates staging to the Git CLI through repo.git.add(). The CLI rejects out-of-repository paths [14].

Impact. Sensitive host files such as SSH keys or dotfiles can be staged and then exposed through a staged diff, or carried into a commit that sends them to a remote on the next push. The repository root forms the implied scope of git_add; failing to enforce containment allows out-of-scope files to be staged into the repository index. The issue was assigned CVE-2026-27735 [14]. The complete three-case dynamic validation runs against the pre-patch version: the unsandboxed staging-and-diff sequence returns the planted credential contents, the sandboxed benign sequence succeeds on an in-scope file, and the sandboxed malicious sequence returns a permission-denied error (EPERM) with the credential bytes absent.

### 5.3 Synthesis

The cases require containment at different points in the call sequence. For git_init, the creation target must lie within the deployment’s workspace before a repository is created there. Once a sensitive directory has become a repository, later calls that name the same repo_path can stage and display its files without leaving that repository root. A check against only the newly selected root would therefore miss the earlier workspace violation. For git_add, the repository already exists: each entry in files must remain within it. The preceding state-changing call makes the bytes reachable, and the staged-diff response reveals the disclosure.

In both cases, the intended scope, caller-selected path, and missing containment instantiate conditions (i)–(iii) of §2.2. Neither case requires a pre-existing containment check. The same reasoning applies to other tools: a configured vault root supports an intended scope, whereas a suggestive name such as read_build_log exhibits greater scope ambiguity.

Prior L3 vulnerabilities in the reference Filesystem MCP Server—such as sibling-prefix bypass (CVE-2025-53110 [30]) and symlink traversal (CVE-2025-53109 [29])—provide external benchmark cases. MCP-FSD flags their source-level patterns to verify static rule coverage, though they remain separate from our 13 newly reported findings.

## 6 Discussion

### 6.1 Mitigations

At L3, developers should enforce canonical-path containment, validate schema fields, and address symlink races at access time. An SDK-level containment helper would reach the many Node servers that currently ship no such check (§4.5). At L2, a protocol extension could expose a per-tool fs_scope field in tools/list, allowing clients to inspect the requested read/write scope before approval and enforce the approved policy on server execution [40]. MCP-FSD’s read-write and read-only path sets offer a candidate representation for that field. Inferred policies would need review against deployment requirements. Our three-case validation demonstrates that operating-system process isolation reliably enforces least-privilege boundaries without disrupting benign tool functionality. At L1, registry screening can identify filesystem capabilities for further review.

### 6.2 Limitations

First, the pipeline only validates servers it can install and run. The dynamic results are conditional on successful startup and the selected runtime configurations. Second, dynamic validation may miss a violation whose out-of-scope effect never appears in a response, or that requires a runtime precondition the harness does not reproduce. Third, we do not measure the accuracy of the inferred boundaries themselves. A policy that is too restrictive can flag legitimate access, while one that is too permissive can miss a violation. Source coverage and a successful benign call do not establish authorization accuracy. Future benchmark efforts should establish expert-annotated boundaries across diverse server documentation to systematically quantify boundary inference precision and recall.

Fourth, the effect model includes writes, but the disclosure-oriented evaluation does not systematically measure unauthorized creation, modification, or deletion. The git_init case illustrates write-driven setup, and our separate Memory MCP Server report demonstrates configuration injection through a persistence write when an attacker controls the launch-time persistence path. Its fix was merged upstream without a CVE.

Assessing these writes requires filesystem-state evidence as well as responses. In a targeted case study on mcp-architect, a caller-controlled projectId is joined to the storage root without containment: an unsandboxed invocation successfully writes a sentinel file outside the allowed storage directory, whereas sandboxed replay is blocked by the OS policy (EPERM). This demonstrates how an integrity-focused oracle can detect unauthorized filesystem writes even when no file contents are returned in tool responses.

Fifth, enforcement strength follows the sandbox backend (§3.3). Sixth, validation covers selected tools and explicitly stated call sequences, not systematic discovery of cross-tool chains. A tool that writes attacker-controlled content into a file that a second tool later reads can launder capability across the pair while each tool, evaluated alone, respects its boundary.

Seventh, several stages rely on LLM-generated judgments, namely the capability-triage labels used in the L1 signal (§4.2), the rule families behind the static emissions, and the boundary-policy drafts. Those results inherit the model’s error modes. A systematic accuracy study of these model-dependent stages remains future work, along with full reporting of model versions, prompts, and decoding settings.

### 6.3 Ethical Considerations

This work analyzes publicly available MCP servers and validates disclosure against fixture credentials, never real secrets. We follow responsible-disclosure practice: the Git MCP cases of §5 were reported to the affected vendor, and both received CVE assignments. Dynamic validation runs on controlled installations with synthetic fixtures and resets between cases. PoC 1 intentionally omits the test sandbox.

## 7 Related Work

#### MCP security and filesystem detection.

Table 3 situates MCP-FSD among MCP security studies [41, 38, 36, 37, 35, 17] and filesystem-flaw detectors [1, 22, 20, 21]. The closest contract-analysis work, DCIChecker [35], combines structured code extraction with direct, reverse, and arbitration prompts to detect description-code inconsistencies. MCP-FSD focuses on filesystem effects triggered by attacker-controlled arguments and tests them against an inferred policy for each tool.

| Work | Target / scope | Evidence / method | 
|---|---|---|
| PathSentinel [20] | Android filesystem attacks and platform access-control policy | Program and policy analysis with generated exploit validation | 
| MICRYSCOPE [41] | Cryptographic misuse in MCP servers | Cross-language API and dependency analysis with taint rules | 
| MCPGuard [38] | MCP threats and defenses | Systematization of scanning and runtime-monitoring approaches | 
| MCP-SandboxScan [37] | External-input exposure and filesystem capability violations | WASM/WASI execution with output matching and denial evidence | 
| DCIChecker [35] | Description-code inconsistency, including undeclared effects | Structured code extraction and LLM cross-validation | 
| MCP-FSD | Filesystem effects relative to per-tool policy hypotheses | Source screening and fixture-based three-case execution under OS containment | 

While MCP-SandboxScan [37] utilizes WASI sandboxing and output matching to detect external-input leakage, MCP-FSD couples static screening with dynamic three-case replay on native host runtimes, capturing complex library-mediated flows against inferred per-tool scopes. Similarly, where mobile analyzers such as PathSentinel [20] evaluate applications against pre-existing platform access-control policies, MCP-FSD infers least-privilege boundaries directly from unstandardized tool descriptions and deployment configurations.

Description-code agreement, file-to-output flow, and authorization answer different questions. A description can promise to stage local files without specifying which directories are allowed. A diff response establishes that file bytes reached the client, while the repository-root policy states the scope against which the access is tested. MCP-FSD records the source candidate, policy, and execution transcripts together, connecting the declared operation to the tested access and returned bytes.

Agent security, prompt injection, and isolation. Related work benchmarks harmful tool use [33, 10, 3, 45, 43, 23], studies agent backdoors [39, 42], and attacks or defends model instruction-following [9, 32, 46, 11]. It also applies models to offensive-security tasks [12, 19] and documents path traversal in the agent harness itself [6, 5]. MCP-FSD tests the effects of separately launched MCP server processes using existing OS containment and deception primitives [18, 40, 8, 4, 2]. Paired malicious replay and a benign control test the inferred policy (§3.3).

## 8 Conclusion

Filesystem capability laundering exposes a fundamental gap between client-side tool approval and unconfined server filesystem execution. MCP-FSD bridges this gap by coupling static screening, inferred least-privilege boundaries, and dynamic three-case validation across 21,097 cataloged servers. Real-world vulnerabilities in foundational tools—such as repository creation and staging flaws in Anthropic’s Git server—demonstrate how ordinary tool interactions can inadvertently leak sensitive host credentials. These findings demonstrate the necessity of ecosystem-scale registry screening and explicit, runtime-enforced per-tool filesystem contracts.
