Designing Deploy-Time Flexibility for Modular Systems — Florin Coros | Craft 2025

1. Key points — Decide after compiling, not while designing

The thesis: "Monolith or microservices" is the wrong question. The right goal is a modular system, and deployment should be a post-compilation decision: the same binaries run as a modular monolith (in-process function calls) or as microservices (REST/gRPC/message bus). The demo switches modes by copying a DLL into another folder and restarting — no recompile.

Root-cause claim: Both architectures fail for the same reason — bad decomposition — because we decompose while thinking about communication and deployment ("will these two things live on the same server?"). A modular system lets you separate the communication concern and defer it to deploy time.

The "stability" triad: Maintainability, extensibility, reusability are inseparable — "You cannot have one without the other." Teams ask only for maintainability because reusability is a hard sell to management ("what the manager hears is that someone else, another project, will benefit of our work") — but engineering-wise, investing in extensibility and reusability is what buys maintainability.

Sizing heuristic: The only two costs in software are the cost to build a service and the cost to integrate services. The architect's entire job is to keep the system in the "area of minimum cost" — in orders of magnitude, ~10 services (20–25 fine; 2 or 90 are not). The curve has diminishing returns, so don't chase the exact minimum.

Contracts are load-bearing: Explicit contracts with abstraction (the client doesn't need to know how it's done) and encapsulation (the client can't depend on the implementation even if it wants to). Without contract-only dependencies, "we are either here or here without knowing it" on the cost curve.

Three pillars make deploy-time flexibility work: (1) dependencies only through contracts, enforced by structure; (2) proxies — every contract is implemented by a proxy that forwards over the wire or in-process; (3) type discovery — a generic host that configures DI declaratively at startup by scanning assemblies, instead of imperative registration code that would force the host to reference all implementations.

Origin story: A Dutch investment bank spent three years splitting a Delphi monolith (drivers: shrinking Delphi talent pool and ~14-month release cycles caused by manual end-to-end testing) — then discovered 10–15-hop call chains whose network latency broke core use cases like placing an order. Florin's proposal to co-locate chatty services in one process at deploy time won the project and inspired the talk.

Production discipline: Even in-process calls should go through proxies wrapping the real implementation, so error semantics stay consistent (a REST call yields a 500; an in-process call would throw a raw IndexOutOfBoundsException — "the contract is not consistent if you switch the types of deployment") and so you get logging/telemetry.

Portability claim: Nothing here is .NET-specific — "as long as you have interfaces and a little bit of reflection, things can be done" in Java or TypeScript. "The power of IT is mainly the structure and the design."

The history loop: ~15 years ago monolith→microservices, ~5 years ago microservices→modular monolith. "We are moving in this circle mainly because we don't ask the correct question."

3. Tools, practices, and methodologies

Contract assemblies — A physical boundary (.NET assembly / Java package) containing only interfaces (operation contracts), DTOs (data contracts), and exceptions (fault contracts); zero logic allowed. Use it as the only dependency target between modules.

App Boot (GitHub: iquark/appboot) — Small open-source .NET library for type discovery: a [Service] attribute on an implementation class declares which interface it fulfills; the Bootstrapper scans a filtered list of assemblies at startup and registers everything into the DI container. It abstracts the container itself (registration behaviors, ServiceInfo with interface/implementation/lifetime), so any DI container plugs in — the demo uses appboot.unity (Unity).

ServiceProxy attribute + behavior ordering — Proxies get their own attribute and registration behavior; register the proxy behavior first, the real-service behavior second, so "always the last ones will override the first ones." A priority-ordered registration catalog makes the outcome deterministic regardless of DLL load order — fixing the non-determinism where either proxy or real implementation could win.

Per-contract proxies — One proxy per contract, convention-based URL building + HttpClient. In production, a second set of in-process proxies wraps real implementations for consistent error handling, logging, and telemetry.

Generic host — One host process that can host any service: at startup it scans deployed DLLs and loads whatever modules are present. Production refinements he names: a truly generic controller mapping conventions to contract functions, or dummy proxies that return 404 for undeployed contracts instead of crashing.

internal implementations — Implementation classes are marked internal on purpose, so tooling (ReSharper) won't even suggest referencing them — encapsulation enforced by visibility.

Dependency-rule enforcement — Generate the project dependency diagram from code (he uses ReSharper) and keep "no dependencies between modules, only through contracts." Options for CI: Visual Studio Enterprise architecture diagrams validated at build, reflection-based unit tests checking references, or manual review — "I don't automate this because… it's very visible" in the generated diagram during code review.

Single-output build + post-build copy scripts — All projects compile into one bin folder; BAT-file post-build events assemble deployment configurations (one folder per service, or co-located folders). The demo's DLL copy stands in for what a Dockerfile or pipeline does in production.

Deployment guidance — One Dockerfile/build per deployment configuration copying the right binaries; pipelines that know which DLLs go where; service discovery instead of hard-coded addresses. Kubernetes deployment "is the same. It's not really impacted by this design."

Warm-up / DLL preloading — Assembly scanning happens at startup: on the server, treat it as warm-up (fire requests post-deploy); for desktop/front-end modular monoliths, preload DLLs to avoid startup lag.

DTO design rule — Contract data types must be trivially serializable for the chosen protocol (JSON for REST, protobuf for gRPC); prefer concrete simple types — "an array rather than an IList."

The cost graph — Plot cost-to-build vs. cost-to-integrate against number of services; target the flat "area of minimum cost," exploiting diminishing returns instead of optimizing the exact minimum.

Demo repo & training — The step-by-step repo is on the Co-Design GitHub (folder "Inter Process Communication trading app," git tags prefixed IPC); the material is "a mini version" of their training, Application Infrastructure for Clean Architecture.

4. Unanswered questions and omissions

Data and transactions are entirely absent. He lists "transactions" as a core microservices pain, but says nothing about databases, shared vs. per-service schemas, or transactional consistency across services in either deployment mode. Likewise, the monolith's state-synchronization problem ("quite tricky to achieve") is named and never solved.

The independent-scaling trade-off goes unaddressed. Co-locating sales and quotation for performance gives up exactly the per-service scalability that motivated splitting the monolith in the first place. The bank's problem is solved by partially undoing the bank's solution — that tension is never confronted.

No numbers. The whole premise is eliminating network latency for chatty services, yet there are no benchmarks, and identifying chatty pairs is hand-waved as "look through some metrics from production."

The hardest piece is unproven in the demo. The "truly generic host" with convention-based generic controllers was hard-coded for the talk; he admits the demo "just assumes" a service exists for any incoming call — "it will just crash" otherwise.

Only REST was shown. gRPC and message-bus modes are claimed, never demonstrated; and how a 500 and an in-process exception become "the same contract" (fault serialization) is asserted, not built.

The cost of the mechanism itself is never weighed. No discussion of when this is overkill versus just picking one deployment style; no treatment of the maintenance burden of custom infrastructure (App Boot, behaviors, conventions, dual proxy sets), onboarding, or debugging through an indirection layer where runtime behavior depends on deployment layout.

Security is a blind spot. Nothing on authentication, authorization, or trust between services in distributed mode.

Observability is one sentence. Telemetry appears only inside the proxy discussion; there's no tracing/correlation story for calls that switch between in-process and network hops depending on deployment.

Portability is asserted, not demonstrated. Java/TypeScript feasibility rests on "interfaces and a little bit of reflection," but the demo leans on .NET-specific assembly loading and DLL-copying mechanics.

Testing is diagnosed but never solved. He criticizes testability in both monoliths and microservices, yet never shows how this design improves testing — e.g., running integration tests in-process against the same binaries.

The bank story has no epilogue. The POC won the project and the team grew to ~20 people, but we never learn whether performance was actually fixed or how the approach fared over the 11 years since.

Failure handling beyond retries/timeouts (raised only when an audience member asked): no circuit breakers, idempotency, or partial-failure discussion — despite reliability being one of his stated motivations.

The organizational angle is skipped. Contract ownership gets one sentence ("you could also achieve some contract ownership by placing the contracts to each service"); no Conway's-law/team-topology discussion, even though modular systems are as much an organizational pattern as a technical one.
