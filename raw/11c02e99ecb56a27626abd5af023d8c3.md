Machine Learning in Production — Adam Pelle (Marshmallow), Craft 2025

1. Key points: Your analytical data just became production data

The shift that started everything: Insurance use cases — risk scoring, fraud detection, dynamic pricing — killed the old model of offline analytics (services → Snowflake → data scientists → insights → back to product engineers), which was "offline, reactive and it's very slow." Real-time pricing means the old "let me get back to you next week" became "let me get back to you in 150 milliseconds."

The talk's central insight: Once ML models consume your data pipeline, the data flow becomes a cycle — analytical data comes back out as operational data. "Operational data equals to analytical data." The old excuse — best-effort emission from services, "if it's sent, it's sent, if not, that's life" — "is no longer true because it has consequences." A missing field no longer ruins a dashboard; it degrades a live prediction.

Data quality is the binding constraint: Model success is "explicitly bound to the data." Poor inputs produce "compounding errors downstream" — garbage in, garbage out — so transformations need standardization and consistency.

An unresolved organizational tension: Services want a "need to know" approach to data; models want to be fed as much as possible. Finding the middle ground "creates an organizational tension which requires clear governance."

ML endpoints are microservices and should be treated like them: same production standards — latency SLAs, high availability, code quality, testing, the four golden signals — plus ML-specific verification: contract testing, schema verification, and backtesting.

Drift is inevitable, so monitor and retrain: data drift (input distribution shifts from external events, e.g., pandemic-era vehicle mileage) and concept drift (the input→output relationship breaks, e.g., repair shops raising costs invalidates the old ground truth). Proactive scheduled retraining beats reactive.

Verification exists to manage real risk: these models touch revenue, user experience, and a heavily regulated business — backtesting is "about building confidence" and mitigating "financial or even legal risk."

Scale and trajectory: 14 online inference endpoints, ~25 models (some endpoints host multiple models) across claims, fraud, and pricing; busiest endpoint ~30 requests/second; goal is 100+ models in every major business domain.

The honest confession (from Q&A): the biggest challenge was timing. They shipped models into production "without any sort of considerations just to really get to the market very fast," ate the resulting "problems, failures," then retroactively assembled an MLOps team and roadmap.

3. Tools, practices, and methodologies

AWS SageMaker — managed platform for training and deploying ML models. Marshmallow's inference endpoints run on it, called via HTTP REST "similar to any other microservice"; canary releases come via SageMaker production variants.

Python project templates + helper libraries — scaffolding and shared libs to bootstrap new endpoints "pretty, pretty fast." The hard problem: propagating template changes to existing models (see AI agents below).

Docker base image + CI/CD — endpoints layer their code onto a shared base image; deployment is fully automated through CI/CD.

Four golden signals monitoring — latency, throughput, error ratio, etc. Monitor ML endpoints exactly like every other microservice.

Feature store (Tecton / Feast) — stores and manages features for both online inference and offline training. Benefits: versioning with visible history, cross-team consistency ("avoid [the] situation when each and every team doing the same thing a little bit differently"), and automated backfill — introduce a feature today, backfill a year of history "without any sort of additional configuration." Tecton is the "boxed solution" Marshmallow uses; Feast is open source and self-hosted.

Feature taxonomy — three types to design around: on-demand (computed from request inputs alone, e.g., a risk score), aggregational/dynamic (per-customer lookups, e.g., vehicle values insured over the last five years), and periodically updated (batch jobs, e.g., market-average vehicle value).

PSI (Population Stability Index) & Kolmogorov–Smirnov test — statistical methods to compare training/test distributions against production distributions for drift detection.

Bidirectional contract testing (Pact broker) — consumers generate pacts via WireMock from captured network calls (Marshmallow is "a Java company"); providers publish an OpenAPI schema (generated from Pydantic) to a Pact broker; the broker validates consumer pacts against provider contracts. "Prevents integration failures before deployments." Painless for them because they already had OpenAPI contracts.

Schemathesis / Dredd — schema verification tools that generate random data from the contract, call the endpoint, and observe behavior. Closes the gap where "the provider does not verify its own schema."

Decimals as strings — represent financial decimal fields as strings to avoid serialization/rounding issues across languages; requires custom fields for min/max bounds and "very cumbersome" support built across the stack — but "definitely worth it."

Backtesting — replay historical production inputs through a candidate model built from the PR branch as a Docker image (anonymize data if needed). Critical detail: re-run everything with the current production model state, since old data was computed with an old model state. Use it to confirm expected outcomes (e.g., "we expect that we could give like 20% lower prices"), detect regressions, and do statistical evaluation.

AI agents for test propagation — experiment in progress: agents iterate over every model to add tests when template changes are non-trivial, because "you need to mock things differently at each and every model."

Automated PR tooling — scripts run across GitHub repos to open pull requests for trivial template changes.

MLOps team — assembled after the initial fast-and-loose deployments, to build the roadmap of everything above.

4. Unanswered questions and omissions

Delayed ground truth. For claims and fraud models, true labels arrive months after prediction. His drift recipe compares distributions, but he never says how they measure actual model accuracy in production while outcomes haven't materialized — the hardest monitoring problem in insurance ML, skipped entirely.

The feedback loop he drew but didn't confront. He proudly points out the data flow is now a cycle — but a cycle means models are trained on data shaped by the previous model's own decisions (pricing changes who buys, which changes the claims data). Adverse selection and self-referential training data are the elephant in his own diagram.

Adversarial drift. Fraud detection is a headline use case, yet fraudsters actively adapt to models. No mention of adversarial monitoring or robustness.

Canary releases that lie. Golden signals catch latency and errors — but a canary model that responds perfectly and predicts garbage passes every check he described. How do they evaluate prediction quality during rollout? Never answered. No shadow deployments, A/B tests, or champion/challenger either.

Governance in name only. The service-vs-ML data tension "requires clear governance" — but he never says what the governance is: who owns features, who's accountable for upstream data quality, how disputes get resolved.

No enforcement mechanism for data quality. Best-effort emission is declared dead, but what replaces it? No schemas on Kafka topics, no data quality tests, no contracts at the streaming layer are described — the "how" of the talk's central argument is missing.

Cost with no numbers. "These things cost a lot" — and cost optimization is listed as a future direction with zero concrete strategies.

Regulation without explainability. Compliance and legal risk are invoked three times, but there's no mention of model explainability, documentation, audit trails, or how they'd defend a pricing decision to a regulator — table stakes in insurance.

AI agents: experiment, no verdict. "Started to experiment" — no results, no evaluation criteria, no failure modes.

No rollback story. What happens when a production model misbehaves — kill switches, rollback procedures? Absent.

No war stories. "We had a couple issues with this" — the failures that forced the MLOps team into existence are never described. The talk stays at the architecture diagram level.

No GenAI anywhere. A 2025 ML-in-production talk with zero mention of LLMs — either genuinely absent from their stack (worth stating) or a conspicuous omission.
