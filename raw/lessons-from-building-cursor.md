Model-building is product-building. Cursor trains its own models (like Composer 1.5) because certain capabilities—semantic search across huge codebases, recursive subagents, self-summarization—can only be learned through RL, not prompted. “If it’s not built into the model, the model won’t be able to use the thing.”

RL infrastructure is a new kind of hard. Training with millions of sandboxes and 100M+ CPU hours per year forces you to build your own orchestration; you can’t just outsource to cloud providers. Monitoring and deploying long-running agents (minutes to days) breaks traditional RPC assumptions. Workflow engines like Temporal and Restate are early answers.

Cloud agents need a step change, not a UI tweak. Today’s cloud agents are a worse version of local agents. To grow usage 1000×, the model must take responsibility for testing its own code and proving correctness. The blocker is “devex”: models silently degrade when services aren’t started in the right order, because no one writes them a clear runbook. Companies will need “devex teams” that document how to boot up a repo for an AI.

Context windows are a solved problem through RL. Instead of prompting a model to summarize, RL incentivizes it to produce summaries that are genuinely useful to its future self. The model also learns to dump old conversations to files and grep them later. “You don’t need a trick.”

Coding got solved in six months. Between March/April and December, the best engineers stopped writing code by hand. This is a “boring fact,” not a provocation. Engineering practice will keep changing with one or two capability jumps every half-year. The next jump: engineers adopt a “managerial instinct,” overseeing agents rather than writing lines.

The browser experiment revealed a qualitative shift. Watching a model build a functional browser—something the speaker says he couldn’t do himself in a month—made it visceral that models are now doing things humans simply cannot. This points toward “self-driving codebases” where you allocate a budget and the codebase manages its own security, tech debt, bugs, and features.

Advice for engineers is pragmatic, not prescriptive. If the codebase lives for years, review every line. If it’s a weekend project, who cares? Artisanal coding will survive in niches, but most engineers already enjoy coding more because boring debugging has vanished.

Tools, practices, and methodologies

Composer 1.5 model — A fast, RL-trained coding model positioned between Sonnet 4.5 and Opus 4.5. Use it when you want low-latency, engaging code generation with baked-in skills like semantic search and self-summarization.

RL for tool-use and self-summarization — Instead of prompting a model to use grep or write summaries, train it with RL so that it learns to produce grep queries and summaries that are genuinely useful for its future self. This is how Cursor makes models effective over very long tasks.

Semantic search in large codebases — The Composer model is trained to find relevant code in 1–3 queries rather than tens of greps. This is a capability that only emerges through RL, not prompting.

Self-summarization with file dumps — When the context window fills, the model writes a summary and dumps the previous conversation to a file. It can later grep that file to retrieve past context. RL makes the summaries lossy in the right way—retaining what matters.

Temporal / Restate — Workflow engines for long-running, reliable agents. Temporal (from Uber) and Restate allow you to run agents that take hours or days, with automatic retry if any step fails. The speaker sees these as the right client-server abstraction for agents.

Cloud agents with built-in testing — The next capability jump: agents that run in the cloud, test their own code, and prove correctness before showing you a diff. This shifts responsibility from the human reviewer to the model and could increase cloud agent usage by 1000×.

Devex runbooks for models — Teams should create explicit instructions for how to boot up all services in the right order so that an AI agent can test an app like a human would. Without this, the model silently degrades.

Managerial workflow for engineers — As models improve, engineers will spend more time allocating tasks, reviewing high-level output, and using “managerial instinct” rather than writing code line-by-line.

Self-driving codebase (future concept) — Allocate a daily budget (e.g., $100K) to a codebase, and agents autonomously handle security, tech debt, bug fixes, and feature work. This is a speculative vision, not a current practice.

Unanswered questions and omissions

What are the specific RL algorithms? The speaker explicitly declines to discuss them, calling them “hard to talk about.” The entire training methodology remains a black box.

How does the model “prove” correctness? The talk insists the model should test its own code, but never explains the mechanism. Is it running unit tests, integration tests, doing visual regression, or something else? The hard part of testing—knowing what to test—is left unaddressed.

Why doesn’t model routing work? The speaker says routing confuses users and that Cursor avoids it, but there’s no diagnosis of the underlying problem. Is it a UX issue, a technical limitation, or a model-capability gap?

What did the browser experiment actually teach about agent organization? The interviewer asks about flat vs. hierarchical agent structures, but the speaker only shares the emotional shock of seeing the model do something he couldn’t. The concrete lessons about multi-agent coordination are missing.

How do you prevent a self-driving codebase from going off the rails? The vision of allocating $100K/day with no human review raises obvious questions about quality, security, alignment, and cost control. None of these are addressed.

What about cost, latency, and environmental impact? Running millions of sandboxes and training models with massive RL is expensive and energy-intensive. The talk doesn’t mention trade-offs or accessibility for smaller teams.

“Coding got solved” — what does that actually mean? The statement is deliberately provocative, but it’s never defined. If coding is solved, why are capability jumps still needed? What remains unsolved? The tension is left hanging.

What skills should engineers develop now? The advice boils down to “go along with it” and “review every line if it matters.” There’s no concrete guidance on how to cultivate the “managerial instinct” or which niches will remain artisanal.

The “devex for models” problem is described but not solved. The speaker says companies will need devex teams to write runbooks for AI, but offers no examples, standards, or tooling. How do you maintain such runbooks as the codebase evolves? How do you verify the model follows them correctly?

Job displacement and ethics are barely touched. The talk acknowledges the scariness in passing but offers no reflection on the societal implications of “no one writing code by hand” or self-driving codebases.
