Bruno Sanguinetti, CTO of Dotphoton, claims that a small Swiss startup can deliver ESA-grade requirements traceability for a satellite image compressor using Grist plus GitHub, LaTeX/Typst, and Docker — and that Grist is effectively the only tool that makes this workflow possible, because formal QA tooling (IBM Doors) is too clunky and expensive, and general-purpose tools (Word, Notion, Airtable, Monday.com) fail on speed, relational structure, or WYSIWYG exports. The proof he offers: Dotphoton cut its documentation-to-execution time ratio from roughly 5:1 (at his previous company doing Ariane rocket ignition-system testing) to 2:1 or 3:1, achieved an 8:1 compression ratio versus the industry's ~2:1, and got customer sign-off to replace a "many tens of thousands" quote that would have required hiring two extra people. A skeptic could dispute the "only software" claim or whether a spreadsheet-like tool can really satisfy formal space-industry QA at scale.

Key points

Traceability means one-to-one matching across the V model's layers. Acceptance tests must map to real needs defined at a specific date; requirements must map to needs; tests must map to requirements — and all of it must stay consistent as code and documents evolve over a multi-year project (theirs ran 2021–2023).

The enemy is QA displacing quality. Formal traceability processes become the focus instead of the actual work, and engineers "miss the forest for the trees" — a fresh outsider might spot an obvious flaw (centimeters vs. inches) that process-buried insiders can't see. The fix is making document output automated and painless.

Documents must be reproducible and versionable. The same Word file rendered as 300 pages on one machine and 301 on another; French-vs-English Word versions silently added pages. Word/Access failed; Notion's exports weren't WYSIWYG — catastrophic when legal requirements depend on exact output.

Bugs are expected; undeclared bugs are not. ESA doesn't expect bug-free software — it expects you to find, declare, and trace bugs so a conscious go/no-go decision can be made and fail-safes designed.

The architecture: Grist as database and interface, GitHub as versioned release. A Python script pulled Grist data via API as CSV/JSON, injected it into a LaTeX template, and committed the Grist file, LaTeX source, and code into one repository that became the release — everything in sync. The Grist file itself goes into GitHub so relations are versioned too.

The system evolved through three generations: v1 (Python + LaTeX), v2 (bidirectional GitHub integration, automated test-status updates, PDF generation — "maybe too many features"), v3 (simpler, Docker services, Typst for PDFs).

Open source needed a commercial backer to pass procurement. Space-project tools must themselves have traceable development; buying Grist's commercial version gave them someone to call "if it stops working on a Friday night like notion."

Change impact analysis went meta. They deliberately did not track requirement changes in Grist — it got "too messy and conceptually difficult" — and instead tracked changes in Markdown files in a GitHub master project with submodules, treating Grist as "a snapshot of the system as it is now."

Tools, practices, and methodologies

Grist — relational database/spreadsheet hybrid used as both the traceability database and the team interface; chosen over Airtable, Excel, Monday.com, and Notion for sub-second copy-paste, speed, and a data model that "makes sense" to technical teams.

V model — the space-industry QA framework: define needs top-down, implement, then verify bottom-up with layered tests; Grist tables map each layer's artifacts to each other via requirement IDs and verification methods.

GitHub as the release mechanism — Grist database file, LaTeX/Typst source, and code all committed to one repository; the repo is the release, guaranteeing documents match delivered code.

Python script via Grist API — pulls data as CSV/JSON and injects it into LaTeX templates; the original automation layer.

Typst (via a Docker service) — templating language for PDF generation that renders in ~10 milliseconds and supports functions (e.g., sums) inside templates; triggered from Grist via a toggle column firing a REST request, with the PDF uploaded back as a row attachment.

Toggle-column + request trigger pattern — replacing n8n: a checkbox column triggers a request to a service, which does its work and resets the toggle.

Local LLM (Gemma, on-premise) — required for security/customer constraints; auto-fills CRM fields from pasted emails and drafts quote emails; also used (with Claude, on non-critical parts) for writing change-impact Markdown files.

Picasso-bison approach to schema design — build the overbuilt version, then delete fields in two seconds until only the essential lines remain; back up by downloading the whole database and re-uploading if something breaks.

The 8:1 compression result is claimed but never connected to the traceability system — no evidence that the Grist workflow caused better engineering outcomes, only cheaper documentation.
