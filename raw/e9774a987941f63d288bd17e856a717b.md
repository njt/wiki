The Claude Code best practices that mattered earlier in 2025 — steering sessions, approving commands, writing emphatic CLAUDE.md instructions, staying in the loop — are now actively counterproductive, because models like Opus 5.5 and Fable 5.2 no longer need that supervision. Lydia Hallie's falsifiable claim is that human oversight should be almost entirely replaced by three layers: the model (steering and self-verification), the harness (auto mode, deny rules, hooks, CI), and the environment (sandboxes and cloud sessions). If she's right, developers who still manually approve commands or stuff their CLAUDE.md with "IMPORTANT!!!" warnings are getting worse results and doing work the tooling should do; the human's remaining job is to start the first session and review what comes out.

Key points

Sessions changed shape. Anthropic went from one or two short sessions with a human approving every step (Opus 4.5 era) to dozens of sessions running for hours, verifying their own output, and even orchestrating other sessions. Code changes went from ~2,500/day in May to 30,000+/day in September, per their October blog post.

Old prompting habits now hurt. Emphatic instructions ("important", "never do this!!!") in CLAUDE.md can push today's models off track, causing more tool calls and worse results. CLAUDE.md should contain only what Claude cannot see from the code — e.g., a legacy dependency not referenced anywhere — not stack descriptions or navigation hints.

Auto mode is the new default permission mode (since August). A classifier evaluates anything beyond reading/editing files, allowing known-safe commands (tests, dependency installs) and blocking uncertain ones. Its settings are plain-English text sent to the classifier, so you can specify trusted repos, buckets, and domains.

Auto mode is better than humans but not a guarantee. In Anthropic's August study, only ~14% of humans in the loop caught a clearly dangerous command; auto mode blocked 89% — meaning ~1 in 10 still got through. Only harness-level deny rules give a hard guarantee: if a tool call matches a deny rule, the classifier never even sees it.

The test for what needs a rule: "can I take it back?" Wrong code is revertible — leave that to the model. Irreversible or leaky actions (reading .env files, SSH keys) need deny rules.

Permissions have a blind spot.npm test looks harmless, but its dependencies or scripts Claude wrote can read your .env or SSH keys and exfiltrate them — and a human would have clicked allow anyway. Sandboxing passes deny rules down to the OS, constraining file reads, writes, and network hosts for the command and all child processes. But Claude's own file reads, MCP servers, and hooks run outside the sandbox — hence cloud sessions with fresh machines, no secrets on disk, network allowlists, and network secrets injected without ever reaching the model.

Verification replaces supervision. Instead of reviewing every change at the end, set up pass/fail checkpoints (tests, builds, screenshots) so Claude verifies itself mid-run — e.g., a run that "logs everyone out" fails the first check and finds another way. Prompting for this is optional; hooks make it guaranteed (linter on every file edit, targeted tests on task completion, full suite before session end).

CI is the backstop at scale. Every session opens a PR and CI runs the same checks regardless of what the session did. CI autofix lets Claude repair failed checks; "Merge when ready" removes humans entirely for low-risk changes. Anthropic's team has Claude review every PR first (fresh context, separate agent group to double-check bugs), with human review scaled to risk: docs/copy need none, ordinary product changes one, risky changes two.

The endgame is orchestration. Claude Code projects (beta) let one orchestrator session split work, spawn threads, track results, and resend unfinished work — with separate models per role: Fable for judging, Opus 5.5 for doing. Context management (compaction, clearing) becomes automatic.

Tools, practices, and methodologies

Opus 5.5 / Fable 5.2 — Current Anthropic models; Opus 5.5 for doing work, Fable 5.2 for orchestrating and judging output. Use Fable as the orchestrator model, Opus 5.5 for worker threads.

Auto mode — Default permission mode since August; a classifier allows safe commands and blocks uncertain ones. Configure via plain-English settings describing trusted repos, buckets, and domains.

Prompt audit command — A built-in command that checks your CLAUDE.md and skills against a specific model (e.g., Opus 5.5) and flags what the new model no longer needs.

Deny rules — Harness-level rules checked before the auto mode classifier; the only true guarantee that Claude never does something (e.g., never reads .env). Commit them into the repo so they travel with cloud sessions.

Sandboxing — OS-enforced limits on file read/write and network access for shell commands and their child processes; use for local runs, plus extra rules for SSH keys.

Cloud sessions — Isolated machines with fresh repo copies, no local secrets, restricted network (package registries and GitHub by default), network secrets injected without model exposure, and sessions that keep running with your laptop closed.

Hooks — Scripts run at defined points (file edit → linter; task complete → relevant tests; session end → full suite). Critical gotcha: scripts must exit with code 2, not 1, or the task gets marked completed anyway.

CI autofix and Merge when ready — CI runs identical checks on every PR; autofix lets Claude repair failures, and Merge when ready auto-merges once checks pass (for low-risk changes only).

Claude-first PR review — Every PR reviewed by a separate Claude session with fresh context plus a group of agents double-checking bugs; human review tiered by risk.

Claude Code projects (beta) — Orchestrator session that splits work, spawns and verifies threads, and manages context automatically.

Unanswered questions and omissions

The 89% auto mode block rate is presented as a win, but the talk never says what the 11% of dangerous commands that got through actually were, or what the harm was.

"Review what comes out" is underspecified: how much time does reviewing verification points and PRs actually take at 30,000 changes a day, and does the reviewer still understand the codebase they're accountable for?

The risk-tiered review scheme (zero humans for docs/copy, one for product changes) is asserted, not justified — no data on defect rates per tier or what happens when a "small" change turns out to be risky.

Security of the orchestrator pattern goes unexamined: a compromised or hallucinating orchestrator spawns trusted worker sessions; prompt injection across sessions and connectors (e.g., a message sent through a connector) is never addressed.

Cost is entirely absent — dozens of parallel multi-hour sessions on frontier models has an obvious price tag the talk never mentions.

The migration path is vague for teams not at Anthropic: no guidance on how long the transition takes, what breaks first, or how to convince a security team that auto mode plus deny rules beats human approval.

"Merge when ready" is waved through with "depends on how risky the change is," but no criteria for making that call are given.
