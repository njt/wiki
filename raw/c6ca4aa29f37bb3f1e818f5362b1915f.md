DuckLake's decision to store its catalog and metadata in a SQL database rather than on object storage is what makes it the first lakehouse format that can genuinely serve interactive, low-latency workloads — and with a handful of tuning techniques (partitioning, sorting with space-filling curves, parquet write settings, inlining, and catalog maintenance), you can get both faster and cheaper without trade-offs. The speaker's falsifiable claim is that Iceberg and Delta "put their metadata in the wrong spot": because object storage is high-throughput but high-latency (~100ms per request), Iceberg's four serial metadata steps cost a third to half a second per query even in the best case, while DuckLake's single ~5ms Postgres round trip plus DuckDB 2.0's asyncio (3x faster bulk reads) makes it the faster architecture by design, not just by tuning.

Key points

Architecture is the tuning framework. DuckLake has three tunable buckets — the catalog/metadata (a relational DB like Postgres), storage (object store holding parquet), and compute (usually DuckDB). Every optimization maps to one of these.

Latency math vs. Iceberg. Iceberg requires four serial requests (catalog → manifest list → manifests → parquet), each potentially 100ms+ on object storage. DuckLake talks to Postgres once (~5ms), then reads parquet. Four decades of relational database optimization (indexing, fine-tuned lookups) apply to the metadata layer.

Measure before tuning. Turn on logging everywhere: Postgres slow-query logs with explain plans, DuckDB profiling (HTTP times, scan time, join time). The speaker's move: point an AI agent at the JSON logs and ask what the bottleneck is.

Rules of thumb by workload shape. Big reads → file layout (partitioning/sorting). Small reads → catalog. Big writes → compute (compression cost). Many small writes → inlining.

Partitioning and sorting are the first lever. DuckDB 2.0 adds PARTITION BY and SORT BY in CREATE TABLE/CTAS. Partitioning skips whole files; sorting enables row-group-level pruning via parquet statistics. "Hidden partitioning" lets analysts filter on the original column while the optimizer reasons about transforms (year/month/day). Sort-by-expression is unique to DuckLake — sorting can be any scalar function, not a fixed library list.

Z-ordering/Hilbert curves for multi-filter workloads. Sequential sorts scramble the second column; space-filling curves keep data "near" on multiple dimensions contiguous, so geographic-style multi-column filters read one contiguous chunk.

Parquet write settings: use parquet v2 (a decade old, safe), switch snappy → zstandard (more Pareto-optimal), and multiply row group size 2–4x, targeting ~10 row groups per file. Tune settings jointly via design of experiments with an agent — sequential tuning lands in local optima. Combined, the speaker saw ~40% improvement, "not a 10x."

Inlining is DuckLake's killer feature for small writes. Inserts ≤10 rows (default) go into the catalog, not parquet — lower latency, no small-file problem, transactional and instantly readable (unlike a Kafka buffer), and it eliminates most compaction work. Flush at roughly your target parquet file size (~1M+ rows).

Catalog tuning: index the column-statistics table (the biggest catalog table), size the DB so the whole catalog fits in RAM (a petabyte-scale lakehouse catalog is only a few gigs — skip the "$1 postgres"), and expire/delete old snapshots (progressive stair-step expiration: daily → weekly → monthly).

Maintenance is mandatory, unlike a warehouse: compact deletions and compact files to ~1GB (bigger for archival data); set the deletion window to 10 days so you don't need object-storage retrieval after a vacation. Logically deleted files still cost storage until physically removed.

DuckDB 2.0 asyncio: one core launches ~4 background threads for parallel object-storage reads instead of 1 synchronous — hence the ~3x bulk-read speedup, confirmed by an audience member's production workload.

Tools, practices, and methodologies

DuckLake — open lakehouse format with SQL-database catalog; set up in three commands, scales to petabytes, data stays in your own S3/GCS bucket.

DuckDB profiling/logging — enable to log HTTP times, scan/join/aggregation timings as JSON for agent analysis.

Postgres slow-query logging — log queries over a time threshold with query text and explain plan for catalog tuning.

Z-ordering / Hilbert curve sorting — multi-column clustering for workloads filtering on different columns.

Design of experiments tuning — have an agent vary file size, row group size, and compression jointly rather than sequentially; target ~10 row groups per file.

Inlining + periodic flush — buffer small inserts in the catalog, flush at ~target file size; monitor inline volume via the SQL catalog.

Snapshot expiration (progressive/stair-step) — two SQL commands to expire and delete old versions, tiered by age.

Hot/cold table split — Matt's pattern: point most users at a "current" table, power users at a "historical" table, with atomic cross-table transactions making the rollover safe.

CTAS re-clustering — CREATE OR REPLACE TABLE ... PARTITION BY ... SORT BY AS SELECT * to retrofit layout onto existing data (note: new partition/sort keys only apply to new files otherwise).

Unanswered questions and omissions

No live benchmarks were shown; the 40% tuning gain is from the speaker's own testing six months ago, and the 3x DuckDB 2.0 figure is partly corroborated only by an anonymous chat comment.

The headline Iceberg-vs-DuckLake latency comparison is arithmetic from assumed request counts, not a measured head-to-head benchmark.

The Hive Metastore question from the audience was explicitly deferred to the end and never answered.

Write contention is mentioned in passing ("someone beat you to it and they changed the table while you were writing" produces orphaned files) but how to detect, prevent, or clean these at scale isn't covered.

No discussion of catalog high availability, failure modes, or what happens when Postgres goes down — the single catalog is a new dependency Iceberg's REST catalog also has, but the operational story is unexplored.

Cost modeling is thin: how catalog database costs scale with snapshot frequency, and when a managed warehouse beats a self-tuned lakehouse, go unaddressed.

Concurrency, access control, and governance — table expectations for a lakehouse talk — never come up.

The "it depends" refrain (compression, wide tables, workload mix) is honest but leaves the reader without a decision procedure beyond "ask your agent to run experiments."
