# Real-Time Multiplayer Interfaces

### When humans and agents work in real-time, the interface becomes a shared protocol, not a screen. The work is teaching both sides to read each other, respond, and know when to interrupt.

*Version of a thesis I wrote here on content.moldandyeast.com.*

Cronjobs are having a comeback. We add little heartbeats to our agents, they start to hold state *(durable objects ? =))*, and state is the thing that turns a tool into a participant. Once both sides persist, every interface is a multiplayer interface. Which means we need real-time ones.

By real-time I don’t mean fast alone, speed will be solved. I mean a fluid dialogue, where both sides continuously listen, respond, and can interrupt. Not the trad sending a prompt and waiting through a thinking loop. Something more granular, more back and forth. A true conversation. Agents are increasingly durable now, they hold state, and self-driven, they run on heartbeats. They can start to read from sensors, APIs, cameras, the room. And simultaneously our roles are shifting underneath all of it. We move from the center, as operators and executors, to the edges, as initiators at the first mile, confirmers at the last, or observers a mile above.

### Interruption goes both ways

The agent can cut into my thought the same way I cut into its task. So real-time collaboration hinges less on the technology and more on a shared social protocol between us and them. Both sides need to read each other’s state and know when, how, and whether to interrupt, without fracturing attention or spiraling each other off task. TLDR: we both need to be able to read the fucking room. ;)

So far, interrupting an agent mid-task can make it spiral, the way we do when we get yanked off a thought. They are more human then we give them credit to already. Agents though will get better at holding focus *(that’s how tech works)*. But they are the ones who have to learn when, where, why, and especially when not to interrupt. Although it probably still cuts the other way too. The ease of running many streams at once fractures our attention. So our current obvious fix, let agents skip asking for permission and just report when done, but that only moves the problem. We add more streams and more streams and need to find the next layer to enable skipping again. Key is letting them interrupt us mid-thought makes everything worse *(usually)*. If you think your attention is fractured, wait till you unleash the swarm. 

### The asymmetry that worries me

Reading and responding cost something on both sides, but not the same thing. For the agent it costs computation, and computation is buyable. I guess thats the bull case for what all those data centers are for. For us in reality it costs attention, and attention is not buyable *(only out-sourcable)*. We already struggle with the amount we are asked to pay. So under incomplete and shifting data, prioritization and misunderstanding become the things we are actually designing around. 

### We stop designing screens

We can already generate any interface for any task we can articulate. The challenge is no longer whether we can generate them *(it never was if we should)*. It is whether they match intent and context, in the moment, as both sides read and respond to each other. So we stop designing fixed moments. We design the constraints, primitives, and protocols from which the right interaction gets ideally derived in the moment *(THE DREAM)*. 

### Five principles for the loop

That shift, from drawing screens to designing the system that grows them, is what I am currently explore:

- **Mutual readability.**

Both sides observable to each other. Not a one-way adaptive surface, a loop.

- **Appropriate load.**

Proportionate to the payoff, on each side. “Add more compute” and “demand more attention” are not design solutions.

- **Interruption as a first-class act.**

When, and especially when not, in both directions.

- **Derived, not fixed.**

The question is not whether interfaces can be generated, but whether they match.

- **Learns with us, does not calcify.**

Grows through a two-way loop, stays self-reflective, never compounds our preferences into bias.

### The wicked part

That last one is the hard one. The moment we co-create a shared abstraction layer, it can carry quiet bias, and it starts cold, with no precedent to draw on. An adaptive interface can only respond well to a situation we have met at least once. Everything else is a guess. So maybe we rehearse. Small, recurring, Duolingo-like interactions that surface the edge cases before the high-risk moment, not during it. You don't want to work out with an agent how to handle a security incident while it is happening.

### What to play-test?

=> **How do we read and respond to each other in real-time?**

- How might we state intent concisely, without leaving too much room for ambiguity? 
- How might we capture the right context to support intent, without collapsing into surveillance, and without pretending more context alone solves it? 
- How might we make situational awareness legible: time, place, device, the task in focus, and the weight of the task we might be disrupting? 
- How might we switch roles organically as we initiate, execute, or oversee, when responsibility itself is fluid? 
- How might we rehearse for high-risk moments before they happen, rather than improvising in them? 

None of these are solved. That is the point. Let’s play together.
