Dr. Egor Kraev on Structured Objects: "No Escape, No Leak"

Key Points

The most impactful production use of GenAI is making LLMs emit structured objects — reliably, every time. Kraev, who has done ML "since the last millennium," frames the whole talk around a single claim: LLMs only add value when their output plugs into old-school systems, and those systems "expect objects of a very defined shape," not essays. The "agent AI nirvana... I don't think will ever happen." Everything else follows from this.

Schema validation is not enough; you need guaranteed validation of complex, real-world constraints. Pydantic-backed structured output guarantees the shape. It does not guarantee that names and amounts match the input, that a SQL query returns a non-empty result, or that a string contains valid markdown. "Reality is rarely so simple that just enforcing a schema is enough."

Every standard approach leaks. He walks an escalation ladder — prompt + parser + hope ("probably will not work"), JSON mode (valid JSON, wrong schema), function calling/with_structured_output (valid schema, unvalidated semantics), retries ("try again, try again, you might get lucky"), validator-as-a-tool agentic loop (the LLM gives up after 3–4 tries and returns something anyway), and return_direct (still no guarantee the returned object is the validated one). The recurring failure: "you cannot trust the LLM to reliably relay its input to the tool. You just can't, because it's not what it does."

The fix: make the validator the only exit. In his framework, an agent flag forces return through the validation tool — "there is no escape, there is no leak." If validation fails after X iterations, you get None: "at least you get a clear failure. You don't get something that the LLM thinks is valid, but it's not."

Don't let the LLM touch objects; give it tools that touch objects. For modifying complex artifacts (chart configs, etc.), the "ship in a bottle pattern" keeps the object living outside the LLM, with the LLM choosing among semantically natural actions (add a series, change chart type). Otherwise, "if you just say, here's the original thing, change X, it will change X, it will also change Y, Z, A, B and C all over the place." Same principle, he says, should govern MCP servers: "You don't have atomic transactions as tools. You have meaningful semantically natural actions."

Don't generate SQL; generate semantic-layer queries. He "laugh[s] evilly whenever I see anybody declare reliable security SQL generation." Instead, expose a semantic layer of metrics and dimensions, have the LLM produce a small pydantic query against it, and convert to SQL with "fully deterministic machinery" that is "stupidly easy to make work."

The philosophy: LLM as a small box among boxes, not a conductor. "Contrary to most of the agentic hype," give the LLM "as little leeway as possible" and let it do only "the one little thing that nothing but an LLM can do." Everything deterministic — including data orchestration — stays old school. "This way it's cheap, it's simple and it works."

Second production pattern: keep LLMs off the critical path. Have the LLM produce a validated complex object once, then reuse it. This gives you "squishy inputs, but hard outputs" — faster, more reliable.

"AI is just a marketing term." — deployed to justify treating LLMs as one tool among many.

"If you send information to a regulator that's wrong, your company may not survive it." — why the Wise suspicious-activity-report use case demands guarantees, unlike customer care, where "you get shitty customer care, but your company can survive it."

"You could probably write a SQL query that could compose the works of Shakespeare if you tried hard enough." — why SQL's expressiveness makes LLM-generated SQL unverifiable.

"I laugh evilly whenever I see anybody declare reliable security SQL generation." — his bluntest dismissal in the talk.

"The LLM is an unreliable messenger... you cannot trust the LLM to reliably relay its input to the tool. You just can't, because it's not what it does." — the recurring theme, stated as a law of nature.

"There is no escape, there is no leak." — describing the validation pattern where the agent can only return through the validator.

"Using LLMs to remove friction so you can do the same things you used to before, but now the tool has common sense." — his prediction for the next wave, as the "bigger LLMs" wave saturates.

Tools, Practices, and Methodologies

Pydantic — Python data-model library. His baseline requirement: "I would never ever try to do anything simpler than this when producing structured objects." Use it to define the schema for structured output.

LangChain with_structured_output (and equivalents in every framework) — schema-guaranteed LLM output via function calling. Guarantees schema validity only, not custom validators — but "in a lot of applications that's already enough."

with_retries — the "dumbest approach": retry until lucky. Treated as a floor, not a solution.

Validator-as-a-tool agentic loop — the classic pattern where the agent calls a validation tool before returning. "For me, this kind of feedback loop is exactly what an AI agent is." Insufficient because the LLM can give up and return anyway.

return_direct — tool attribute that returns the validated result directly, bypassing the LLM. Eliminates one leak; leaves the give-up leak.

Motley Crew — his open-source agentic framework (written a year ago to mix and match agentic frameworks). The key features: an agent flag forcing return only through the tool (the validation pattern), tools with direct access to the agent's original input, and a key-value store attached to the agent that tools can use to exchange tokens/blobs without the LLM as messenger. He admits you could build all this in custom Python or LangGraph — "here it comes built in."

Semantic layer — an abstraction exposing only the metrics and dimensions users might want. The LLM generates a small pydantic query against it; deterministic code converts to SQL. His recommended replacement for direct LLM SQL generation.

Ship in a bottle pattern — the object lives outside the LLM; the LLM manipulates it only via semantically natural action tools (add/remove measure, add dimension, change chart color). Also his stated pattern for MCP servers.

Intermediate stripped-down pydantic object — even when the final output is complex, have the LLM produce a minimal object containing only the fields it should decide, then have the validation function convert it to the real thing. Used to turn a loose wordy prompt into full SQLAlchemy schemas with foreign keys.

Regex + spaCy entity extraction — "old school" verification that names and amounts in a suspicious activity report exactly match the raw input.

LLM log-likelihoods as classifier features — for LLM-as-classifier, return log likelihoods (a structured output) and feed them into an old-school model alongside other features.

Synthetic Data Vault — library he recommends (but didn't use) for reproducing the structure of a real dataset.

Headless Claude Code — for stage-two synthetic data population: describe the data-generating process in words, let Claude Code write the Python, wrap it in validation (code must run, must touch every table). For code generation generally: "I wouldn't use raw LLMs, I would use something like Claude Code or Cursor."

Restart the loop — when the LLM gets stuck in a wrong pattern, "just restarting the loop has always worked" so far.

Off-the-critical-path pattern — LLM generates a validated complex object once; the object, not the LLM, serves production traffic. Faster, reusable, reliable.

Unanswered Questions and Omissions

Zero numbers. No iteration counts, failure rates, latency, token costs, or before/after reliability metrics — from a talk whose entire thesis is reliability. "After X iterations" — what is X, in practice? What does a validation loop cost in wall-clock time and tokens?

The termination caveat is hand-waved. He concedes "there is no guarantee that the validation loop will ever conclude" and covers it with "so far, restarting the loop has always worked." That's an anecdote, not a guarantee — from a talk titled around guarantees.

Validation guarantees shape, not quality. A schema-valid, validator-passing object can still be semantically wrong in ways the validator doesn't check. No discussion of evaluating output goodness, only output validity.

Guardrails and DSPY: explicitly dodged. "To be honest, I don't know. I haven't tried guardrails." His novelty claim ("I haven't really seen it advertised elsewhere") is untested against a ecosystem he admits he can't track — "there's been an agentic framework a month at least lately."

Security is absent. He mocks "reliable secure SQL generation" yet never addresses prompt injection, adversarial inputs, or what happens when the data feeding the semantic layer is attacker-influenced. For a talk about giving LLMs database-adjacent access, that's a hole.

No human-in-the-loop discussion. For regulator-facing outputs (the SAR example), is there a human reviewer on top of the validation loop? Never said. Also unclear: was the SAR system actually deployed at Wise, or is it a motivating hypothetical?

Conflict of interest unexamined. The talk's central solution is his own framework. LangGraph is acknowledged as capable of the same custom flows only in passing during Q&A.

Multimodal output: punted. "I'm not sure how you would do this" — the entire validation edifice depends on deterministic validators, and he concedes LLM judges return you to "the stochastic country." This is a real boundary of the approach, noted but not explored.

The "model doesn't matter" claim is asserted, not shown. "As long as it's something released this year, it's probably going to work" — no evidence, and it sits in tension with widespread experience that weaker models struggle with tool-calling discipline.

Big-picture claims without argument. "Agent AI nirvana... I don't think will ever happen" and "the current wave of just making the LLMs bigger is saturating" are both delivered as verdicts, not defended.

State and concurrency ignored. The key-value store attached to the agent is sketched in one breath — no word on persistence, multi-user access to a shared object, or what happens when the "object hanging around somewhere" is needed by two sessions at once.
