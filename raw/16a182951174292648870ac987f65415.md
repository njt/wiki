Platform Team Structures and Concerns — Adrian Cockcroft (Craft 2025)

1. Key Points

You never build "a platform" — you build a layered stack of platforms. Each layer has different knowledge, tooling, and ownership: deploy platform (Kubernetes, Lambda) on top of virtualization/networking (EC2, VMware), on top of language platforms, OSes, and hardware. Different teams handle different layers, and the layers "sediment" — platforms accumulate functionality moving up the stack while pushing commoditized pieces down to layers below. Keep platforms thin and keep refactoring.

Treat every platform as a product. Every platform team needs a product manager — explicitly hired, or the line manager if the team is small. Without product management you can't prioritize the flood of feature requests or maintain a roadmap. The teams that do this well "hire them into these roles."

Internal and external platforms obey opposite physics. Externalized interfaces must be stable (Netflix's TV firmware API can't break for a decade); internal platforms should change constantly and messily. Vendors externalize their interfaces, so their incentive is "to fatten their layer so they can charge you more" — the exact wrong incentive if you want a thin, fast-evolving platform. Netflix's answer: prefer open source, and contract vendors to support open source tools rather than sell fat platforms (Netflix was nginx's first customer — "we actually paid the guy to start the company").

Netflix's strategy: thin fast-changing layer on a stable AWS base. When AWS lacked a key management system, Netflix built one; when AWS shipped KMS, Netflix retired theirs and migrated. Repeatedly. They deliberately avoided vendors adding functionality on top of AWS so AWS itself would be pushed to evolve.

Wardley maps are the communication tool for platform migration. Start with the user need (never "installing Kubernetes" — that's the wrong answer), build the dependency chain underneath, then argue as a team over every arrow: what to push right into commodity, what to buy as a cloud service, what stays custom. The map becomes the shared roadmap.

Nubank proves the model at extreme scale. 118M customers, thousands of Clojure microservices on Datomic/DynamoDB ("the largest customers of DynamoDB on AWS's platform"), ~1,000 deploys per day (24,500 in April alone), running core banking on Kubernetes on spot-market ARM chips — "if you're a traditional banker, your head explodes somewhere in that sentence."

Prioritize platform work with a Doomsday Clock. For every platform component, the product manager's job is to know when it will stop working and how long the fix takes. Sort by that, throw effort at the top of the pile, and you stop reaching doomsday.

The stability-vs-change conflict is solved by versioning and traffic routing. Deploy new versions alongside old ones (immutable, additive — zero risk until traffic routes to them), let change-hungry teams debug new features, then let stability "sediment across" to everyone else. The fundamental primitive is version-aware traffic routing — "the thing we built in 2010, which a lot of people still aren't using today, which confuses me."

The client library is the interface, not the wire protocol. Consumers import the service team's client library; all protocol versioning is hidden behind it. And client and server should have different object models ("facets") — sharing an object definition across a microservice boundary is accidental coupling that locks versions together.

3. Tools, Practices, and Methodologies

Team Topologies (book) — The source of the "platform team" concept; use it as the framework for deciding what kinds of teams to build.

Wardley mapping — Map user needs over a dependency chain positioned by evolution stage (custom → product → commodity); use it to argue out platform migration arrows as a team and produce a shared roadmap. He references Simon Wardley's morning keynote.

MapKeep — The tool he used to draw the travel-search example map; a practical way to build your own platform migration maps.

The Doomsday Clock (Nubank / Kat Swetel) — Prioritization method: each platform product manager estimates when their component stops working and fix duration; sort the portfolio by that and clear the top of the pile.

Immutable code, service pattern — Every push starts a new autoscale group alongside the old version; zero production risk until traffic routes to it. Enables canary testing in production.

Version-aware traffic routing — The fundamental primitive (Netflix built it in 2010); route by version to control who sees new code — test cell first, then a cohort, looking for "measurable improvement" (hypothesis-driven development).

Feature flags / A/B testing — LaunchDarkly, or the Wasabi library (2016-era); the switching mechanism on top of version routing.

Version scheme: interface.feature.bugfix — Bug fixes get fully automated canary rollout around the world; features need feature-based routing; interface changes mean keeping old versions alive a long time.

Client library as the interface — Consume dependencies by importing their client library from your repo/artifactory; the service team hides all protocol versioning behind it. Keep it simple: "the disk device driver, not the file system." Bonus: building the client forces you to consume your own service for testing and load testing.

Facets — Give client, server, and cache different object models (client knows only "name," server knows the full customer) to break the accidental coupling of shared object definitions across microservices.

Version pinning + change one thing at a time — Never deploy your new code on a new dependency or platform library; pin everything, change one layer, canary it, then move to the next. "Completely automatable extra work" — the build pipeline unpicks multi-version deploys into individual testable ones.

Garbage collection for versions — Deploy is synchronous, cleanup is asynchronous. Incremental tidy-up, or "stop the world": the quarterly Breaking Build (a Breaking Bad pun — posters with a date, old versions removed from the build repo, production labeled as bad). "You either do it incremently or all at once."

Nubank's reference stack — Clojure microservices, Datomic on DynamoDB, Istio service mesh, Kafka, EKS with Karpenter managing nodes/pods, EC2 with Intel/Graviton, heavy spot usage; VictoriaMetrics + Grafana replacing Splunk for observability.

Controllability — The discipline after observability: chaos testing, game days, incident management. The reliability team by another name.

Megpt (GitHub) — His open tool for building an AI persona from an author's content: point a published-content CSV at YouTube playlists, PDFs, blog posts, copy to Google Drive, ingest via Supra's free tier. Extensible — send him a pull request to become a sample author.

Supra (supra cockcroft chat) — His own AI persona, trained on his blog posts and talks; ask it the questions he's answered a thousand times.

Cursor + Claude — His vibe-coding environment for building the workload-analysis tools nobody else would write.

Deming's supplier principle (via John Willis) — Pick suppliers and go deep; build a mutually beneficial relationship (keiretsu-style). Netflix made AWS better and AWS "took very, very good care of us." Too many suppliers at once creates conflict; abusive relationships mean get out.

4. Unanswered Questions and Omissions

The title promises team structures; the talk delivers platform structures. Team Topologies gets one sentence of endorsement. Nothing on team sizing, Conway's Law alignment, interaction models between platform and stream-aligned teams, or how to actually form these teams — the organizational half of the topic is mostly absent.

The versioning scheme's cost is admitted but never quantified. "It sounds like a lot of extra work, and it is extra work" — hand-waved as "completely automatable," with no discussion of who builds and maintains that automation, or the operational overhead of running unlimited concurrent versions ("I have no idea how many versions there were. Lots.").

The advice is frozen in 2014. He explicitly disclaims: "I left Netflix in 2014, so what they do now, I don't know." Does the hand-rolled version-routing approach still make sense when Nubank runs Istio, which handles traffic shifting natively? The tension between the two halves of his own talk goes unexamined. He also concedes "I don't know what people use now" for A/B testing libraries.

Regulation at Nubank is a punchline, not a topic. Core banking on spot-market ARM chips gets the "head explodes" joke, but how Nubank satisfied Brazilian banking regulators, auditors, and resilience requirements is never addressed — arguably the hardest part of that story.

Vendor lock-in counterarguments are dismissed, not answered. The Q&A asks directly about reliance on AWS/Azure; his answer is "go deep on one supplier." The failure mode of that strategy — pricing leverage, regional outages, strategic dependency — is never weighed.

The classic platform-engineing failure mode is missing: adoption. Nothing on the "build it and they don't come" problem, developer experience metrics, golden paths, or how to measure whether a platform team is succeeding. No KPIs anywhere in the talk.

The Doomsday Clock's hard part is glossed over. Estimating when a scaling limit will bite and how long a fix takes is a forecasting problem; he describes the sorting, not the estimation.

No legacy migration path. Both case studies (Netflix, Nubank) were cloud-native from early on. Nothing for the majority of the audience: companies with data centers, mainframes, or existing platform debt trying to move.

Facets' maintenance cost is unexamined. Maintaining divergent object models for client, server, and cache avoids coupling but creates duplication — who keeps those in sync, and at what cost, is untouched.

The AI persona segment is a tangent. Roughly the last ten minutes pivot to Megpt and vibe coding — entertaining, but it crowds out the "how to make it work" material the talk structure promised, and AI's impact on platform engineering as a discipline (rather than on Adrian's personal productivity) is never discussed.

Internal platform funding and team-topology economics. Product managers are mandated, but how platform teams are funded, whether they charge back, or how they survive budget scrutiny is never raised.
