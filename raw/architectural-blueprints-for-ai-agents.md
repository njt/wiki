The business driver is a labor shortage, not novelty. Nokia's private-network division (2,000 people) builds systems for mines, trains, and energy — one network function alone has "a configuration file that contains 27,000 configuration entries." Agents exist to make scarce engineers productive, then to run autonomously inside the network.

Learning 1: generic agent frameworks don't survive industry. They tried LangChain, LlamaIndex, and most recently Atomic Agents — all "totally different abstractions." For agents embedded in real complex systems, build your own hosting logic, orchestration logic, and architecture concept.

Learning 2: vector RAG is not enough. After injecting "thousands of PDF files," Confluence pages, and JIRA content into various vector DBs, they concluded semantic similarity cannot deliver relationships and deep context. The fix is a deeply connected knowledge graph — Graph RAG.

An agent is "a kind of semantic execution logic." Still a class — structured input → operations → structured output — "but in a semantic way": it analyzes intentions and environment, decides, plans, selects and executes tools. It necessarily mixes LLM calls with native code (the "worker logic") — "it's unavoidable."

Environment is the design axis everyone skips. The agent needs an environment "precisely describing the world the same way how humans understand the world," represented as a graph. Agents both read/traverse it and write back — "creating new knowledge and... evolving the graph."

The blueprint has six blocks: operation manual, structured I/O, memory, environment/context providers, toolbox, worker logic.

The operation manual is not a prompt collection. It's documentation covering identity (invocation, capabilities, scope — so the agent can refuse out-of-scope work), purpose and expectations (the basis for evaluation), and an ontology — "a schema for the world." Stored externally via a repository pattern, so agents load the latest manual at runtime — meaning "an agent can build another agent."

Three orchestration patterns (credited to Anthropic's blog): router + agent handoff (linear), parallel execution + a synthesizer agent, and evaluator/observer loops — "I give you agent five rounds, five iterations to try to complete the task."

Memory is a four-rung ladder: naive queue (runs out of context) → LLM summaries ("sometimes it's good, sometimes it's bad") → vectorized memory (sometimes relevant, sometimes not) → graph memory — "the highest complexity but the most sophisticated."

The graph is fed by four pipelines: DITA customer documentation (XML from content repositories — "we try to go to the roots," not PDFs/Office files), a live scan of the Kubernetes cluster (microservices, interfaces, dependencies) to "mirror the real world to the agents," functional requirements, and all failures/bug fixes/support incidents — correlated into one property graph. At runtime: vector search to find relevant nodes, then traversal of their neighborhoods.

Tools must be designed, not wrapped. Don't "take a REST API and just mimic the API as a tool" — describe precisely what it does, its inputs and outputs. Externalize via MCP because "we cannot build all the tools that we need."

3. Tools, practices, and methodologies

LangChain / LlamaIndex / Atomic Agents — open-source agent frameworks. His use case: experimentation only; their abstractions don't map to industrial agents, so build your own hosting and orchestration.

Anthropic's blog on agentic orchestration — his recommended reading; the source of the three patterns he deploys (router+handoff, parallel+synthesizer, evaluator loop).

Instructor (Python library) — forces LLMs to emit structured outputs (Pydantic data classes, schematized JSON). Use for all agent I/O and to make chained agents compatible.

Pydantic data classes — define structured input/output contracts so one agent's output plugs into the next agent's input.

Neo4j — "probably the most popular graph engine"; one of their two production graph engines.

KùzuDB — in-memory, embeddable analytical graph engine; used in the demo to visualize the agent environment; can be embedded into any service.

Cypher — graph query language. "If you have any experience with SQL then you can just learn" it; he calls mastering graph query languages "an important skill."

Graph RAG — their core retrieval method: vector search to locate relevant nodes, then graph queries to traverse and pull the neighborhood. Delivers the relationships and deep context similarity search can't.

DITA — XML-based schema for technical content. Inject XML directly from content repositories instead of PDFs and Office files — "go to the roots."

MCP (Model Context Protocol) — standard mechanism for agents to discover external tools; build agents as MCP clients. "I believe that the model context protocols will be the standard for the future."

Repository pattern for operation manuals — store the manual outside the agent so it loads the latest version at runtime; enables one agent to modify another's behavior.

Command architecture pattern for the toolbox — register built-in and external tools; add or remove by configuration.

The memory ladder — queue → LLM-generated summaries → vectorized memory (in-memory vector DB) → graph memory; climb as context-window pressure and sophistication demands grow.

Four injection pipelines — DITA docs, live Kubernetes cluster scan, functional requirements, and failures/bug fixes/support incidents, all correlated into one property graph.

Evaluator/QA agents — custom agents that check other agents; automatable down to "an Excel file" of expert questions, compared against human answers, producing a quality score.

Intention manager — host-side logic that parses human intention and picks the best agent using the identity and scope declared in each agent's operation manual.

4. What the Blueprint Leaves Off the Page

Autonomous agents on live networks, zero safety discussion. The troubleshooting agent "runs commands," writes and executes bash and Python on systems where one function has 27,000 config entries. No guardrails, approval gates, rollback, blast radius, or "what if the agent is wrong" — in a talk whose flagship scenario is provisioning network slices in five minutes. Can an LLM chain even hit that latency SLA? Never addressed.

No numbers anywhere. The premise is engineer scarcity and productivity, yet there's not one metric: no time saved, no tickets resolved, no before/after.

"RAG simply not enough" is asserted, never demonstrated. No benchmark of vector RAG vs. Graph RAG. The obvious counterargument — that their RAG pipeline (chunking, metadata, retrieval quality) was the problem, not the method — is never entertained.

Graph drift and maintenance. The pipeline scans the Kubernetes cluster to "mirror the real world," but how often? What happens when graph and reality diverge? Who authors and maintains the ontologies — presumably the same scarce domain experts the agents are supposed to multiply?

Which LLMs, running where? A private-network, on-prem business injecting customer documentation and support incidents into graphs — and the talk never mentions model choice, on-prem vs. cloud inference, or data sovereignty.

No payoff criteria for the graph investment. He concedes graph memory is "the highest complexity" and graph skills are "a learning curve," but never says when a graph beats a vector DB. "Sometimes it's good, sometimes it's bad" is the closest he gets to a decision framework.

Evaluation is thin. The Q&A answer — domain experts, an Excel file, a quality score — contains no regression testing, no production monitoring, no handling of behavior drift across model updates. And who evaluates the evaluator agents?

Agent failure modes are absent. Wrong graph traversal, hallucinated steps, tool misuse — the observer/evaluator pattern is named, but its reliability is unexamined.

"An agent can build another agent" is dropped and abandoned. Self-modifying operation manuals raise governance, versioning, and safety questions the talk never touches.

Orchestration is outsourced to a blog post. He defers to Anthropic for patterns and shares no Nokia war stories: coordination failures, the cost of parallel agents, conflict resolution between agents.

The demo shows retrieval, not action. We see graph visualization and querying, but never an agent executing a real change on the network.

A small factual wobble: he calls Cypher "the international graph query language" — it's Neo4j's language (the ISO standard is GQL, which Cypher influenced). Minor, but a flag for how loosely some confident claims are grounded.
